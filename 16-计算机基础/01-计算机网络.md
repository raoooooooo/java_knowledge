# 计算机网络

> 📌 **一句话理解**：计算机网络的核心是**分层**——每一层只管自己的事，靠协议把数据从一端送到另一端；面试高频几乎全集中在 **TCP（三次握手/四次挥手/可靠传输）** 和 **HTTP/HTTPS（演进与安全）** 两条线上。

---

## 核心概念

### 一、网络分层模型 ⭐⭐⭐⭐⭐

#### 1. OSI 七层 vs TCP/IP 四层（实际用这个）

```
OSI 七层模型          TCP/IP 四层模型          举例协议
┌─────────────┐
│  应用层      │┐
├─────────────┤│      ┌──────────┐         HTTP、FTP、DNS、SMTP
│  表示层      │├─────►│  应用层   │
├─────────────┤│      └──────────┘
│  会话层      │┘
├─────────────┤       ┌──────────┐         TCP、UDP
│  传输层      │──────►│  传输层   │
├─────────────┤       └──────────┘
├─────────────┤       ┌──────────┐         IP、ICMP、ARP
│  网络层      │──────►│  网络层   │
├─────────────┤       └──────────┘
├─────────────┤       ┌──────────┐         以太网、Wi-Fi、光纤
│ 数据链路层   │┐─────►│网络接口层 │
├─────────────┤│      └──────────┘
│  物理层      │┘
└─────────────┘
```

> ⚠️ **易混点**：OSI 有 7 层，但**实际工程用的是 TCP/IP 四层模型**。很多面试官嘴上说"七层模型"，其实是 OSI 理论模型；真正落地的是四层（也有讲五层的——把网络接口层拆成"数据链路层 + 物理层"）。回答时说明清楚即可。

#### 2. 为什么要分层？

- **各层之间解耦**：上层只管"我要发什么"，下层只管"怎么搬"，互不关心实现。
- **灵活性好**：换一层不影响其他层（比如传输层从 HTTP over TCP 换成 HTTP over QUIC，应用层代码不用改）。
- **标准化**：每层有明确协议，不同厂商设备能互通。

#### 3. 数据在各层怎么封装的？

发送方**从上往下**每经过一层就加一个"头"（Header），接收方**从下往上**每经过一层就去掉一个头。

```
应用层数据:  [ Data ]
加TCP头:     [ TCP头 | Data ]
加IP头:      [ IP头 | TCP头 | Data ]      ← 这就是"包" Packet
加帧头帧尾:  [ 帧头 | IP头 | TCP头 | Data | 帧尾 ]   ← 这就是"帧" Frame
```

**各层数据单位名称（面试常问）：**

| 层 | 数据单位 | 英文 |
|------|---------|------|
| 应用层 | 报文 | Message/PDU |
| 传输层 | 报文段/数据报 | Segment（TCP）/ Datagram（UDP） |
| 网络层 | 数据包 | Packet |
| 数据链路层 | 帧 | Frame |
| 物理层 | 比特 | Bit |

> 💡 **速记口诀**：数（据链路层）帧、网（络层）包、传（输层）段、应（用层）报文。

### 二、TCP vs UDP ⭐⭐⭐⭐

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接性 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认、重传、流控、拥塞控制） | 不可靠（尽最大努力交付） |
| 传输形式 | 面向**字节流** | 面向**报文**（保留报文边界） |
| 速度 | 较慢 | 快 |
| 头部开销 | 20 字节起步 | 8 字节固定 |
| 通信方式 | 一对一 | 一对一/一对多/多对多（广播多播） |
| 应用场景 | 文件传输、HTTP、邮件 | DNS、视频直播、游戏、QUIC |

**UDP 用在哪：**
- DNS 查询（快，一条请求一条响应，丢了重查就行）
- 视频/语音直播（偶尔丢几帧不影响，强调实时性）
- DHCP、SNMP、游戏实时位置同步

**TCP 用在哪：** 要求不丢不重不乱的所有场景——HTTP/HTTPS、文件下载、邮件、SSH。

> ⚠️ **纠正一个常见误解**："UDP 一定比 TCP 快"不完全对。UDP 头部开销小、无握手，单看传输本身快；但 UDP 不管可靠性，**应用层要自己保证可靠就得自己实现重传/流控**（QUIC 就是这么干的，在 UDP 上实现了类 TCP 的可靠机制）。所以"快"是有代价的。

### 三、TCP 三次握手 ⭐⭐⭐⭐⭐（最高频）

#### 1. 过程图

```
客户端                                   服务端
CLOSED                                  LISTEN
  │                                        │
  │ ① SYN=1, seq=x                        │
  │ ────────────────────────────────────►  │
SYN_SENT                                  │
  │                                  SYN_RCVD
  │           ② SYN=1, ACK=1, seq=y, ack=x+1
  │ ◄────────────────────────────────────  │
ESTABLISHED                               │
  │                                        │
  │ ③ ACK=1, seq=x+1, ack=y+1              │
  │ ────────────────────────────────────►  │
ESTABLISHED                            ESTABLISHED
```

**三步：**
1. 客户端发 **SYN**（请求建立连接），进入 `SYN_SENT`。
2. 服务端收到后回 **SYN+ACK**（同意连接，并捎带确认），进入 `SYN_RCVD`。
3. 客户端再发 **ACK**（确认服务端的 SYN），双方都进入 `ESTABLISHED`。

#### 2. 为什么是三次？不是两次？不是四次？（必背）

> 🎯 **一句话答案：三次握手是为了确认双方的收发能力都正常，并防止历史重复连接的初始化。**

**逐条理解：**
- **最少需要三次才能确认双向通道**：
  - 第一次：服务端确认 → 客户端的发送、服务端的接收 OK。
  - 第二次：客户端确认 → 服务端的发送、客户端的接收 OK；此时**客户端已经知道双向都通**。
  - 第三次：服务端确认 → 服务端也确认了客户端的接收 OK（因为客户端能回应 ACK，说明它收到了第二次）。
  - 两次握手时，服务端发了 SYN+ACK 就以为连接建立了，但它**无法确认客户端的接收能力**。

- **防止历史重复连接（更核心的理由）**：
  假如客户端发了一个旧 SYN（网络延迟滞留），延迟到达服务端时，服务端若两次握手就直接建立连接，浪费资源等待一个早已失效的客户端。三次握手下，服务端发 SYN+ACK 后要等客户端第三次 ACK；客户端发现这个 SYN 是旧的（seq 对不上），就发 RST 中止，避免了无效连接。

- **同步双方初始序列号 ISN**：seq 是后续可靠传输的基础，第三次 ACK 确认了服务端的 seq 被客户端收到。

> ⚠️ 常见错误回答"三次握手是因为要同步序列号"——这只是原因之一。最根本是**确认双向收发能力 + 防止历史重复连接**。

#### 3. 为什么不是四次？

三次已经足够确认双向通道，第四次是冗余的（第三次 ACK 已经能确认客户端收到了服务端的 SYN）。所以没必要。

#### 4. SYN 泛洪攻击与防御

- **攻击原理**：攻击者伪造大量源 IP，发海量 SYN 包。服务端每收到一个 SYN 就分配资源、回 SYN+ACK，进入 `SYN_RCVD` 等第三次 ACK，但 ACK 永远不来 → **半连接队列耗尽**，正常用户无法连接。
- **防御**：
  - **SYN Cookie**：服务端收到 SYN 时**不立即分配资源**，而是把信息编码进 Seq 返回（加密生成 cookie），等第三次 ACK 带回 cookie 验证通过才真正建立连接。
  - 调大半连接队列、缩短 SYN+ACK 重传次数、防火墙过滤。

### 四、TCP 四次挥手 ⭐⭐⭐⭐⭐（最高频）

#### 1. 过程图

```
客户端（主动关闭方）                  服务端（被动关闭方）
ESTABLISHED                          ESTABLISHED
  │                                        │
  │ ① FIN=1, seq=u                         │
  │ ────────────────────────────────────►  │
FIN_WAIT_1                          CLOSE_WAIT
  │                                        │
  │           ② ACK=1, ack=u+1            │
  │ ◄────────────────────────────────────  │
FIN_WAIT_2                                │
  │      （服务端处理剩余数据，可发送）       │
  │                                        │
  │           ③ FIN=1, seq=w              │
  │ ◄────────────────────────────────────  │
TIME_WAIT                             LAST_ACK
  │                                        │
  │ ④ ACK=1, ack=w+1                      │
  │ ────────────────────────────────────►  │
  │ 2MSL                                   CLOSED
CLOSED
```

#### 2. 为什么是四次，不是三次？

**关键：TCP 是全双工的，关闭要双向各关一次。**

- ① 客户端发 FIN：表示"我没数据发了"。
- ② 服务端回 ACK：表示"知道了"。**但此时服务端可能还有数据没发完**，所以先回 ACK 进入 `CLOSE_WAIT`，继续发剩余数据。
- ③ 服务端数据发完后，发 FIN：表示"我也没数据了"。
- ④ 客户端回 ACK：表示"收到，我关了"。

> 💡 **三次握手能合并 SYN+ACK，四次挥手为什么不能合并？** 因为三次握手时服务端收到 SYN 立刻就能回 SYN+ACK（本来就要建连接）；而四次挥手时，服务端收到客户端的 FIN 后，**自己可能还有数据要发**，不能立刻跟着发 FIN，所以 ACK 和 FIN 必须分开（③②之间有个"处理剩余数据"的窗口）。若服务端刚好没数据要发，理论上 ACK+FIN 可合并，**实际中确实会合并成三次挥手**。

#### 3. TIME_WAIT 为什么存在 2MSL？（必考）

主动关闭方在最后回 ACK 后进入 `TIME_WAIT`，要等 **2 倍 MSL**（Maximum Segment Lifetime，报文最大生存时间）才真正 CLOSED。原因有二：

1. **保证最后一个 ACK 能到达对端**：如果④的 ACK 丢了，服务端会超时重发③的 FIN。客户端若已 CLOSED 就无法响应，服务端永远收不到 ACK 死循环。等 2MSL：一来一回正好够重传一次 FIN 到达 + ACK 返回。
2. **防止旧连接的报文干扰新连接**：让本次连接的所有报文在网络中自然消亡（每个报文最多存活 1 MSL，2MSL 后必然消失），避免被复用相同四元组的新连接错误接收。

> ⚠️ **谁会有 TIME_WAIT？** 主动关闭连接的一方。所以服务端主动 close 会堆积 TIME_WAIT，客户端主动 close 也会。

#### 4. TIME_WAIT 过多怎么办？

- **现象**：大量 TIME_WAIT 占用端口和内存，导致无法建立新连接。
- **处理**：
  - 调整 `net.ipv4.tcp_tw_reuse = 1`（允许复用 TIME_WAIT 连接做客户端，**安全，推荐**）。
  - `tcp_tw_recycle`（已废弃，NAT 环境下有坑，**别用**）。
  - 让服务端用长连接 / 缩短 `tcp_max_tw_buckets`。
  - **根本上**：用连接池复用连接，减少频繁建连断连。

#### 5. CLOSE_WAIT 过多说明什么？

`CLOSE_WAIT` 是被动方收到 FIN、回了 ACK 但**还没发自己的 FIN** 的状态。大量 CLOSE_WAIT 几乎都是**应用层 bug**——收到了对端的关闭信号但代码没调用 close()/没释放资源（比如异常没走到 finally 里的 close）。排查方向是查应用代码哪里漏关连接，而不是调内核参数。

### 五、TCP 可靠传输机制 ⭐⭐⭐⭐

TCP 怎么保证可靠？靠这几招组合：

| 机制 | 作用 |
|------|------|
| 序列号 + 确认应答 | 给每个字节编号，收到回 ACK，确认对方收到了 |
| 超时重传 | 发出去没收到 ACK，超时就重发 |
| 滑动窗口 | 允许一次发多个包不必逐个等 ACK，提升效率 |
| 流量控制 | 接收方通过窗口大小告诉发送方"我还能收多少"，防止压垮接收方 |
| 拥塞控制 | 感知网络拥塞，主动降速，防止压垮网络 |
| 校验和 | 检测数据是否损坏 |

#### 1. 滑动窗口

- **没有窗口时**：发一个包 → 等 ACK → 再发下一个（停等协议），效率极低。
- **有窗口后**：窗口大小 = "不用等 ACK 可以连续发的数据量"。窗口内可连续发送，收到 ACK 后窗口向前滑动。

#### 2. 流量控制（Flow Control）

- 接收方在 ACK 里带 **rwnd（接收窗口）** 告诉发送方"我缓冲区还剩多少"。
- 若 rwnd=0，发送方停止发送，并定期发**窗口探测**报文，等接收方腾出空间。

#### 3. 拥塞控制（Congestion Control）⭐⭐⭐

**流量控制是"接收方告诉发送方"，拥塞控制是"发送方自己感知网络"。** 四个阶段：

```
拥塞窗口 cwnd
    │
    │              /──── 拥塞避免（线性增长）
    │            /
    │          /          ╲ 快恢复（拥塞后线性）
    │        /              ╲
    │      /  慢开始          ╲
    │    /  （指数增长）        ╲
    │  /                         ╲─── 慢开始/拥塞避免...
    │/       ↑快重传触发
    └───────────────────────────────── 时间
```

- **慢开始**：cwnd 从 1 开始，**每收到一个 ACK 翻倍（指数增长）**，快速增长到阈值 ssthresh。
- **拥塞避免**：超过 ssthresh 后改为**线性增长**（每轮 +1），谨慎试探。
- **快重传**：收到 **3 个重复 ACK** 就立刻重传丢失的包，不必等超时。
- **快恢复**：快重传后，ssthresh 减半为 cwnd/2，cwnd 也设为 ssthresh，进入**线性增长**（不是从 1 重新慢开始）。

> ⚠️ **区分两种丢包处理**：
> - **超时（RTO）**：认为网络严重拥塞，ssthresh=cwnd/2，**cwnd 回到 1 重新慢开始**。
> - **3 个重复 ACK（快重传）**：认为只是个别丢包，网络没那么糟，**cwnd 减半走快恢复**，不回 1。

### 六、HTTP 基础 ⭐⭐⭐

#### 1. HTTP 请求/响应结构

```
请求：
  POST /api/login HTTP/1.1        ← 请求行：方法 URL 版本
  Host: www.example.com           ← 请求头
  Content-Type: application/json
  Content-Length: 36
  (空行)
  {"user":"tom","pwd":"123"}      ← 请求体

响应：
  HTTP/1.1 200 OK                  ← 状态行：版本 状态码 短语
  Content-Type: text/html          ← 响应头
  (空行)
  <html>...</html>                 ← 响应体
```

#### 2. 常见方法

| 方法 | 语义 | 幂等 | 安全 |
|------|------|------|------|
| GET | 获取资源 | 是 | 是 |
| POST | 创建资源 | 否 | 否 |
| PUT | 完整更新（替换） | 是 | 否 |
| DELETE | 删除 | 是 | 否 |
| PATCH | 部分更新 | 否 | 否 |

> ⚠️ **GET 和 POST 本质区别**（被问烂的题）：从 HTTP 协议层面，**两者都是 TCP 连接，没有本质区别**，只是语义不同。所谓的"GET 不能有 body、GET 长度有限、GET 不安全"更多是**浏览器/约定层面的限制**，不是 HTTP 协议强制。面试时答"语义不同 + 历史约定差异"即可，别钻牛角尖说"POST 发两次 TCP 包"那种网络段子。

#### 3. 状态码

| 类别 | 含义 | 典型 |
|------|------|------|
| 1xx | 信息 | 100 Continue |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301 永久、302 临时、304 Not Modified |
| 4xx | 客户端错误 | 400、401 未认证、403 没权限、404、405、429 限流 |
| 5xx | 服务端错误 | 500、502 网关错误、503 不可用、504 网关超时 |

- **301 vs 302**：301 永久重定向（浏览器会缓存），302 临时重定向（不缓存）。
- **401 vs 403**：401 是"你是谁？"（未认证/没登录），403 是"我知道你是谁，但你没权限"（已登录无权限）。

#### 4. Cookie 与 Session

- **Cookie**：存在**客户端**浏览器，每次请求自动带上，可被用户查看/篡改。
- **Session**：存在**服务端**，安全性高；通过 Cookie 里带一个 SessionId 关联。
- **Token（JWT）**：无状态，服务端不存，签名防篡改，适合分布式。

### 七、HTTP 各版本演进 ⭐⭐⭐⭐

| 版本 | 年份 | 关键特性 | 解决/未解决问题 |
|------|------|---------|----------------|
| HTTP/1.0 | 1996 | 每次请求都建新 TCP 连接 | — |
| HTTP/1.1 | 1997 | **长连接**（keep-alive）、管道化、Host 头 | 解决频繁建连；**仍队头阻塞** |
| HTTP/2 | 2015 | 二进制分帧、**多路复用**、头部压缩(HPACK)、服务端推送 | 解决 HTTP 层队头阻塞；**TCP 层仍队头阻塞** |
| HTTP/3 | 2022 | 基于 **QUIC(UDP)**、解决 TCP 层队头阻塞、连接迁移 | 彻底解决队头阻塞 |

#### 1. HTTP/1.1 的队头阻塞

- **TCP 层**：一个请求丢包，后续请求都得等重传（TCP 保证顺序）。
- **HTTP 层**：即使有管道化，响应也必须按请求顺序返回，前一个慢了后面全堵。

#### 2. HTTP/2 怎么解决 HTTP 层队头阻塞

- **二进制分帧**：把每个请求/响应拆成更小的"帧"（Frame），多个请求的帧**交错发送**在一个 TCP 连接上（多路复用），互不阻塞。
- **但 TCP 层队头阻塞还在**：一旦某个帧对应的 TCP 包丢了，整个连接上所有帧都得等这个包重传。这是 HTTP/3 要解决的。

#### 3. HTTP/3 / QUIC

- 基于 **UDP**，在 UDP 上自己实现可靠传输 + 拥塞控制 + 加密（TLS 1.3 内置）。
- **连接迁移**：手机从 Wi-Fi 切到 4G，连接不断（因为 QUIC 用 Connection ID 而非四元组标识连接）。

### 八、HTTPS ⭐⭐⭐⭐⭐

#### 1. HTTPS = HTTP + TLS/SSL

```
应用层：   HTTP
           │
加密层：   TLS/SSL   ← HTTPS 多的就是这层
           │
传输层：   TCP
```

**为什么要 HTTPS？** HTTP 三个问题：**明文传输（窃听）、无身份验证（伪装）、无完整性校验（篡改）**。HTTPS 用加密 + 证书 + MAC 全部解决。

#### 2. 对称加密 + 非对称加密混合

- **非对称加密**（RSA/ECC）：公钥加密、私钥解密。安全但慢，用于**协商对称密钥**。
- **对称加密**（AES）：加解密同一个密钥，快，用于**传输实际数据**。

> 💡 **核心思想**：用非对称加密的安全通道，把对称密钥安全地传给对方，之后用对称密钥加密数据。**非对称保证密钥交换安全，对称保证传输效率**。

#### 3. TLS 握手简化流程（TLS 1.2）

```
客户端                                      服务端
  │ ① ClientHello（支持的加密套件、随机数A）    │
  │ ──────────────────────────────────────►   │
  │                                          │
  │ ② ServerHello（选定套件、随机数B）         │
  │    Certificate（服务端证书+公钥）          │
  │ ┄─────────────────────────────────────◄   │
  │                                          │
  │ ③ 生成预主密钥，用服务端公钥加密发送        │
  │    ───────────────────────────────────►   │
  │                                          │
  │     双方用 随机数A + 随机数B + 预主密钥     │
  │     生成相同的"会话密钥"（对称密钥）        │
  │                                          │
  │ ④ 切换为加密通信，后续用会话密钥加密        │
  │ ◄──────────── 加密数据 ─────────────────►│
```

> ⚠️ **为什么不直接用非对称加密传所有数据？** 因为非对称加密计算极慢（比对称慢几百倍），传大文件扛不住。所以只用来传"会话密钥"这个小东西。

#### 4. 证书与 CA

- 服务端的公钥放在**数字证书**里，证书由 **CA（证书颁发机构）** 签名。
- 客户端用 CA 的公钥（操作系统/浏览器内置）验证证书签名 → 确认服务端身份、防中间人。
- 证书签名 = CA 用私钥对证书内容做摘要加密，客户端用 CA 公钥解密验证。

#### 5. TLS 1.3 的改进

- 握手从 **2-RTT 缩减到 1-RTT**（甚至支持 0-RTT 恢复）。
- 废弃不安全算法（如 RSA 密钥交换、SHA-1），强制前向安全。

### 九、从输入 URL 到页面显示（经典大题）⭐⭐⭐⭐⭐

这道题把整条网络链路串起来，是面试压轴题。完整流程：

```
1. URL 解析          →  解析出协议、域名、路径
2. DNS 域名解析       →  域名 → IP（查浏览器缓存→系统缓存→hosts→本地DNS→递归查询）
3. 建立 TCP 连接      →  三次握手
4. （HTTPS）TLS 握手  →  证书验证 + 协商密钥
5. 发送 HTTP 请求      →  构造请求报文发送
6. 服务器处理并响应    →  返回 HTML
7. 浏览器解析渲染      →  解析 HTML→DOM、CSS→CSSOM，合成渲染树，布局，绘制
8. 连接关闭            →  四次挥手（或长连接复用）
```

**DNS 解析顺序（高频追问）：** 浏览器 DNS 缓存 → 操作系统 DNS 缓存 → hosts 文件 → 本地域名服务器（递归） → 根域名服务器 → 顶级域名服务器 → 权威域名服务器，最终拿到 IP。

### 十、其他高频小题 ⭐⭐⭐

#### 1. TCP 粘包/拆包

- **本质**：TCP 是**字节流**，没有报文边界。应用层连续发两条消息"ABC""DEF"，TCP 可能合并成"ABCDEF"一次发，也可能拆成"AB""CDEF"——接收方分不清边界，这就是粘包/拆包。
- **为什么 UDP 没有？** UDP 面向报文，保留报文边界，一个包就是一个完整消息。
- **怎么解决？** 这是**应用层**的事，TCP 不背锅。常见方案：
  - 消息定长（每条固定长度）。
  - 用分隔符（如 `\r\n`，HTTP 就这么干）。
  - **长度字段**（消息头里带 body 长度，Netty 的 LengthFieldBasedFrameDecoder 就是这个思路）。

#### 2. 正向代理 vs 反向代理

| | 正向代理 | 反向代理 |
|---|---------|---------|
| 代理谁 | 代理**客户端** | 代理**服务端** |
| 谁知道 | 服务端不知道真实客户端 | 客户端不知道真实服务端 |
| 例子 | 翻墙、公司翻墙上网 | Nginx 负载均衡 |

> 详见 `06-中间件/04-Nginx.md`。

#### 3. CDN 原理

- **目的**：让用户从**离自己最近**的节点拿静态资源，降低延迟、减轻源站压力。
- **原理**：用户请求域名 → DNS 解析时返回**离用户最近的 CDN 边缘节点 IP**（基于 DNS 智能调度）→ 边缘节点有缓存就直接返回，没有就回源拉取并缓存。
- 通常配合 DNS 的 CNAME，把域名指向 CDN 厂商的调度域名。

#### 4. 跨域与 CORS

- **同源策略**：浏览器要求协议+域名+端口三者一致才能访问（保护用户）。
- **CORS**（跨域资源共享）：服务端响应头加 `Access-Control-Allow-Origin` 允许指定来源跨域。
- **预检请求**：复杂请求（如带自定义头、PUT/DELETE）会先发一个 **OPTIONS** 请求问服务端"我能不能跨域"，通过后再发真实请求。

#### 5. DNS 用的是 TCP 还是 UDP？

- **默认 UDP**（端口 53），查询报文小，追求速度。
- **区域传送（zone transfer，主从同步大量数据）用 TCP**，保证可靠性。
- 超长响应（512 字节以上）也回退到 TCP。

## 常见面试题

### Q1：详细说一下 TCP 三次握手，为什么不是两次？

（见核心概念三）三次握手是为了确认双方收发能力都正常，并防止历史重复连接。第一次客户端发 SYN，第二次服务端回 SYN+ACK（客户端此时确认双向通），第三次客户端回 ACK（服务端确认客户端接收正常）。两次握手时服务端无法确认客户端接收能力，且无法阻止历史失效 SYN 建立的无效连接。

### Q2：三次握手可以携带数据吗？

第一次、第二次**一般不带数据**（带数据有安全风险，攻击者可塞大量数据耗尽服务端资源）。**第三次 ACK 可以携带数据**——因为此时连接已建立，客户端已确认双向通道，发数据是安全的。这也是优化点：第三次握手顺带把 HTTP 请求发出去，省一个 RTT（TCP Fast Open 就是这个思路）。

### Q3：ISN（初始序列号）为什么不是固定的从 0/1 开始？

若固定，攻击者容易预测序列号伪造报文（TCP 序列号预测攻击）。所以 ISN 要**随机生成**，且随时间变化，增加伪造难度。同时 ISN 是后续字节编号的基准。

### Q4：SYN 和 FIN 能否占用一个序列号？

**不能。** SYN 和 FIN 各自消耗一个序列号（虽然它们不携带数据），因为它们都需要被确认。所以三次握手中 `ack=x+1`（SYN 占了 x，下个字节从 x+1 开始），四次挥手中 ACK 的 `ack=u+1`（FIN 占了 u）。而纯 ACK 不消耗序列号。

### Q5：已经建立了连接，客户端突然故障怎么办？

TCP 有**保活计时器（keepalive）**。服务端每次收到客户端数据就重置计时器；若超时（默认通常 2 小时）没收到任何数据，服务端开始**每隔一段时间发探测报文**，连续若干次探测都失败，就判定客户端故障，关闭连接释放资源。

### Q6：TCP 如何保证可靠传输？

序列号 + 确认应答 + 超时重传 + 滑动窗口 + 流量控制 + 拥塞控制 + 校验和 + 对失序报文重排。（见核心概念五）

### Q7：流量控制和拥塞控制的区别？

- **流量控制**：接收方→发送方，防止**接收方**被压垮（rwnd 接收窗口）。
- **拥塞控制**：发送方自主感知**网络**拥塞并降速（cwnd 拥塞窗口）。
- 实际发送窗口 = min(rwnd, cwnd)。

### Q8：HTTP/1.1、HTTP/2、HTTP/3 的区别？（高频）

- 1.1：长连接 + 管道化，但 HTTP 层队头阻塞。
- 2：二进制分帧 + 多路复用 + 头部压缩，解决 HTTP 层队头阻塞，但 TCP 层仍有。
- 3：基于 QUIC(UDP)，解决 TCP 层队头阻塞，支持连接迁移，握手更快。

### Q9：HTTPS 的握手过程？为什么用混合加密？

非对称加密协商出对称的会话密钥，之后用对称密钥加密数据。非对称保证密钥交换安全但慢，对称保证传输快。证书由 CA 签名，客户端用 CA 公钥验证防中间人。（见核心概念八）

### Q10：从浏览器输入 URL 到页面展示发生了什么？

DNS 解析 → TCP 三次握手 → （HTTPS）TLS 握手 → 发送 HTTP 请求 → 服务器处理响应 → 浏览器解析渲染（DOM/CSSOM/渲染树/布局/绘制）→ 连接关闭。（见核心概念九）

### Q11：TCP 粘包怎么解决？

TCP 是字节流无边界，粘包是应用层问题。用定长消息、分隔符、或消息头带长度字段（Netty LengthFieldBasedFrameDecoder）解决。（见核心概念十）

### Q12：HTTP 长连接和短连接的区别？

- 短连接：每次请求都新建 TCP 连接，请求完就关闭（HTTP/1.0 默认）。
- 长连接（keep-alive）：一个 TCP 连接可发多个请求，减少握手开销（HTTP/1.1 默认）。连接池就是复用长连接。

### Q13：Cookie、Session、Token 的区别？

Cookie 存客户端不安全；Session 存服务端安全但要占内存、不利于分布式扩展；Token(JWT) 无状态、服务端不存、适合分布式，靠签名防篡改。

### Q14：GET 和 POST 的区别？

语义上 GET 获取资源幂等安全，POST 创建资源非幂等。本质都是 TCP 连接，"GET 无 body、长度限制"是浏览器约定非协议强制。（见核心概念六）

## 资料勘误与重点提醒

> ⚠️ 网络资料/面经里流传的常见错误与必须澄清的点：

1. **"三次握手是为了同步序列号"是片面答案**。根本原因是确认双向收发能力 + 防止历史重复连接初始化。序列号同步只是附带结果。面试答全才显功力。

2. **"UDP 一定比 TCP 快"不完全对**。UDP 头小无握手，单看快；但可靠性需应用层自己实现（QUIC 就是在 UDP 上重造可靠传输）。"快"有代价。

3. **"GET 不能有 body"是浏览器约定，不是 HTTP 协议规定**。协议层面 GET 可带 body（虽不推荐）。别钻"POST 发两次包"的网络段子。

4. **四次挥手有时是三次**：当被动关闭方收到 FIN 时恰好没有数据要发了，可以把 ACK 和自己的 FIN 合并成一次发，变成三次挥手。这不是错误，是优化。

5. **`tcp_tw_recycle` 别开**：在 NAT 环境（多客户端共用一个公网 IP）下会因时间戳判断导致连接被丢弃，4.12 内核后已移除该参数。要复用 TIME_WAIT 用 `tcp_tw_reuse`（仅做客户端时安全）。

6. **TIME_WAIT 在主动关闭方**。很多人记反。谁主动 close，谁进入 TIME_WAIT 等 2MSL。

7. **CLOSE_WAIT 过多是应用 bug**，不是内核问题——是收到了对端 FIN 却没调 close()。查代码，别调参数。

8. **HTTP/2 没有彻底解决队头阻塞**：解决了 HTTP 层的，但 TCP 层丢包仍会让整个连接阻塞。HTTP/3(QUIC) 才根治。这是常被混淆的考点。

9. **DNS 默认走 UDP（53 端口）**，但区域传送和超长响应用 TCP。"DNS 只用 UDP"是错的。

10. **重点补充（资料常漏的高频点）**：
    - **快重传触发条件 = 收到 3 个重复 ACK**，不必等超时。
    - **超时 vs 3 重复 ACK 的处理不同**：超时回 cwnd=1 慢开始；重复 ACK 走快恢复（cwnd 减半不回 1）。
    - **TLS 1.3 把握手压到 1-RTT**，废弃了 RSA 密钥交换，强制前向安全。

> 📌 **本章总结**：网络面试就两条主线——**TCP 生命周期**（三次握手建连 → 可靠传输 → 四次挥手断连，重点 TIME_WAIT/SYN 攻击/拥塞控制）和 **HTTP 演进与安全**（1.0→1.1→2→3 各解决什么、HTTPS 混合加密 + TLS 握手）。把"输入 URL 到页面显示"作为串联全链路的压轴题练熟，网络部分基本稳了。
