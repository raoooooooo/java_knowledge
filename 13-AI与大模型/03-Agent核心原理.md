# Agent 核心原理

> Agent 是 2024-2025 年 AI 工程化的核心范式。本章讲清楚：Agent 是什么、上下文工程、长短记忆、任务规划、工具调用、自我反思，以及 Agent 的完整能力体系。

---

## 一、核心概念

### 1.1 什么是 Agent

- **定义**：以 LLM 为大脑、能**自主感知环境 -> 规划 -> 调用工具 -> 执行行动 -> 观察结果 -> 迭代**直到完成目标的系统。
- **经典公式**：`Agent = LLM（大脑）+ Planning（规划）+ Memory（记忆）+ Tools（工具）+ Action（行动）`。
- **一句话区分**：
  - **Chatbot**：一问一答，无状态，无行动。
  - **Workflow（工作流）**：固定流程编排，确定性，分支由规则决定。
  - **Agent**：流程由 LLM **自主决定**，非确定性，能动态选择工具和路径。

> ⚠️ 面试金句：Agent 与 Workflow 的本质区别是「**控制权交给 LLM**」。Workflow 是开发者写死流程，Agent 是 LLM 自己决定下一步干什么。二者并非对立，生产中常混合：外层 Workflow 控制骨架，节点内用 Agent 处理不确定子任务。

### 1.2 Agent 运行循环（The Agent Loop）

所有 Agent 框架的内核都是同一个循环：

```
while 未完成 且 未超轮数:
    1. 组装上下文（系统提示 + 记忆 + 历史 + 工具说明 + 当前状态）
    2. LLM 推理，输出：思考 / 调用哪个工具 / 最终答案
    3. 若调用工具 -> 执行工具 -> 把结果作为 Observation 放回上下文 -> 回到 1
    4. 若给出最终答案 -> 结束
```

这就是 ReAct 范式的工程化。**Harness**（见「07-ClaudeCode与Harness原理」）就是负责运行这个循环、管理上下文与工具调度的运行时。

## 二、上下文工程（Context Engineering）

> 这是比 Prompt Engineering 更高一层的概念，也是 2025 年的新共识：**Agent 的能力上限，很大程度取决于上下文工程的质量，而非模型本身。**

### 2.1 什么是上下文工程

- **Prompt Engineering**：优化「单次提问」。
- **Context Engineering**：优化「整个 Agent 运行过程中，每一轮塞给 LLM 的完整上下文」--包括系统提示、记忆、历史、工具结果、检索内容、当前任务状态。

### 2.2 上下文工程的核心动作

| 动作 | 含义 | 目的 |
|------|------|------|
| **写入（Write）** | 把重要信息写进上下文/记忆 | 后续可用 |
| **选择（Select）** | 每轮决定把哪些信息放进上下文 | 防止上下文爆炸 |
| **压缩（Compress）** | 对冗长内容做摘要/抽取 | 省 token、提速度 |
| **隔离（Isolate）** | 子任务用独立子上下文 | 防止噪声污染主上下文 |
| **遗忘/淘汰（Forget）** | 主动丢弃过时/无用信息 | 聚焦当前任务 |

### 2.3 上下文窗口管理策略

- **滑动窗口**：只保留最近 N 轮对话。
- **自动压缩（Auto-Compact）**：当上下文接近窗口上限时，自动把旧内容总结成摘要，保留要点，腾出空间。Claude Code 的 `/compact` 即此机制。
- **关键信息锚定**：系统提示、任务目标等关键内容始终保留在上下文头部，防止被压缩丢失。
- **子 Agent 隔离**：把大任务拆给子 Agent，子 Agent 用独立上下文处理，只返回结论--避免把中间海量细节灌回主上下文（污染+超限）。

## 三、记忆系统（长短期记忆）★

> 用户重点知识点。记忆是 Agent「像人一样」的关键。

### 3.1 短期记忆（Short-term / Working Memory）

- **载体**：上下文窗口本身（当前对话历史）。
- **特点**：快、即时，但**容量有限、会随压缩/截断丢失**。
- **类比**：人的「工作记忆」，正在思考的事。

### 3.2 长期记忆（Long-term Memory）

- **载体**：上下文窗口之外的持久化存储。
- **常见实现**：
  - **向量记忆库**：把过往对话/事实向量化，按语义检索相关记忆注入（本质是 RAG 应用于「记忆」）。
  - **知识图谱**：结构化存储实体关系，适合精确回忆关联信息。
  - **文件系统**：把笔记/结论写到文件（如 Claude Code 的 `memory/` 目录），需要时读取。
  - **键值数据库**：存用户偏好、事实等结构化记忆。
- **类比**：人的「长期记忆」，需要「回忆」才能用。

### 3.3 记忆管理三问（写什么、怎么找、何时忘）

- **写入（Encoding）**：什么值得记？通常存：用户偏好、关键决策、事实、失败教训。不是所有对话都存。
- **检索（Retrieval）**：按当前任务语义检索相关记忆，注入上下文。检索不准 = 记忆用不上。
- **遗忘/反思（Forgetting/Reflection）**：
  - 主动淘汰过时信息（如时效性数据）。
  - **反思机制**：定期对记忆做总结/合并/泛化（如 Generative Agents 的 reflection：把「我昨天吃了面、前天吃了面」抽象成「我最近常吃面」），压缩冗余、提炼规律。

### 3.4 记忆类型分层（参考认知科学）

| 类型 | 内容 | 生命周期 |
|------|------|---------|
| 工作记忆 | 当前任务上下文 | 单次会话 |
| 情景记忆 | 具体事件/对话 | 可持久、按场景检索 |
| 语义记忆 | 事实/知识 | 长期 |
| 程序记忆 | 技能/操作经验（如 Skill） | 长期，可复用 |

> 对应到工程：工作记忆=上下文窗口；情景/语义记忆=向量库/图数据库；程序记忆=Skill/工具库。

## 四、任务规划（Planning）

- **任务分解（Decomposition）**：把复杂目标拆成可执行子任务。如 Plan-and-Execute、ReWOO。
- **规划策略**：
  - **一次性规划**（Plan-then-Execute）：先列全部计划再执行。高效但僵化，遇意外难调整。
  - **滚动规划**（Replan）：执行几步后根据结果重新规划。灵活但调用多。
  - **无显式规划**（ReAct 式）：每步现想现做，灵活但易跑偏。
- **子任务依赖**：树/图结构管理依赖关系（如 todo list），完成一个解锁下游。

## 五、工具调用（Tool Use / Function Calling）

### 5.1 原理

1. 开发者把工具的**名称、描述、参数 schema**（JSON Schema）以特定格式放进上下文。
2. LLM 推理后输出一个**结构化的工具调用请求**（函数名 + 参数 JSON）。
3. 框架拦截该请求，执行真实工具，把返回值作为 Observation 喂回 LLM。
4. LLM 基于结果继续推理。

### 5.2 Function Calling vs MCP

- **Function Calling**：模型厂商提供的「输出结构化函数调用」能力，是**模型层**特性。
- **MCP**（见「06-协议生态」）：把工具/数据源**标准化**的协议，是**生态层**标准。MCP Server 暴露的工具，最终也通过 Function Calling 让模型调用。二者是「协议」与「调用」的关系，不冲突。

### 5.3 工具设计的工程要点

- **描述要清晰**：模型靠描述选工具，描述模糊就会选错或不用。
- **参数要简单**：复杂参数模型容易填错，能默认就默认。
- **错误要可读**：工具失败返回可读错误，模型才能自我修正重试。
- **工具不宜过多**：工具太多模型会选错（注意力稀释），应按场景分组/按需加载（Skill 机制）。

## 六、自我反思与自我修正（Self-Reflection）★

- **思想**：Agent 执行后不直接接受结果，而是**评估自己的输出**，发现问题时回头修正。源自 Reflexion 范式。
- **典型机制**：
  - **Critic / Evaluator**：用一个 LLM（或同一 LLM 换角色）评审 Actor 的输出。
  - **Verifier / Guardrail**：用规则或外部校验（如代码能否编译/测试是否通过）做客观验证。
  - **Self-Correction Loop**：评审不通过则把「问题+评审意见」放回上下文，让模型修正，循环到达标或上限。
- **意义**：这是 Agent 区别于「一次性生成」的关键--能从失败中迭代。代码 Agent 改 bug 到测试通过、写作 Agent 反复打磨，都靠它。

## 七、Agent 能力体系（全景）★

> 用户明确要求的四层能力分类。这是评估/设计一个 Agent 产品的框架。

### 7.1 基础能力（让 Agent「能用」）

| 能力 | 说明 |
|------|------|
| **多轮对话** | 维持上下文连贯的多轮交互，记住上文 |
| **知识库问答** | 基于 RAG 回答私有/领域知识，可溯源 |
| **内容生成** | 文本/代码/结构化数据生成 |

### 7.2 核心能力（让 Agent「像 Agent」）

| 能力 | 说明 |
|------|------|
| **任务规划** | 目标分解、子任务编排、动态重规划 |
| **工具调用** | 选择并调用工具，组合多工具完成任务 |
| **自我反思** | 评估自身输出，发现错误并修正迭代 |
| **长期记忆** | 跨会话记住用户/事实/经验，按需检索 |

### 7.3 工程与部署能力（让 Agent「能上线」）

| 能力 | 说明 |
|------|------|
| **可视化编排** | 拖拽式编排 Agent/工作流（Dify/Coze/LangFlow） |
| **监控与日志** | Trace、Token 成本、延迟、错误率观测（见第8章） |
| **API 接口** | 对外暴露 REST/Streaming API，供业务集成 |
| **多模型支持** | 模型路由、可切换、降级、成本优化 |

### 7.4 安全与合规能力（让 Agent「能合规」）

| 能力 | 说明 |
|------|------|
| **内容审核** | 输入/输出内容审核（涉政/暴恐/违规），拦截与改写 |
| **权限管理** | RBAC/ABAC，控制谁能用哪个 Agent、调哪个工具 |
| **数据隐私** | PII 脱敏、数据不出域、私有化部署、审计日志 |

> 面试可按这四层展开讲一个 Agent 产品该具备什么，从「能用 -> 像 Agent -> 能上线 -> 能合规」层层递进。

## 八、常见面试题

1. **Agent 和 Chatbot、Workflow 的区别？**
   Chatbot 无状态无行动；Workflow 流程写死确定；Agent 控制权交给 LLM 自主决策、能调工具迭代。生产常混合 Workflow+Agent。

2. **Agent 的运行循环是怎样的？**
   组装上下文 -> LLM 推理 -> 调用工具 -> 观察 -> 回到组装上下文，直到给出最终答案或达上限。

3. **Agent 的短期记忆和长期记忆分别怎么实现？**
   短期=上下文窗口内的对话历史；长期=外部存储（向量库/知识图谱/文件/KV），按需检索注入。检索质量决定长期记忆有没有用。

4. **上下文工程和提示工程区别？为什么重要？**
   提示工程优化单次提问；上下文工程优化整个运行周期每轮的完整上下文（含记忆、工具结果、状态）。Agent 能力上限很大程度取决于上下文工程而非模型本身。

5. **Agent 上下文快满了怎么办？**
   自动压缩旧内容为摘要、滑动窗口截断、关键信息锚定保留、用子 Agent 隔离子任务只回传结论、压缩工具返回结果。

6. **自我反思怎么实现？有什么用？**
   Actor 输出后用 Critic/Verifier 评审，不通过则带评审意见让模型修正循环。作用是让 Agent 能从失败迭代而非一次性生成。

7. **工具太多导致模型选错工具怎么办？**
   按场景分组、按需加载（Skill）、描述写清、参数简化、用路由 Agent 先分流。
