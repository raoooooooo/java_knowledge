# Prometheus 指标详解

## 核心概念

Prometheus 有 **4 种核心指标类型**，掌握了这 4 种，基本就能应对 90% 的监控场景。

---

## 一、Counter（计数器）

### 是什么？
**只增不减的计数器**。就像汽车的里程表，只会往上走，不会往下掉。

### 通俗理解
- 像你手机的「屏幕使用时间」——只用不重置，只会越变越大
- 像超市的客流量统计——今天进来多少人，只加不减
- 像网站的总访问量——累计多少人来过

### 典型应用场景
- 接口请求总次数
- 异常发生总次数
- 消息队列消息消费总数
- CPU累计使用时间

### 怎么看？
**不要直接看 Counter 的绝对值，要看它的「增长率」。**

例子：
```
# 好的做法：看5分钟内的QPS
rate(http_requests_total[5m])  

# 坏的做法：直接看总量（毫无意义）
http_requests_total  
```

### 面试题：Counter 重启归零了怎么办？
Prometheus 的 `rate()` 函数会自动处理这种情况，它会检测到计数器重置并正确计算增长率。

---

## 二、Gauge（仪表盘）

### 是什么？
**可增可减的瞬时值**。就像汽车的时速表，反映的是「当前这一刻」的状态。

### 通俗理解
- 像温度计——现在多少度，随时变
- 像油箱油表——现在还剩多少油
- 像股票价格——当下的价格，涨涨跌跌

### 典型应用场景
- 当前内存使用率
- 当前活跃线程数
- 队列里的待处理消息数
- 磁盘剩余空间
- 当前在线用户数

### 怎么看？
**直接看 Gauge 的值就行，它就是当前状态。**

例子：
```
# 直接看当前内存使用率
jvm_memory_used_bytes{area="heap"}  

# 看最大值/最小值（一段时间内）
max_over_time(jvm_memory_used_bytes[1h])  
```

### Counter vs Gauge 一句话总结
| 对比项 | Counter | Gauge |
|--------|---------|-------|
| 趋势 | 只增不减 | 可增可减 |
| 含义 | 累计总量 | 当前状态 |
| 常用函数 | rate(), increase() | avg_over_time(), max_over_time() |
| 例子 | 总请求数 | 当前内存使用率 |

---

## 三、Histogram（直方图）

### 是什么？
**统计数据的分布情况**。这是最容易搞混的一个，也是最强大的一个。

### 通俗理解
想象你是老师，统计全班考试成绩：
- 你不是只算平均分（那太粗糙了）
- 你想知道：多少人考了60分以下，多少人60-80，多少人80-90，多少人90+
- 这就是 Histogram 做的事情——**告诉你数据在各个区间的分布**

### 典型应用场景
- 接口响应时间（P50/P95/P99）
- SQL执行耗时
- 请求体大小分布

### 核心原理
Histogram 会预先定义一些「桶」（bucket），然后统计每个桶里落了多少数据。

比如接口响应时间的桶可能是：
```
0.1s, 0.2s, 0.5s, 1s, 2s, 5s, +∞
```

Histogram 自动记录3个值：
1. **`_sum`**：所有观测值的总和
2. **`_count`**：观测的总次数
3. **`_bucket`**：每个桶的累计次数（注意是「累计」！）

### 怎么用？——计算百分位数（P95/P99）

这是 Histogram 最常用的功能，也是面试必问。

**例子：想知道 95% 的请求都在多少毫秒内完成？**

```promql
# P95 响应时间
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# P50（中位数）响应时间
histogram_quantile(0.50, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# P99 响应时间
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
```

### 怎么看平均值？
用 `_sum / _count` 就得到平均值：
```promql
rate(http_request_duration_seconds_sum[5m]) 
/ 
rate(http_request_duration_seconds_count[5m])
```

### 为什么不用平均？——「平均」会骗人！

想象一下：
- 100个请求，99个都在100ms内完成
- 1个请求用了10秒

**平均响应时间 = (99×0.1 + 1×10) / 100 = 0.199s = 199ms**

看起来还不错？但实际上有 **1% 的用户等了整整10秒！**

用 Histogram 看 P99，你就能发现这 1% 的糟糕体验。

### 桶（Bucket）怎么选？
- 桶不是越多越好，也不是越少越好
- 重点关注你关心的区间：比如大部分接口在1s内，那桶就集中在0-1s区间多放几个
- Prometheus 默认有一组桶，不够再加

## 四、Summary（摘要）

### 是什么？
**客户端直接计算百分位数**。和 Histogram 类似，但计算发生在被监控端，不是 Prometheus 服务端。

### 简单对比
| 特性 | Histogram | Summary |
|------|-----------|---------|
| 计算位置 | Prometheus服务端 | 被监控客户端 |
| 精度 | 近似（依赖桶） | 精确 |
| 聚合能力 | 可以跨实例聚合 | 不能跨实例聚合 |
| 性能 | 服务端计算压力大 | 客户端计算压力大 |

**实际工作中，Histogram 用得比 Summary 多得多，因为跨实例聚合太重要了。**

## 常见面试题

### 1. Counter 和 Gauge 的区别是什么？
**答案：**
- Counter 是只增不减的计数器，适合统计累计总量，看的是增长率
- Gauge 是可增可减的瞬时值，适合表示当前状态，直接看值本身

### 2. 为什么需要 Histogram？平均值不够吗？
**答案：**
- 平均值会掩盖极端情况（大部分很快，少数极慢）
- Histogram 能看到数据的真实分布
- 可以计算 P50/P95/P99 等百分位数，了解真实的用户体验

### 3. Histogram 的 bucket 是累计的吗？
**答案：**
是的！比如桶 `le=1s` 包含了所有响应时间 ≤ 1秒的请求，也包含了 ≤ 0.5s、0.2s 等更小桶的请求。

### 4. P95 是什么意思？
**答案：**
95% 的请求都在这个时间以内完成，只有 5% 的请求比这个慢。

### 5. Histogram 和 Summary 选哪个？
**答案：**
- 需要跨实例聚合 → 选 Histogram
- 追求精确的百分位数，不需要跨实例 → 选 Summary
- **90% 场景选 Histogram**

## 实战小技巧

### 1. 看接口QPS（用Counter）
```promql
# 5分钟内的平均QPS
rate(http_requests_total[5m])
```

### 2. 看内存使用趋势（用Gauge）
```promql
# 1小时内的最大内存使用
max_over_time(jvm_memory_used_bytes[1h])
```

### 3. 看慢接口比例（用Histogram）
```promql
# 响应时间超过1秒的请求占比
sum(rate(http_request_duration_seconds_bucket{le="1.0"}[5m])) 
/ 
sum(rate(http_request_duration_seconds_count[5m]))
```

## 一句话记忆法

| 指标类型 | 一句话记住 | 口诀 |
|---------|-----------|------|
| Counter | 只增不减看增速 | **计数看增长** |
| Gauge | 可增可减看当前 | **仪表看此刻** |
| Histogram | 统计分布看P95 | **直方看分布** |
| Summary | 客户端算百分位 | **摘要少使用** |

---

**总结：** 监控不是为了好看，而是为了发现问题。选对指标类型，你就能更快定位问题根源。
