# 24 - 性能与成本优化

> LLM 应用最大的痛点：慢且贵。本章讲 Token 经济学、Prompt 压缩、缓存、推理加速（vLLM/量化）。这是降本增效的硬功夫，面试「怎么降 LLM 成本/提速」高频。第五篇收尾。

---

## 一、Token 经济学与成本模型 ★

### 1.1 成本构成

```
总成本 = Σ (输入token × 输入单价 + 输出token × 输出单价)
```

- **输入和输出都算钱**，输出通常贵 3~5 倍。
- 多轮对话历史也是输入 token，轮次越多越贵（上下文压缩的动因）。
- RAG 检索片段、工具结果也是输入 token。
- 多模态按分辨率算 token。

### 1.2 哪里烧钱

| 场景 | 烧钱点 |
|------|--------|
| 多轮对话 | 历史越堆越多，每轮都重发 |
| RAG | 检索片段多，塞进 prompt |
| 长 Prompt | Few-shot 太多、模板太长 |
| Agent 循环 | 多步每步都调 LLM |
| 大模型干小活 | 简单任务用旗舰模型 |

### 1.3 成本估算

```
单次成本 ≈ (输入token × 输入单价 + 输出token × 输出单价)
月成本 ≈ 日均请求 × 30 × 单次成本
```

- 建监控按用户/Agent/时段统计 token 费用（20 章），发现异常。

> 💡 **面试金句**：成本 = 输入 token×输入单价 + 输出 token×输出单价（输出贵 3~5 倍）。烧钱点：多轮历史累积、RAG 片段、长 Prompt、Agent 循环、大模型干小活。降本三板斧：压缩上下文（减输入）、用小模型（降单价）、缓存（复用结果）。

## 二、Prompt 压缩与上下文裁剪 ★

### 2.1 减少输入 token

| 手段 | 说明 |
|------|------|
| **Prompt 压缩** | LLMLingua 等删低相关 token，压到 1/10（06 章） |
| **历史压缩** | 自动压缩旧对话成摘要（10 章） |
| **滑动窗口** | 只保留最近 N 轮 |
| **工具结果裁剪** | 只留关键字段，别全量回灌 |
| **RAG 片段控制** | Rerank 后取 Top-5，别塞 50 段 |
| **Few-shot 精简** | 2~5 个有代表性的，别堆一堆 |

### 2.2 减少输出 token

- 明确要求简洁（「一句话回答」「不超过 100 字」）。
- 用结构化输出（JSON）比自由文本省。
- 设 `max_tokens` 上限防跑飞。

### 2.3 结构化省 token

- JSON 输出比散文省（字段名固定，不啰嗦）。
- 枚举值比自由文本省（`status: "paid"` vs 一段描述）。

## 三、缓存与语义缓存 ★

### 3.1 精确缓存

- 相同请求复用结果。适合固定问答 FAQ、元数据查询。
- Redis 存 hash(query) -> result。

### 3.2 语义缓存 ★

- 相似请求（语义相近）复用结果。
- 用 Embedding 判断 Query 相似度，超阈值命中缓存。
- 命中省一次 LLM 调用（省钱+提速）。

```java
// 语义缓存
float[] qVec = embeddingModel.embed(query);
CacheEntry hit = cache.findSimilar(qVec, 0.95);  // 相似度阈值
if (hit != null) return hit.result;   // 命中
String result = llm.call(query);
cache.store(qVec, result);
```

### 3.3 Prompt Caching（模型层）

- 部分模型支持 prompt caching：相同前缀的 prompt 缓存，重复前缀算便宜。
- 适合：固定系统 prompt + 变化用户输入的场景。

### 3.4 缓存坑

- **相似度阈值**：设太低返回不相关、设太高命中率低。调好+抽检。
- **失效**：知识/数据更新要清缓存，否则返回旧答案。
- **敏感数据**：别缓存含 PII 的结果。
- **个性化**：用户特定的问题别缓存（每人答案不同）。

## 四、批处理 API 与并发

### 4.1 批处理 API

- 部分模型支持 batch API：异步批量处理，单价低很多（半价级别）。
- 适合非实时场景（离线数据处理、评测、批量标注）。
- 不适合实时对话（异步要等）。

### 4.2 流式与并发

- **流式（SSE）**：首 token 快，改善体感（02 章）。
- **并发请求**：多个独立请求可并发调（如多源检索、多 Worker）。
- 注意模型 API 的并发限制（QPM/TPM），超了 429，要客户端限流。

### 4.3 请求合并

- 多个相似请求合并成一次批量（如批量分类）。
- 减少调用次数省成本。

## 五、推理加速（私有化部署）★ 进阶

> 私有化部署开源模型时，不做加速会慢得没法用。这是自部署的必修课。

### 5.1 vLLM ★

- 开源推理引擎，**PagedAttention** 技术大幅提升吞吐。
- 连续批处理（continuous batching）：动态拼批，GPU 利用率高。
- 兼容 OpenAI API，替换方便。
- 是私有化部署首选推理加速方案。

### 5.2 量化（Quantization）

- 把模型权重从 FP16 降到 INT8/INT4，减显存、提速度，精度略降。
- GPTQ/AWQ/GGUF 等量化方案。
- 适合显存有限场景，牺牲少量精度换成本。

### 5.3 蒸馏

- 用大模型蒸馏出小模型，小模型在特定任务接近大模型效果但快得多。
- 适合固定任务场景（如特定领域问答）。

### 5.4 其他加速

- **TensorRT-LLM**（NVIDIA）：极致优化，部署稍复杂。
- **TGI**（HuggingFace Text Generation Inference）。
- **KV-cache 复用**：相同前缀复用 KV-cache 提速。

### 5.5 选型

```
私有化首选        -> vLLM（吞吐高、易用、兼容 OpenAI）
显存有限          -> 量化（INT8/INT4）
固定任务极致优化   -> 蒸馏小模型
NVIDIA 极致       -> TensorRT-LLM
```

> 💡 **面试金句**：私有化部署必做推理加速，首选 vLLM（PagedAttention+连续批处理，吞吐高、兼容 OpenAI API）。显存有限用量化（INT8/INT4 减显存提速略降精度），固定任务用蒸馏小模型。

## 六、性能优化总结

| 维度 | 手段 |
|------|------|
| **延迟** | 流式（首 token 快）、小模型、缓存命中、私有化加速（vLLM） |
| **吞吐** | 连续批处理（vLLM）、并发、批处理 API |
| **成本** | 压缩上下文、小模型、缓存、批处理 API、量化蒸馏 |
| **可用** | 降级、多模型、限流 |

## 七、生产踩坑

1. **不监控 token 成本**：烧钱不知道。按用户/Agent/时段监控告警（20 章）。
2. **大模型干小活**：简单分类用旗舰模型浪费。小模型+级联（22 章）。
3. **多轮历史不压**：越堆越贵。自动压缩/滑动窗口。
4. **工具结果全量回灌**：大 JSON 费 token。裁剪关键字段。
5. **语义缓存阈值错**：返回不相关结果。调阈值+抽检+知识更新清缓存。
6. **私有化不加速**：自部署开源模型慢。用 vLLM。
7. **量化精度损失**：INT4 可能明显掉效果。评估任务精度要求选量化级别。
8. **流式代理问题**：Nginx buffering 打断流。关 buffering+超时调大（02 章）。

## 八、常见面试题

1. **LLM 成本怎么算？怎么降？**
   成本=输入token×输入单价+输出token×输出单价（输出贵3~5倍）。降本三板斧：压缩上下文（减输入）、用小模型（降单价，级联让小先试）、缓存（精确+语义复用）。配合批处理 API（离线半价）、Prompt 压缩。

2. **语义缓存是什么？有什么坑？**
   相似请求用 Embedding 判断相似度，超阈值复用结果，省一次 LLM 调用。坑：相似度阈值设错返回不相关、知识更新要清缓存、敏感数据别缓存、个性化别缓存。

3. **Prompt 怎么压缩省 token？**
   LLMLingua 删低相关 token 压到 1/10、历史压缩成摘要、滑动窗口只留最近 N 轮、工具结果裁剪关键字段、RAG Rerank 后取 Top-5、Few-shot 精简 2~5 个、结构化输出比散文省。

4. **多轮对话怎么省成本？**
   历史越堆越贵。自动压缩旧对话成摘要（10 章）、滑动窗口只留最近 N 轮、关键信息锚定、子 Agent 隔离只回传结论、必要时用长上下文模型一次性带历史（权衡 Lost in the Middle）。

5. **私有化部署模型慢怎么办？**
   推理加速：首选 vLLM（PagedAttention+连续批处理，吞吐高、兼容 OpenAI API）。显存有限用量化（INT8/INT4），固定任务用蒸馏小模型。NVIDIA 极致用 TensorRT-LLM。

6. **vLLM 为什么快？**
   PagedAttention（类似操作系统的分页管理 KV-cache，减少显存碎片）+ 连续批处理（动态拼批，GPU 利用率高）。吞吐比原生 Transformers 高数倍，且兼容 OpenAI API 替换方便。

7. **量化有什么代价？**
   INT8/INT4 减显存提速度，但精度略降。INT4 可能明显掉效果。按任务精度要求选量化级别，关键任务评估退化可接受度。

8. **怎么改善 LLM 响应延迟？**
   流式（SSE 首 token 快改善体感）、用小模型/级联、缓存命中秒回、私有化用 vLLM 加速、并发独立请求、减少上下文（输入短推理快）。监控 TTFT 和总时延。

## 九、资料勘误与重点提醒

1. **「大模型一定更好用」是成本误区**：资料常默认用最强模型。生产简单任务用小模型（级联让小先试），能省大部分成本，效果未必差。
2. **「语义缓存随便用」有坑**：相似度阈值错返回不相关、缓存不失效返回旧答案、敏感数据不该缓存、个性化别缓存。资料常不讲这些。
3. **「私有化部署直接跑」低效**：原生 Transformers 推理慢。资料少讲推理加速，实际必用 vLLM/TGI，否则慢得没法用。
4. **「量化无损」不严谨**：资料常说量化「几乎无损」。实际 INT4 可能有明显精度下降，按任务评估，关键任务慎用 INT4。
5. **多模态计费少提**：资料讲成本常只算文本 token。图片/视频按分辨率算 token，多模态成本易超。
6. **流式不省钱少强调**：资料讲流式常不提「流式仍按总 token 计费，不省钱只改体感」。流式是体验优化不是成本优化。
