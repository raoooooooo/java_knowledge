## 面试问题与答题思路

### 一、MCP 与 AI Agent 相关

#### 1. MCP 是什么？在 AI 系统里承担什么角色？底层用哪个协议？有哪几种模式？

**参考答案：**

MCP 全称 **Model Context Protocol**，是 Anthropic 推出的开放协议。定位是 **AI 应用与外部工具/数据源之间的标准化中间层**。

- **解决的痛点**：以前每个 AI 应用要连数据库、文件系统、第三方 API，都得自己写胶水代码，厂商锁定严重。MCP 统一了接口规范，让 AI Agent 可以"插拔式"挂载各种工具。
- **底层协议**：走 **JSON-RPC 2.0**（请求-响应式的远程过程调用协议）。
- **传输模式（2 种，不是 3 种 ⚠️）**：
  - **stdio 模式**：AI 进程与工具进程通过标准输入输出通信，适合本地 CLI 工具和本地 Server。
  - **Streamable HTTP 模式**：基于 HTTP + SSE 的长连接通信，适合远程/网络化场景。Client 发 POST 请求，Server 用 SSE 流回响应。

> ⚠️ **资料勘误**：原文提到"Memory 模式"是第三种模式，这是不对的。MCP 规范中**只有 stdio 和 Streamable HTTP 两种传输模式**。Memory（记忆管理）是 MCP 可以承载的一种能力/应用场景，不是传输模式。MCP 定义了三类核心能力：**Tools（工具调用）、Resources（资源访问）、Prompts（提示模板）**，不包含 Memory 模式。

---

#### 2. 有用过 Skills 吗？讲一下？

**参考答案：**

Skills 是构建在 MCP 之上的**能力抽象层**。如果说 MCP 定义了"怎么连（通信协议）"，Skills 定义的是"能做什么（能力模块化）"。

- 以 GitHub Skill 为例，它封装了"创建仓库、提交代码、创建 PR"等一组相关操作。AI Agent 调用 Skill 时，不需要自己组合多个底层 MCP 调用，直接发一条指令即可。
- **分层理解**：MCP 是对外接口的标准化（协议层），Skills 是对内能力的模块化（能力层）。
- 在 Claude Code 中，Skill 是一种渐进式披露能力的机制——按需加载、按场景激活，避免上下文被所有工具定义撑爆。

---

#### 3. MCP 里的 tool 和普通 function calling 有什么区别？

**参考答案：**

很多人容易混淆，核心区别有三点：

| 维度 | 普通 Function Calling | MCP Tool |
|------|----------------------|----------|
| **执行主体** | LLM 只负责"决定调哪个、生成参数"，**执行在调用方（你的服务端）** | Tool 在 **MCP Server 端**自动执行，Client 拿到的是执行结果 |
| **发现机制** | 静态注册，你事先把函数定义写死传给模型 | **动态发现**，Server 启动时告诉 Client 它提供哪些 tool，Client 可以运行时查询 |
| **协议标准化** | 各家厂商各搞一套（OpenAI / Anthropic / Google 格式不统一） | **统一协议**，任何 MCP Client 都能连任何 MCP Server |
| **能力范围** | 只有工具调用 | 工具 + 资源（Resources）+ 提示（Prompts）三位一体 |

### 二、Linux 基础

#### 4. 进程、线程和协程是什么？有什么区别？

**参考答案：**

- **进程（Process）**：**资源分配的最小单位**。拥有独立的内存空间、文件描述符表、页表、PID。进程间相互隔离，一个进程挂了不影响其他进程。
- **线程（Thread）**：**CPU 调度的最小单位**。属于同一个进程的线程共享进程的内存空间（堆、全局变量），但每个线程有自己的栈和寄存器。上下文切换开销比进程小。
- **协程（Coroutine）**：**用户态的轻量级线程**。由程序（运行时/语言库）自己调度，不经过操作系统内核。切换开销极小，一个线程里可以跑上万个协程。

**对比表：**

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 资源分配 | 是，独立地址空间 | 共享进程地址空间 | 共享线程地址空间 |
| 调度者 | 操作系统 | 操作系统 | 用户态（程序/ runtime） |
| 上下文切换开销 | 大（页表/文件表/TLB刷新） | 中（栈/寄存器） | 极小（几个寄存器） |
| 数量级 | 几十~几百 | 几千 | 几万~几十万 |
| 数据共享 | 困难（IPC） | 容易（共享内存，需加锁） | 最简单（同线程内） |

---

#### 5. 对于 CPU 来说，并行和并发有什么区别？

**参考答案：**

- **并发（Concurrency）**：逻辑上的"同时"。单核 CPU 通过时间片轮转快速切换任务，宏观上看像一起跑，微观上同一时刻只有一个任务在执行。
- **并行（Parallelism）**：物理上的"同时"。需要多核/多 CPU 硬件支持，同一时刻确实有多个任务在不同核心上执行。

**一句话区分**：并发是"一个人同时吃三个汉堡（轮流咬）"，并行是"三个人同时吃三个汉堡"。

#### 6. 一段代码执行的时候内存分布长什么样？

**参考答案：**

从高地址到低地址：

```
高地址
+-------------------+
|  内核空间 (kernel) |  ← OS 用，用户态不可访问
+-------------------+
|     栈 (stack)     |  ← 局部变量、函数调用帧、返回地址
|        ↓ 增长      |
+-------------------+
|    内存映射区       |  ← mmap 映射、共享库、匿名映射
+-------------------+
|        ↑ 增长      |
|     堆 (heap)      |  ← malloc/new 动态分配
+-------------------+
|   BSS 段 (.bss)    |  ← 未初始化的全局/静态变量，默认清零
+-------------------+
|   数据段 (.data)   |  ← 已初始化的全局/静态变量
+-------------------+
| .rodata (只读数据)  |  ← 字符串常量、const 全局变量
+-------------------+
|   代码段 (.text)   |  ← 机器指令，只读可执行
+-------------------+
低地址
```

#### 7. 数据段存的是哪些东西？

**参考答案：**

数据段（`.data` 段）存的是**已初始化且初始值不为 0** 的全局变量和静态变量。

```c
int global = 42;          // .data 段
static int s_val = 100;   // .data 段

int uninit_global;        // .bss 段（未初始化，默认 0）
static int s_uninit;      // .bss 段

const char *s = "hello";  // "hello" 字面量在 .rodata（只读数据段）
                          // 指针 s 本身在 .data 段
```

> 💡 为什么 BSS 段要单独分出来？因为未初始化的变量默认都是 0，如果放在 .data 段会浪费磁盘空间——BSS 段在磁盘上不占空间，程序加载时由 OS 清零。

#### 8. malloc 和 free 的内部原理知道吗？

**参考答案：**

**malloc 底层实现（以 glibc ptmalloc 为例）：**

1. **向内核申请内存**：通过 `brk()` 或 `mmap()` 系统调用
   - 小内存（< **128KB**，可调）：用 `brk()` 移动堆顶指针，扩展堆空间
   - 大内存（≥ 128KB）：用 `mmap()` 映射一块匿名页（独立于堆之外）
2. **用户态内存管理**：ptmalloc 维护空闲内存块链表（bins/arena），用户申请时从空闲链表里找合适的块分配
3. **内存块结构**：每个分配块前面有一个 `struct malloc_chunk` 头部，记录块大小、是否空闲、前后指针等信息

**free 的原理：**

1. 通过指针 `p` 往前偏移找到 `malloc_chunk` 头部，拿到块大小
2. 将块标记为空闲，放入对应的空闲链表（bin）
3. **向前/向后合并**：如果前后相邻的块也是空闲的，就合并成一个大块，减少内存碎片
4. **归还 OS 的时机**：free 不一定把内存还给操作系统。对于 brk 分配的小内存，只有当堆顶有足够大的连续空闲空间时才会通过 `brk()` 回调归还；mmap 分配的大内存 free 时直接 `munmap()` 归还。

> ⚠️ **常见坑**：free 后指针变量本身的值没变，仍然指向那块内存（野指针），需要手动置 NULL。

### 三、进程通信

#### 9. 多进程之间的通信方式有哪些？优缺点？

**参考答案：**

| 方式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **管道 (pipe)** | 父子进程间，半双工，字节流 | 简单 | 只能亲缘进程、单向、无格式 |
| **有名管道 (FIFO)** | 磁盘上有路径，无亲缘限制 | 无亲缘关系也能用 | 半双工、效率一般 |
| **消息队列** | 内核维护的消息链表，有格式 | 有消息类型/优先级、可随机读 | 内核有大小限制、拷贝开销 |
| **共享内存** | 直接映射同一块物理内存 | **最快**，无需拷贝 | 需自己做同步、不安全 |
| **信号量** | 用于进程间同步/互斥 | 专门做同步 | 不传数据 |
| **Socket** | 跨机器通信 | 灵活、跨网络 | 开销大 |
| **信号 (signal)** | 异步通知 | 轻量 | 只能传少量信息、不可靠 |

---

#### 10. 共享内存的优缺点详细聊聊？

**参考答案：**

**优点：**
- **最快的 IPC 方式**：数据直接在用户态读写，不需要 read/write 系统调用，没有内核态和用户态之间的拷贝开销。
- 适合大数据量传输。

**缺点：**
- **同步问题**：多个进程同时读写会有竞态条件，必须配合信号量/互斥锁使用。
- **生命周期管理复杂**：共享内存在内核中维护，不会随进程退出自动销毁（除非显式删除），所有使用方需要协调。
- **大小固定**：创建时指定大小，后续不能动态扩容。
- **安全性**：所有挂载了这块共享内存的进程都能读写，权限控制粒度粗。

### 四、IO 与网络基础

#### 11. Linux 的 IO 多路复用有哪些类型？

**参考答案：**

| 机制 | 数据结构 | fd 上限 | 工作方式 | 时间复杂度 |
|------|---------|---------|---------|-----------|
| **select** | fd_set 位图 | 1024（FD_SETSIZE） | 每次遍历全部 fd，水平触发 | O(n) |
| **poll** | 链表（pollfd 数组） | 无限制（内存够就行） | 每次遍历全部 fd，水平触发 | O(n) |
| **epoll** | 红黑树 + 就绪链表 | 无限制 | **事件驱动**，只返回就绪 fd，支持 LT/ET | O(1) |

**epoll 为什么快：**
- 用红黑树（rbtree）管理所有被监听的 fd，增删改效率高
- 就绪 fd 用**双向链表**维护，epoll_wait 直接取链表，不用遍历全部
- **mmap** 了一块共享内存，内核和用户态共用就绪链表，避免拷贝

#### 12. OSI 七层模型和四层模型？

**参考答案：**

**OSI 七层模型（理论模型）：**
1. 物理层 → 2. 数据链路层 → 3. 网络层 → 4. 传输层 → 5. 会话层 → 6. 表示层 → 7. 应用层

**TCP/IP 四层模型（实际使用）：**
1. 网络接口层 → 2. 网际层（IP） → 3. 传输层（TCP/UDP） → 4. 应用层（HTTP/SSH/FTP…）

**对应关系：**
- 应用层 ← OSI 的应用层 + 表示层 + 会话层
- 网络接口层 ← OSI 的物理层 + 数据链路层

> 💡 面试常考：TCP 在第 4 层（传输层），IP 在第 3 层（网络层），HTTP 在第 7 层（应用层）。

#### 13. TCP 和 UDP 是什么？区别？

**参考答案：**

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接性 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认+重传） | 不可靠，尽力而为 |
| 有序性 | 保证有序（序列号） | 不保证顺序 |
| 流量控制 | 滑动窗口 | 无 |
| 拥塞控制 | 慢启动/拥塞避免/快重传/快恢复 | 无 |
| 首部开销 | 20 字节（不含选项） | 8 字节 |
| 速度 | 慢，开销大 | 快，开销小 |
| 适用场景 | 文件传输、网页浏览、邮件 | 视频会议、直播、DNS、游戏 |

#### 14. TCP 连接怎么进行的？

**参考答案：**

**三次握手：**

```
Client                          Server
  | --- SYN (seq=x) -----------> |    ① 客户端发 SYN，进入 SYN_SENT
  | <-- SYN+ACK (seq=y,ack=x+1)- |    ② 服务端回 SYN+ACK，进入 SYN_RCVD
  | --- ACK (ack=y+1) ---------> |    ③ 客户端回 ACK，双方进入 ESTABLISHED
```

**为什么不是两次？**
防止**已失效的连接请求报文**突然传到服务端。比如客户端第一个 SYN 卡在网络里超时了，客户端重发了一个新的，等连接建好并释放后，旧的 SYN 才到服务端。如果是两次握手，服务端收到旧 SYN 就会建立连接，白白浪费资源。三次握手中，客户端收到旧 SYN+ACK 后发现 seq 不对，会发 RST 拒绝，服务端就不会建立无效连接。

#### 15. TCP 为什么可靠？

**参考答案：**

五大机制保证可靠：

1. **序列号 + 确认机制**：每个字节都有序号，接收方回复 ACK 确认收到哪了。没收到 ACK 就超时重传。
2. **校验和**：发送端计算校验和，接收端验证，检测传输中是否出错。
3. **流量控制**：滑动窗口（rwnd），接收方告诉发送方自己的缓冲区还剩多少，防止发送太快把接收方撑爆。
4. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复，根据网络状况调整发送速率。
5. **超时重传**：发出去的包在 RTO 时间内没收到 ACK，就重传。

#### 16. TCP 的粘包听说过吗？

**参考答案：**

TCP 是**流式协议**，数据像水流一样没有边界。应用层连续发多个小数据包时，接收方可能一次收到多个包的数据（粘包），也可能只收到一个包的一部分（拆包）。

**产生原因：**
- 发送方：Nagle 算法合并小数据包一起发
- 接收方：TCP 缓冲区攒够了一起读
- MSS/MTU 限制：大于 MSS 的包会被分片

**解决方案（应用层加边界）：**
1. **定长包**：每个包固定 N 字节，简单但浪费空间
2. **特殊分隔符**：如 `\n`、`\r\n`，简单但数据里不能有分隔符
3. **头部加长度字段**：最常用，前 4 字节存包体长度，先读长度再读内容（如 Protocol Buffers、HTTP Content-Length）

#### 17. 四次挥手的机制和状态？

**参考答案：**

```
Client                          Server
  | --- FIN (seq=u) -----------> |    ① 主动关闭方发 FIN，进入 FIN_WAIT_1
  | <-- ACK (ack=u+1) ---------- |    ② 被动方回 ACK，进入 CLOSE_WAIT
  |                               |       （此时被动方还能继续发数据）
  | <-- FIN (seq=w) ------------ |    ③ 被动方数据发完，发 FIN，进入 LAST_ACK
  | --- ACK (ack=w+1) ---------> |    ④ 主动方回 ACK，进入 TIME_WAIT
  |                               |       被动方收到 ACK 后 CLOSED
  |  (等待 2MSL 后 CLOSED)       |
```

**为什么是四次？**
因为 TCP 是**全双工**的，每个方向要单独关。服务端收到 FIN 时可能还有数据没发完，所以先回 ACK，等数据发完了再发 FIN，分成两步。

---

#### 18. TIME_WAIT 状态过多是什么原因？

**参考答案：**

TIME_WAIT 是**主动关闭方**发完最后一个 ACK 后进入的状态，持续 **2MSL**（Linux 默认 60s，MSL=30s）。

**过多的原因：**
- **服务端主动关闭大量短连接**：比如 HTTP 短连接场景没开 keep-alive，每个请求都建连-关连，主动关闭方 TIME_WAIT 堆积
- **负载均衡器频繁建连/断连**
- **爬虫/压测端**主动发起并关闭大量连接

**危害：**
- 端口耗尽（最多 65535 个），新连接建立失败
- 占用内核资源

**解决：**
- 开启 `tcp_tw_reuse`：允许将 TIME_WAIT 的端口用于新的 outbound 连接（需配合 timestamps）
- 开启 `tcp_tw_recycle`：快速回收（NAT 环境下有坑，Linux 4.12 后已移除）
- 调整 `tcp_fin_timeout`，加快 FIN_WAIT_2 → TIME_WAIT 的流转
- 用长连接代替短连接（HTTP keep-alive）

#### 19. 输入 URL 的整体流程？网络协议怎么变化？

**参考答案：**

**完整流程：**
1. **URL 解析**：浏览器解析协议、域名、端口、路径
2. **DNS 解析**：浏览器缓存 → 系统缓存（hosts）→ 本地 DNS → 根/顶级/权威 DNS 递归查询，拿到 IP
3. **TCP 连接**：三次握手
4. **TLS 握手**（HTTPS）：密钥协商
5. **发送 HTTP 请求**：构造请求报文（请求行 + Header + Body）
6. **服务端处理**：Nginx 反向代理 → 应用服务器 → 数据库
7. **返回 HTTP 响应**：状态码 + Header + Body
8. **浏览器渲染**：解析 HTML → 构建 DOM → 加载 CSS/JS → 布局 → 绘制
9. **关闭连接**：四次挥手

**协议层级视角：**

| 层级 | 协议 |
|------|------|
| 应用层 | DNS（UDP 53）、HTTP/HTTPS、TLS |
| 传输层 | TCP（三次握手、可靠传输） |
| 网络层 | IP（寻址、路由）、ICMP |
| 数据链路层 | ARP（找下一跳 MAC）、以太网帧 |
| 物理层 | 网线/光纤/无线信号 |

#### 20. 本地发包到另一台机器，怎么一步步传过去？

**参考答案：**

1. **判断目标 IP 网段**：源主机用「自己的 IP & 子网掩码」和「目标 IP & 子网掩码」对比
   - 同一子网：直接交付，下一步找目标 MAC
   - 不同子网：发给**默认网关**，下一步找网关 MAC
2. **ARP 协议获取 MAC**：查本地 ARP 缓存，没有就发 ARP 广播请求，目标（或网关）单播回复 MAC
3. **封装以太网帧**：源 MAC + 目标 MAC + IP 包 + CRC 校验
4. **逐跳转发**：每经过一个路由器，**MAC 地址会变**（源 MAC 改成当前路由器出接口，目标 MAC 改成下一跳），但 **IP 地址始终不变**
5. **到达目标子网**：最后一跳路由器发 ARP 找目标主机 MAC，封装后交付

#### 21. 怎么感知到对面的 MAC 地址？

**参考答案：**

**ARP 协议**（Address Resolution Protocol，地址解析协议）。

- 发送方发 **ARP 广播帧**（目标 MAC 全 F），内容是："谁的 IP 是 x.x.x.x？请回复你的 MAC 地址给我"
- 该网段上只有 IP 匹配的机器会**单播回复**自己的 MAC 地址
- 发送方把结果存入 **ARP 缓存**（Linux 默认 60s），下次直接查缓存
- 反过来：已知 MAC 找 IP 用 **RARP**（反向地址解析），现在用得少了（DHCP 基本取代）

#### 24. 怎么存 JSON？

**参考答案：**

#### 26. MySQL 索引是什么？如何实现？

**参考答案：**

索引是**排序好的数据结构**，用来加速数据查找。类似书的目录，通过目录先找到页码再定位内容，而不是一页一页翻。

**InnoDB 默认用 B+ 树实现**，B+ 树的特点：
- 非叶子节点只存 **key + 子节点指针**，不存数据 → 同样高度下能存更多 key，树更矮，IO 更少
- 叶子节点存完整数据（聚簇索引）或主键值（二级索引）
- 叶子节点之间用**双向链表**串联 → 范围查询非常高效
- 所有查询都落到叶子节点 → 查询性能稳定

**两种索引类型：**
- **聚簇索引**：叶子节点存完整数据行，一个表只有一个（主键就是聚簇索引，没主键选唯一非空索引，再不行 InnoDB 自动建一个隐式 rowid）
- **二级索引（非聚簇）**：叶子节点存主键值，查数据需要回表（再走一次聚簇索引）

#### 27. MySQL 事务是什么？底层怎么实现？

**参考答案：**

事务是**一组原子性的 SQL 操作**，要么全部成功，要么全部回滚，中间状态不会被其他事务看到。

**底层三大机制：**

| 机制 | 作用 | 服务于哪个 ACID |
|------|------|----------------|
| **redo log**（重做日志） | 写前日志（WAL），记录"修改了什么"。崩溃后可以重做恢复 | **持久性**（D） |
| **undo log**（回滚日志） | 记录修改前的值，回滚用；也用于 MVCC 读历史版本 | **原子性**（A）+ 隔离性 |
| **MVCC**（多版本并发控制） | 读不加锁，读写不冲突。读操作读 undo 链上的历史版本 | **隔离性**（I） |
| **锁机制** | 行锁 + 间隙锁，写写互斥，防止并发写冲突 | **隔离性**（I） |

> 💡 WAL（Write-Ahead Logging）：先写日志，再写磁盘。好处是崩溃后可以从日志恢复，而且日志是顺序写，比随机写数据页快很多。

#### 28. MySQL 默认隔离级别？隔离级别有哪些？怎么实现隔离性？

**参考答案：**

**四种隔离级别（从低到高）：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED | ✅ 会 | ✅ 会 | ✅ 会 | 直接读最新数据 |
| READ COMMITTED | ❌ 不会 | ✅ 会 | ✅ 会 | MVCC，每次 SELECT 都生成新 ReadView |
| **REPEATABLE READ** ❗ | ❌ 不会 | ❌ 不会 | ❌ 不会（InnoDB） | MVCC + **间隙锁**，事务开始时生成 ReadView 一直用 |
| SERIALIZABLE | ❌ 不会 | ❌ 不会 | ❌ 不会 | 全加锁，串行执行 |

- **MySQL InnoDB 默认是 REPEATABLE READ**（可重复读）
- **怎么实现的**：
  - **MVCC**：读操作不加锁，读历史版本，实现读写不冲突
  - **锁机制**：写操作加行锁；RR 级别下还有**间隙锁（Gap Lock）+ Next-Key Lock**，防止幻读

> ⚠️ 注意：标准 SQL 定义中 RR 级别是会出现幻读的，但 InnoDB 通过 Next-Key Lock（行锁 + 间隙锁）解决了幻读问题。这是 MySQL 的扩展实现，面试要讲清楚。

#### 29. ACID 是什么？

**参考答案：**

| 字母 | 全称 | 含义 |
|------|------|------|
| **A** | Atomicity（原子性） | 事务是最小执行单元，要么全成功，要么全失败回滚。靠 undo log 实现 |
| **C** | Consistency（一致性） | 事务前后数据状态保持一致（约束、规则都满足）。是事务的最终目的，靠 A+I+D 共同保证 |
| **I** | Isolation（隔离性） | 并发事务之间互不干扰。靠 MVCC + 锁机制实现 |
| **D** | Durability（持久性） | 事务一旦提交，数据永久保存，崩溃也不丢。靠 redo log（WAL）实现 |

> 💡 面试加分点：ACID 里 C 是目的，A、I、D 是手段。一致性既包括数据库层面的约束（主键唯一、外键等），也包括业务层面的一致性（如转账前后总额不变）。

#### 30. 什么时候加索引？

**参考答案：**

**应该加的场景：**
- `WHERE` 条件里频繁用到的字段
- `JOIN` 的连接字段（ON 后面的字段）
- `ORDER BY` 排序的字段（索引本身有序，避免 filesort）
- `GROUP BY` 分组的字段
- 区分度高的字段（如用户 ID、手机号），选择性好

**不该加的场景：**
- 数据量很小的表（几千行以内，全表扫也很快）
- **区分度低**的字段（如性别、状态只有几个枚举值，索引命中率低）
- **更新频繁**的字段（每次更新都要维护索引，写放大严重）
- 经常参与计算的字段（函数包裹后索引用不上）

> 💡 一句话原则：**查询高频、区分度高、更新不频繁**的字段适合加索引。

#### 31. B 树和 B+ 树的区别？

**参考答案：**

| 维度 | B 树 | B+ 树 |
|------|------|-------|
| 数据存储 | 所有节点（叶子+非叶子）都存数据 | **只有叶子节点**存数据，非叶子只存 key + 指针 |
| 查询稳定性 | 不稳定，可能在中间节点就找到 | **稳定**，所有查询都要走到叶子 |
| 树的高度 | 同样数据量下更高（非叶子存数据，key 少） | 更矮（非叶子只存 key，扇出大）→ IO 更少 |
| 范围查询 | 需要中序遍历，跨层跳转 | 叶子节点有**双向链表**，直接顺序扫 |
| 叶子链表 | 没有 | 有双向链表 |

**B+ 树非叶子节点存什么？**
存 **key（索引列的值）+ 指向子节点的指针**，不存数据行。这样每个非叶子节点页（默认 16KB）能存更多 key，树的扇出更大、高度更低。

> 💡 面试延伸：一颗高度为 3 的 B+ 树能存多少数据？假设 key 8 字节、指针 6 字节，一页 16KB：
> 非叶子节点：16384 / (8+6) ≈ 1170 个 key
> 叶子节点存数据，假设一行 1KB，一页存 16 行
> 总数：1170 × 1170 × 16 ≈ **2200 万行** —— 所以千万级数据的表，主键查询只要 2~3 次 IO。

#### 33. MySQL 主从同步流程？

**参考答案：**

```
主库 (Master)                          从库 (Slave)
+----------------+                    +-----------------------+
|  dump 线程     | --- binlog 流 ---> |  IO 线程 → relay log  |
| (发送 binlog)  |                    |  SQL 线程（回放）     |
+----------------+                    +-----------------------+
```

**步骤：**
1. 从库执行 `CHANGE MASTER TO` 指定主库 IP、端口、用户名密码、binlog 文件位置，`START SLAVE` 启动
2. **从库 IO 线程**连接主库，主库创建 **dump 线程**，按 binlog 文件名+位置向从库发送 binlog 事件
3. 从库 IO 线程收到后写入 **relay log（中继日志）**，记录自己读到的位置
4. **从库 SQL 线程**读取 relay log，在从库上回放 SQL，更新数据
5. 从库记录自己执行到的位置（SQL Thread Position）

> 💡 面试常追问：
> - **主从延迟原因**：从库单线程回放（MySQL 5.7 后有基于 LOGICAL_CLOCK 的并行回放）、大事务、从库硬件差、网络延迟
> - **同步模式**：异步复制（默认，性能好但可能丢数据）、半同步（至少一个从收到才返回）、全同步（所有从都收到，性能差）

### 六、安全相关

#### 34. CSRF 是什么？怎么防范？

**参考答案：**

**CSRF（Cross-Site Request Forgery，跨站请求伪造）**：攻击者诱导已登录的用户访问恶意网站，恶意网站利用用户浏览器中保存的目标网站 Cookie，向目标网站发起请求，执行非用户本意的操作（如转账、改密码）。

**核心原理**：浏览器的 Cookie 会自动携带，跨站请求也会带上。

**防范方式：**
1. **CSRF Token**：服务端生成随机 token 放在表单或响应里，请求时客户端带上，服务端校验。攻击者的网站拿不到这个 token。
2. **SameSite Cookie**：设置 `SameSite=Strict` 或 `Lax`，禁止跨站请求携带 Cookie
3. **双重 Cookie 验证**：把 Token 存在 Cookie 里，请求时从 Cookie 读出来放到请求头/参数里，服务端比较两者是否一致
4. **Referer 校验**：验证请求来源（但 Referer 可篡改，不可靠，只能做辅助）
5. **关键操作加验证码/二次确认**

**SQL 注入**：用户输入被拼接到 SQL 语句中，导致恶意 SQL 执行。
- **防范**：永远用**参数化查询（PreparedStatement）**，不要拼接用户输入；做输入校验；最小权限原则。

### 七、Java 与容器

#### 35. Java 内存管理和 GC 策略？

**参考答案：**

**JVM 内存结构：**

| 区域 | 线程共享/私有 | 作用 |
|------|--------------|------|
| 堆（Heap） | 共享 | 存对象实例，GC 的主要战场 |
| 虚拟机栈（JVM Stack） | 私有 | 局部变量表、操作数栈、方法调用帧 |
| 本地方法栈（Native Stack） | 私有 | native 方法调用 |
| 方法区 / 元空间 | 共享 | 类信息、常量、静态变量、JIT 编译后的代码 |
| 程序计数器（PC Register） | 私有 | 当前执行到的字节码行号 |

**GC 策略（分代收集理论）：**

| 分代 | 收集器 | 算法 | 触发条件 |
|------|--------|------|---------|
| 年轻代（Eden + S0 + S1） | Minor GC | **复制算法** | Eden 区满了 |
| 老年代 | Major GC / Full GC | **标记-清除** 或 **标记-整理** | 老年代空间不足、大对象直接进入 |

**对象分配与晋升规则：**
1. 对象优先在 Eden 分配
2. Eden 满触发 Minor GC，存活对象复制到 Survivor（S0/S1 轮流）
3. 每熬过一次 Minor GC，年龄 +1
4. 年龄达到阈值（默认 15，CMS 默认 6）晋升老年代
5. 大对象（超过 -XX:PretenureSizeThreshold）直接进老年代

**主流收集器演进：**
Serial → Parallel（吞吐量优先）→ CMS（低延迟）→ G1（Region 分区）→ ZGC（染色指针 + 读屏障，ms 级停顿）

### 八、大模型与网络协议

#### 38. 大模型的 QKV 是什么？

**参考答案：**

Q（Query，查询）、K（Key，键）、V（Value，值）是 **Attention 自注意力机制**的核心概念。

**计算公式：**

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

**直观理解：**
- **Q**：当前词/位置的"查询表示"——我在找什么
- **K**：每个词/位置的"键表示"——我有什么特征
- **V**：每个词/位置的"值表示"——我实际携带的内容信息

**计算过程：**
1. Q 和 K 做点积（再除以 $\sqrt{d_k}$ 缩放），得到注意力分数——衡量当前词对每个其他词的关注程度
2. softmax 归一化成权重（和为 1）
3. 用权重对 V 加权求和，得到当前位置的注意力输出

> 💡 为什么除以 $\sqrt{d_k}$？防止 d_k 太大时点积结果过大，softmax 后梯度太小（反向传播时饱和）。除以 $\sqrt{d_k}$ 把方差拉回 1。

#### 39. SSE 和普通 HTTP 有什么区别？

**参考答案：**

**SSE（Server-Sent Events）** 是基于 HTTP/1.1 的单向推送技术，服务端可以持续向客户端推送数据。

| 维度 | 普通 HTTP | SSE | WebSocket |
|------|----------|-----|-----------|
| 通信方向 | 半双工（请求-响应） | **服务端 → 客户端 单向** | 全双工（双向） |
| 连接模式 | 短连接（也可长连接） | 长连接（EventSource） | 长连接 |
| 协议 | HTTP | HTTP（Content-Type: text/event-stream） | 独立的 ws 协议（基于 TCP） |
| 自动重连 | 无 | ✅ 内置断线重连机制 | 需自己实现 |
| 数据格式 | 任意 | 文本（有特定格式） | 文本 + 二进制 |
| 适用场景 | 请求-响应型 | 服务端推送：通知、实时日志、行情 | 双向交互：IM、游戏、协作 |

#### 40. HTTP 返回码有哪些？HTTP 2.0 比 1.1 优化了什么？

**参考答案：**

**常见状态码：**

| 分类 | 含义 | 常见码 |
|------|------|--------|
| 1xx | 信息性 | 101 Switching Protocols（协议升级，如 WebSocket） |
| 2xx | 成功 | 200 OK、201 Created、204 No Content、206 Partial Content |
| 3xx | 重定向 | 301 永久重定向、302 临时重定向、304 Not Modified、307 临时重定向（保持请求方法） |
| 4xx | 客户端错误 | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、405 Method Not Allowed、408 Request Timeout、429 Too Many Requests |
| 5xx | 服务端错误 | 500 Internal Server Error、502 Bad Gateway、503 Service Unavailable、504 Gateway Timeout |

**HTTP/2 相比 HTTP/1.1 的优化：**

1. **二进制分帧层**：不再是文本协议，数据被分成更小的帧，二进制编码，解析效率更高
2. **多路复用**：**一个 TCP 连接上同时处理多个请求**，每个请求一个 stream，互不阻塞。解决了 HTTP/1.1 的队头阻塞问题（应用层的队头阻塞）
3. **头部压缩（HPACK）**：静态表 + 动态表 + 霍夫曼编码，减少冗余 Header 传输
4. **服务端推送**：服务端可以主动把客户端还没请求的资源（如 CSS、JS）推送过去
5. **流量控制与优先级**：每个 stream 可以设置优先级，重要的请求先处理

> ⚠️ **面试常追问**：HTTP/2 解决了应用层的队头阻塞，但**没有解决 TCP 层的队头阻塞**——一个 TCP 连接上只要丢一个包，所有 stream 都得等重传。HTTP/3 用 QUIC（基于 UDP）彻底解决了这个问题。

### 九、Redis

#### 41. Redis 能存哪些数据结构？string 和 hash 底层怎么实现？

**参考答案：**

**Redis 常用数据结构：**
String、Hash、List、Set、ZSet（有序集合）、Bitmap、HyperLogLog、Geo、Stream。

**String 底层实现 —— SDS（Simple Dynamic String）：**

```c
struct sdshdr {
    int len;       // 已使用长度
    int free;      // 剩余空间
    char buf[];    // 实际数据
};
```

相比 C 字符串的优势：
- **O(1) 获取长度**（C 字符串要遍历到 `\0`）
- **二进制安全**（不靠 `\0` 判断结束，可以存图片、序列化对象等二进制数据）
- **减少扩容次数**（预分配空间，空间不够时按 2 倍或 1MB 扩容，空间冗余，避免每次 append 都重新分配）
- **兼容 C 字符串函数**（buf 末尾还是有 `\0`）

**Hash 底层实现：**

有两种编码方式，根据数据量自动切换：

- **数据量小的时候**：用 **ziplist（压缩列表）**
  - 条件：元素个数 < `hash-max-ziplist-entries`（默认 512）且 每个 value 长度 < `hash-max-ziplist-value`（默认 64 字节）
  - 特点：连续内存，紧凑存储，节省空间
  - 缺点：插入/删除需要移动后续数据，O(n)

- **数据量大的时候**：转成 **dict（哈希表）**
  - 数组 + 链表（链地址法解决哈希冲突）
  - 查找 O(1)
  - **渐进式 rehash**：扩容时不是一次性迁移所有数据，而是边访问边迁移，避免阻塞

> ⚠️ **资料勘误**：原文说 hash 小数据量用 ziplist，这在 Redis 6.x 及以前是对的。但 **Redis 7.0 之后，ziplist 被 listpack 取代**（listpack 是更高效的紧凑列表，去掉了 ziplist 的 prevlen 连锁更新问题）。面试时提一句"新版本用 listpack"是加分项。

## 资料勘误与重点提醒

> ⚠️ 原文中存在以下不严谨或错误的知识点，面试时请按纠正后的回答：

1. **MCP 没有"Memory 模式"**：MCP 只有 stdio 和 Streamable HTTP 两种传输模式。Memory 是 MCP 可以承载的一种能力场景，不是传输模式。MCP 定义了三类核心能力：Tools、Resources、Prompts。

2. **Redis hash 底层 ziplist → listpack**：Redis 6.x 及以前小数据量用 ziplist，**Redis 7.0+ 已用 listpack 取代 ziplist**。listpack 解决了 ziplist 中 prevlen 字段引起的"连锁更新"问题。

3. **HTTP/2 没有完全解决队头阻塞**：HTTP/2 的多路复用解决了**应用层**的队头阻塞（多个请求在一个 TCP 连接上不互相等），但**TCP 层的队头阻塞依然存在**——只要丢一个包，所有 stream 都卡住。HTTP/3 用 QUIC（基于 UDP）才彻底解决。

4. **InnoDB RR 级别解决幻读**：标准 SQL 定义中 REPEATABLE READ 会出现幻读，但 **InnoDB 通过 Next-Key Lock（行锁 + 间隙锁）在当前读下防止了幻读**。快照读靠 MVCC 本身就不会有幻读。这是 MySQL 的扩展实现，面试要点明。

5. **char 类型尾部空格**：CHAR 存储时会用空格填充到指定长度，但**读取时默认会去掉尾部空格**（PAD_CHAR_TO_FULL_LENGTH 模式除外）。这是一个容易被忽略的细节。

6. **TIME_WAIT 的 2MSL 时长**：Linux 上 MSL 通常是 30s，所以 2MSL = 60s。不是所有系统都是 1 分钟，要看具体实现。RFC 793 定义 MSL 为 2 分钟，实际实现通常减半。

7. **MySQL JSON 部分更新不是"原地修改"**：`JSON_SET` 等函数支持部分更新，是指 MySQL 内部可以只修改 JSON 二进制中的指定路径（不需要整个 JSON 反序列化-修改-序列化），但**磁盘上仍然是整页写入**（因为 InnoDB 是按页管理的）。
