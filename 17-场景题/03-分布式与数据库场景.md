# 03 - 分布式与数据库场景题

> 📌 **一句话理解**：分布式场景题考的是"选型与踩坑"——锁怎么选、事务怎么补、ID 怎么发、分片怎么分；数据库场景题考的是"定位与优化"——死锁怎么读日志、慢 SQL 怎么看 explain、大表怎么拆、并发改一行怎么不冲突。核心不是背方案，而是说清**每个方案的代价与适用边界**。

---

## 分布式场景

### 场景1：分布式锁如何实现

**场景描述**

秒杀/库存扣减/定时任务防重入等场景，多个服务实例同时操作共享资源，单机 `synchronized`/`ReentrantLock` 失效，需要一把跨进程的锁。面试官问：**分布式锁有哪些实现方式？怎么选型？**

**问题分析**

1. 分布式锁的本质仍是"互斥"——同一时刻只有一个客户端拿到锁，但锁的存储从 JVM 堆搬到了外部中间件。
2. 一把合格的分布式锁要满足：互斥性、可重入（可选）、防死锁（一定要能释放）、高可用、高性能。
3. 关键难点在于"加锁"与"设过期"必须原子、"释放锁"与"校验持锁者"必须原子，否则任一步骤之间宕机都会留下脏锁。

**解决方案**

| 方案 | 实现原理 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **Redis** | `SET key value NX PX 30000`，value 存唯一标识；释放用 Lua 脚本校验 value 后删除 | 性能高、实现简单、AP | 主从切换可能丢锁、有轻微不一致风险 | 高并发、对极端情况短暂不一致可容忍 |
| **Redlock** | 向 N 个独立 Redis 节点加锁，多数成功且耗时小于过期时间才算成功 | 降低单点主从切换丢锁风险 | 有争议（Martin Kleppmann 质疑）、部署复杂、性能下降 | 对正确性要求极高且能接受复杂度 |
| **Zookeeper** | 创建临时顺序节点，序号最小者获锁，其余 watch 前一个节点 | CP 强一致、客户端宕机自动释放（session 失效）、无主从切换丢锁问题 | 每次加锁要创建节点+watch，性能不如 Redis、有羊群效应（顺序节点已优化） | 对正确性要求高、并发量中等 |
| **数据库唯一索引** | `INSERT INTO lock_table(...) ON DUPLICATE KEY`，抢到唯一索引冲突者获锁 | 实现极简、强一致（DB 事务） | 性能差、需自己管过期/重试、DB 压力大 | 并发量低、不想引入中间件 |

Redis 加锁与释放（Lua 原子）：

```java
// 加锁：NX 保证不存在才设，PX 设过期防死锁，value 必须存唯一标识
String requestId = UUID.randomUUID().toString();
Boolean ok = jedis.set("lock:order:1001", requestId, SetParams.setParams().nx().px(30000));

// 释放：必须用 Lua 校验 value 再删，保证"判断+删除"原子
String lua =
  "if redis.call('get', KEYS[1]) == ARGV[1] then " +
  "  return redis.call('del', KEYS[1]) " +
  "else return 0 end";
jedis.eval(lua, Collections.singletonList("lock:order:1001"), Collections.singletonList(requestId));
```

选型一句话：**性能优先选 Redis（生产用主从+哨兵而非 Redlock），正确性优先选 Zookeeper，简单场景用数据库。**

> ⚠️ 易错点/陷阱：① 加锁必须 `SET ... NX PX` 一条命令原子完成，绝不能先 `setnx` 再 `expire`（两步之间宕机会留下永不过期的死锁）；② 释放锁必须用 Lua 校验 value，不能直接 `del`（会误删别人的锁，见场景2）；③ Zookeeper 是 CP，每次加锁创建临时节点；Redis 是 AP，性能好但主从异步复制，故障切换瞬间可能丢锁——不要误以为 Redis 锁绝对可靠。

### 场景2：分布式锁的坑（锁过期、误删、主从丢锁）

**场景描述**

线上用 Redis 分布式锁跑定时任务，某次业务执行到 40 秒（超过了锁的 30 秒过期时间），锁自动释放后另一个实例拿到锁开始执行，两个实例同时在跑。面试官问：**分布式锁有哪些典型坑？怎么解决？**

**问题分析**

1. **锁过期但业务没执行完**：业务耗时 > 锁 TTL，锁提前释放，别的实例趁虚而入，互斥被破坏。
2. **释放锁时误删别人的锁**：A 持锁过期释放，B 拿到锁，A 执行完直接 `del`，把 B 的锁删了。
3. **主从切换锁丢失**：主节点加锁后还没同步到从节点就宕机，哨兵提升新主，新主上没有这把锁，第三个实例也能加锁成功。

**解决方案**

**坑一：锁过期业务没执行完 → Redisson 看门狗续期**

```
业务线程 ─── 持有锁，执行业务 ────────────────────────────────>
             │                                        │
看门狗 ─── 每 10s 检查锁还在 → 续到 30s ── 每 10s 续 ── 每 10s 续 ──>
```

Redisson 看门狗机制：加锁时若**未指定 leaseTime**，默认租约 30 秒，后台启动一个定时任务每 10 秒（30/3）检查锁是否还被当前线程持有，是则续期到 30 秒，直到业务执行完主动释放。业务挂掉则看门狗也停止，锁到期自动释放。

```java
RLock lock = redissonClient.getLock("lock:order:1001");
// 不传 leaseTime，触发看门狗续期
lock.lock();                 // 默认 30s 租约 + 看门狗续期
// lock.lock(10, TimeUnit.SECONDS);  // ⚠️ 传了 leaseTime 就不启动看门狗，到期必释放
```

**坑二：释放锁误删别人的锁 → value 存 UUID + Lua 原子校验**

加锁时把 `requestId`（UUID）作为 value，释放时用 Lua 脚本"先 get 比较 value，相等才 del"，保证判断与删除原子（见场景1代码）。

**坑三：主从切换锁丢失 → Redlock 或 Zookeeper**

| 方案 | 思路 | 代价 |
|------|------|------|
| Redlock | 向 N 个独立 Redis（非主从）加锁，多数成功才算成功 | 有学术争议，部署复杂 |
| Zookeeper | 临时节点 + session，CP 强一致，客户端宕机自动释放 | 性能低于 Redis |
| 业务幂等兜底 | 锁失效时靠业务层幂等（如状态机校验）防止重复执行 | 不依赖锁的绝对可靠 |

> ⚠️ 易错点/陷阱：① Redisson 看门狗**默认 30s 租约、每 10s 续一次，且仅当未指定 leaseTime 时才生效**——一旦 `lock.lock(10, SECONDS)` 传了租约时间，看门狗就不启动，到期必释放，业务没执行完也会丢锁；② Redlock 有争议——Martin Kleppmann 指出其依赖时钟同步且仍无法根治 GC 停顿导致的持锁失效，实际生产多用"主从+哨兵 + 业务幂等兜底"而非 Redlock；③ 不要用 `setnx` + `expire` 两步加锁，必须 `SET NX PX` 原子加锁。

### 场景3：分布式事务方案选型

**场景描述**

下单流程涉及订单服务（写订单库）、库存服务（扣库存库）、账户服务（扣余额库），三个库要不全成功不全失败。面试官问：**分布式事务有哪些方案？各自适用什么场景？代价是什么？**

**问题分析**

1. 本地事务只能保证单库 ACID，跨库/跨服务需要分布式事务，但 CAP 告诉我们一致性、可用性、分区容错不能同时满足，跨网络必有取舍。
2. 强一致方案（2PC/XA）性能差、阻塞资源；最终一致方案（本地消息表/可靠消息）性能好但有延迟，需业务容忍。
3. 选型核心是问业务：**能否接受短暂不一致？并发量多大？是否侵入业务？**

**解决方案**

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 | 代价 |
|------|--------|------|---------|---------|------|
| **2PC/XA** | 强一致 | 差（阻塞） | 无 | 传统金融、同一 DB 资源 | 协调者单点、资源长时间锁定 |
| **Seata XA** | 强一致 | 差 | 低 | 已支持 XA 的数据库 | 同上，Seata 做协调者 |
| **Seata AT** | 准强一致（最终） | 中 | 低（自动生成回滚 SQL） | 大多数业务 | 有全局锁、短时不一致、需 undo_log |
| **TCC** | 强一致 | 高 | 高（写 Try/Confirm/Cancel） | 资金、库存等高并发 | 业务侵入大、需幂等+空回滚+悬挂处理 |
| **SAGA** | 最终一致 | 高 | 中（写正向+补偿） | 长流程业务（如旅行预订） | 补偿逻辑复杂、中间可见不一致 |
| **本地消息表** | 最终一致 | 高 | 中 | 跨服务异步解耦 | 依赖定时扫表、有延迟 |
| **可靠消息（RocketMQ 事务消息）** | 最终一致 | 高 | 中 | 异步解耦、订单+下游 | 依赖 MQ 可靠性、需幂等消费 |
| **最大努力通知** | 最终一致 | 高 | 低 | 对账、通知类 | 不保证一定成功、需人工兜底 |

Seata 各模式一句话：

```
AT  ：自动模式，代理 SQL 自动生成反向回滚 SQL，业务无感知，适合大多数 CRUD（最常用）
TCC ：手动三阶段，业务自己写 Try/Confirm/Cancel，性能最高但侵入大
SAGA：长事务，正向 + 补偿，适合流程长、各步骤异构的业务
XA  ：强一致，依赖 DB XA 协议，性能最差但严格 ACID
```

选型决策树：

```
要求强一致且并发低？ ──是──> XA / 2PC
        │否
高并发、资金类、能改业务？ ──是──> TCC
        │否
流程长、跨多个异构服务？ ──是──> SAGA
        │否
异步解耦、可接受最终一致？ ──是──> 本地消息表 / 事务消息
```

> ⚠️ 易错点/陷阱：① **CAP 不能同时满足三者**，跨网络系统 P（分区容错）必选，只能在 C 和 A 间取舍；**BASE 是最终一致**（Basically Available + Soft state + Eventually consistent），不是强一致；② TCC 不是万能——必须处理**空回滚**（Try 未执行就收到 Cancel）、**悬挂**（Cancel 先于 Try 到达）、**幂等**（Confirm/Cancel 可能重试）；③ Seata AT 模式有全局锁，并发写同一行时会串行化，不要误以为 AT 没有性能损耗；④ 不要在微服务里滥用强一致分布式事务，多数场景用"本地事务 + 消息最终一致"即可。

### 场景4：分布式ID生成方案

**场景描述**

分库分表后每张表都需要主键，数据库自增在分片场景下会冲突；订单号、流水号也需要全局唯一且有序。面试官问：**分布式 ID 有哪些方案？怎么选？**

**问题分析**

1. ID 的核心要求：全局唯一、趋势递增（利于 B+ 树索引）、高性能、高可用；部分场景还要可读、定长、不含业务信息。
2. 难点在于"唯一"与"有序"在分布式下难以兼得——UUID 唯一但无序，数据库自增有序但有瓶颈。
3. 雪花算法是主流，但要解决时钟回拨、机器位分配问题。

**解决方案**

| 方案 | 有序性 | 性能 | 依赖 | 缺点 | 适用场景 |
|------|--------|------|------|------|---------|
| **UUID** | 无序（随机） | 高（本地生成） | 无 | 36 位长、占空间、B+ 树写放大、不可读 | 仅做唯一标识、不做主键 |
| **数据库自增** | 严格递增 | 低（DB 瓶颈） | DB | 单点、分库后冲突、暴露业务量 | 单库、ID 量小 |
| **数据库号段（Leaf-Segment）** | 趋势递增 | 高（批量取号） | DB | 需维护号段表、重启丢号段 | 中等规模、需可读 ID |
| **Redis incr** | 严格递增 | 高 | Redis | 依赖 Redis 可用性、持久化丢号 | 简单递增、能接受少量丢号 |
| **雪花算法 Snowflake** | 趋势递增 | 高（本地生成） | 时钟 | 时钟回拨、机器位分配 | 主流方案、分库分表主键 |

雪花算法结构（64 bit）：

```
 0 | 41 bit 时间戳(ms) | 10 bit 机器ID | 12 bit 序列号
 │        │                    │                │
 符号位   当前时间-起始纪元     workerId        同ms内自增
 (固定0)  可用约69年           1024台机器       每ms 4096个
```

> ⚠️ 易错点/陷阱：① **UUID 不适合做 MySQL 主键**——无序导致 B+ 树插入时页分裂频繁、写放大严重、查询局部性差；若非要用，建议用 UUID v7（时间有序）或另起自增主键；② 雪花算法最大的坑是**时钟回拨**——机器时间被 NTP 往回调，可能生成重复 ID，解决方案有：回拨小时直接 sleep 等待、回拨大时抛异常、或记录历史时间借"未来时间"生成（需配合机器位隔离）；③ 号段模式批量取号会"预占用"，服务重启会丢失未用完的号段造成 ID 跳跃（不是连续），业务要能接受。

## 数据库场景

### 场景5：分库分表场景

**场景描述**

单表订单数据量已达 5000 万，查询变慢、写入抖动、备份耗时。面试官问：**什么时候该分库分表？怎么分？分片键怎么选？分完有哪些难题？**

**问题分析**

1. 分库分表不是银弹，它带来收益（降低单库压力、缩小单表数据量）也带来成本（跨库查询、分布式事务、运维复杂）。
2. 决策要区分"数据量大"还是"并发量大"——前者考虑分表（降低单表扫描行数），后者考虑分库（分散连接/写入压力）。
3. 分片键一旦选定难以更改，选错会导致跨库查询泛滥。

**解决方案**

**何时分（经验阈值，非绝对）：**

| 信号 | 阈值 | 动作 |
|------|------|------|
| 单表行数 | > 1000 万 | 评估分表 |
| 单表数据文件 | > 10~50GB | 评估分表 |
| 单库 QPS/连接数 | 接近上限 | 评估分库 |
| 单表索引深度、慢 SQL 多 | 优化无效 | 评估分表 |

**垂直 vs 水平：**

```
垂直分库：按业务拆库        user_db | order_db | stock_db   （解耦、专库专用）
垂直分表：按字段拆表        order_base(热字段) | order_ext(冷字段/大字段)
水平分表：按行拆表          order_0 | order_1 | ... | order_N （单表数据量过大）
水平分库+分表：库表都拆      db0.order_0 | db0.order_1 | db1.order_0 | ...
```

**分片键选择：**

| 策略 | 说明 | 风险 |
|------|------|------|
| 按 user_id 取模 | 同用户数据落同一库，利于按用户查询 | 跨用户聚合难、数据倾斜（大 V） |
| 按时间范围 | 天然冷热分离、易归档 | 热点写集中在最新分片 |
| 一致性哈希 | 扩容时迁移数据少 | 实现复杂、仍需处理倾斜 |

**分库分表后的难题：**

| 难题 | 表现 | 应对 |
|------|------|------|
| 跨库 Join | 无法直接 JOIN | 冗余字段 / 应用层组装 / 广播表（小表全量冗余） |
| 跨库聚合 | count/sum/group by 要扫所有分片 | 各分片先聚合再汇总、ES 异步聚合 |
| 跨库分页 | `LIMIT 10000,20` 要每个分片取 10020 条再全局排序 | 改用游标分页 `WHERE id > last_id LIMIT 20`（见场景8） |
| 跨库事务 | 本地事务失效 | 分布式事务（场景3）/ 最终一致 |
| 全局唯一 ID | 自增冲突 | 雪花算法（见场景6） |
| 路由复杂 | SQL 要带分片键才能精准路由 | 中间件 ShardingSphere / MyCat 拦截改写 |

> ⚠️ 易错点/陷阱：① 分库分表是"最后手段"，优先尝试索引优化、读写分离、冷热分离、归档——能不分就不分，分了就回不去；② 分片键要选**查询最频繁且能定位单库的字段**（如 user_id），否则大量查询退化为全分片扫描；③ 分库分表后跨库分页 `LIMIT M,N` 在 M 很大时性能极差，必须改游标分页，不能用传统深分页。

### 场景6：分库分表后的全局唯一ID怎么保证

**场景描述**

分了 16 个库、每库 64 张表后，MySQL 自增主键在多个分片上会重复，聚合查询会主键冲突。面试官问：**分库分表后全局唯一 ID 怎么保证？为什么选雪花算法？**

**问题分析**

1. 自增主键依赖单点 DB，分片后每个分片独立自增必然冲突。
2. 需要一个全局唯一、趋势递增（利于 B+ 树）、本地生成（不依赖中心化 DB）的方案。
3. 雪花算法是业界主流，但必须解决时钟回拨。

**解决方案**

雪花算法（Snowflake）是首选（结构见场景4）：

```
优势：
  - 本地生成，无网络开销，QPS 可达百万级
  - 趋势递增，B+ 树插入友好
  - 64 bit，可直接做 bigint 主键

时钟回拨问题与解决：
  ┌─ 回拨小（< 几 ms）：sleep 等待时间追平，再生成
  ├─ 回拨中（< 几 s）：记录上次时间戳，若当前时间 < 上次则用上次时间 + 1ms（借未来时间）
  └─ 回拨大（> 几 s）：抛异常 / 走备用机器位 / 关闭本机发号
```

其他补充方案：百度的 UidGenerator（雪花变种，用未来时间规避回拨）、美团的 Leaf（号段 + Snowflake 双 buffer，Leaf-Segment 适合可读 ID、Leaf-Snowflake 适合主键）。

```java
// 雪花算法核心逻辑（简化）
public synchronized long nextId() {
    long current = System.currentTimeMillis();
    if (current < lastTimestamp) {
        // 时钟回拨：小则等待，大则抛异常
        throw new ClockBackwardsException(current - lastTimestamp);
    }
    if (current == lastTimestamp) {
        sequence = (sequence + 1) & 0xFFF;        // 12 bit 序列号
        if (sequence == 0) current = tilNextMillis(lastTimestamp); // 同 ms 溢出等下一 ms
    } else {
        sequence = 0;
    }
    lastTimestamp = current;
    return (current - EPOCH) << 22                 // 时间戳左移 22 位
         | (workerId << 12)                       // 机器位左移 12 位
         | sequence;
}
```

> ⚠️ 易错点/陷阱：① 雪花算法**时钟回拨**是最大风险，必须处理——直接抛异常或借未来时间；② 机器位（workerId）10 bit 最多 1024 台，超过需协调分配（用 Zookeeper / 配置中心分配 workerId，避免手动配置重复）；③ 雪花 ID 是**趋势递增而非严格递增**——同一毫秒内不同机器生成的 ID 顺序不保证，不能用于强依赖单调的流水号场景。

### 场景7：MySQL死锁场景与排查

**场景描述**

线上偶发报错 `Deadlock found when trying to get lock; try restarting transaction`，业务日志显示两个接口交叉更新。面试官问：**MySQL 怎么排查死锁？常见死锁场景有哪些？怎么避免？**

**问题分析**

1. 死锁是两个或多个事务互相持有对方需要的锁，互相等待，InnoDB 主动检测到死锁后回滚代价较小的一个事务。
2. 常见两类：行锁交叉更新死锁、间隙锁（Gap Lock）死锁。
3. 排查靠 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段。

**解决方案**

**场景一：行锁交叉更新死锁**

```
事务A：UPDATE t SET ... WHERE id=1;  -- 持有 id=1 的行锁
事务B：UPDATE t SET ... WHERE id=2;  -- 持有 id=2 的行锁
事务A：UPDATE t SET ... WHERE id=2;  -- 等 id=2 锁（被B持有）
事务B：UPDATE t SET ... WHERE id=1;  -- 等 id=1 锁（被A持有）  => 死锁
```

**场景二：间隙锁死锁（RR 隔离级别）**

```
表 t 有 id=10, 20，事务A：SELECT ... WHERE id=15 FOR UPDATE  -- 给 (10,20) 加间隙锁
事务B：SELECT ... WHERE id=12 FOR UPDATE                    -- 也想加 (10,20) 间隙锁，互相等待 => 死锁
事务A：INSERT INTO t VALUES(12);  -- 被B的间隙锁阻塞
事务B：INSERT INTO t VALUES(15);  -- 被A的间隙锁阻塞  => 死锁
```

**排查步骤：**

```sql
-- 1. 看死锁日志（最近一次死锁详情）
SHOW ENGINE INNODB STATUS\G
-- 找 LATEST DETECTED DEADLOCK 段，看两个事务各持有什么锁、等什么锁

-- 2. 看当前锁等待
SELECT * FROM information_schema.INNODB_TRX;        -- 当前所有事务
SELECT * FROM performance_schema.data_locks;         -- 8.0+ 锁信息
SELECT * FROM performance_schema.data_lock_waits;   -- 8.0+ 锁等待

-- 3. 看隔离级别
SELECT @@transaction_isolation;
```

死锁日志关键信息（示例）：

```
*** (1) TRANSACTION:
UPDATE t SET v=1 WHERE id=2        -- 事务1 在等 id=2
*** (1) WAITING FOR LOCK: RECORD LOCKS on `test`.`t` trx id ... lock_mode X
*** (2) TRANSACTION:
UPDATE t SET v=2 WHERE id=1        -- 事务2 在等 id=1
*** (2) HOLDS THE LOCK(S): ... id=2 ...   -- 持有 id=2
*** (2) WAITING FOR LOCK: ... id=1 ...
*** WE ROLL BACK TRANSACTION (2)           -- 回滚了事务2
```

**如何避免：**

| 手段 | 说明 |
|------|------|
| 统一加锁顺序 | 所有事务按 id 升序加锁，消除交叉等待环 |
| 缩小事务 | 业务短小，锁持有时间短，降低碰撞概率 |
| 降低隔离级别 | RC 无间隙锁，可避免间隙锁死锁（需评估业务能否接受幻读） |
| 加合适索引 | 无索引的更新会锁全表/全间隙，极易死锁 |
| 业务重试 | 死锁后捕获异常重试（InnoDB 已回滚一方，重试通常能成功） |

> ⚠️ 易错点/陷阱：① **间隙锁在 RR（可重复读）隔离级别下才会加**，RC（读已提交）没有间隙锁——很多间隙锁死锁切到 RC 就消失，但要评估是否接受幻读；② `UPDATE/DELETE WHERE` 条件**没有走索引会升级为表锁**（实际是给所有行加锁），极易死锁，务必确保 WHERE 走索引；③ InnoDB 不会无限等待死锁，有 `innodb_deadlock_detect=ON`（默认开）主动检测并回滚一方，超时由 `innodb_lock_wait_timeout`（默认 50s）控制。

### 场景8：慢SQL优化场景

**场景描述**

某接口偶发慢，监控发现一条 SQL 平均 800ms，表 2000 万行。面试官问：**这条慢 SQL 怎么分析？怎么优化？**

**问题分析**

1. 慢 SQL 优化的标准动作：`explain` 看执行计划 → 判断是否走索引、是否回表、扫描行数 → 针对性优化。
2. 常见根因：索引失效、回表过多、大分页深翻、索引选错。

**解决方案**

**第一步：explain 分析关键字段**

```
EXPLAIN SELECT * FROM order WHERE user_id=100 AND status=1 ORDER BY create_time LIMIT 20;

关键字段：
  type        : 访问类型，理想 ref/range/const，最差 ALL（全表扫描）
  key         : 实际用的索引，NULL 表示没走索引
  rows        : 预估扫描行数，越小越好
  Extra       : Using index（覆盖索引好）/ Using filesort（额外排序坏）/ Using temporary（临时表坏）
```

| type | 含义 | 评价 |
|------|------|------|
| const/system | 主键/唯一索引等值查询 | 最优 |
| eq_ref | 唯一索引 JOIN | 好 |
| ref | 非唯一索引等值 | 好 |
| range | 索引范围扫描 | 可接受 |
| index | 扫整个索引树 | 较差 |
| ALL | 全表扫描 | 差，必须优化 |

**第二步：常见优化点**

**1. 索引失效场景（让索引白建）：**

| 场景 | 反例 | 正例 |
|------|------|------|
| 函数操作 | `WHERE YEAR(create_time)=2024` | `WHERE create_time>='2024-01-01'` |
| 隐式类型转换 | `WHERE phone=13800000000`（phone 是 varchar） | `WHERE phone='13800000000'` |
| 左模糊 | `WHERE name LIKE '%张'` | `WHERE name LIKE '张%'`（走索引） |
| 联合索引非最左前缀 | 索引(a,b,c)，`WHERE b=1` | `WHERE a=1 AND b=1` |
| OR 两边非全索引 | `WHERE a=1 OR d=2`（d 无索引） | 拆 UNION 或给 d 加索引 |

**2. 回表与覆盖索引：**

```
SELECT status FROM order WHERE user_id=100;       -- 回表（user_id索引->主键->数据行取status）
SELECT user_id FROM order WHERE user_id=100;      -- 覆盖索引（user_id索引即含结果，不回表）
建联合索引 (user_id, status) 可覆盖 SELECT user_id,status FROM ... WHERE user_id=100
```

**3. 大分页深翻优化（重点）：**

```sql
-- ❌ 慢：偏移越大越慢，要扫描前 1000020 行再丢弃
SELECT * FROM order ORDER BY id LIMIT 1000000, 20;

-- ✅ 游标分页：记住上一页最后 id，用 WHERE 条件定位，避免扫描丢弃
SELECT * FROM order WHERE id > 1000000 ORDER BY id LIMIT 20;

-- ✅ 延迟关联：先走覆盖索引查 id，再 JOIN 取数据，减少回表
SELECT t.* FROM order t
INNER JOIN (SELECT id FROM order ORDER BY id LIMIT 1000000, 20) tmp
ON t.id = tmp.id;
```

```
深分页性能对比：
  LIMIT 1000000,20 ：扫描 1000020 行 + 大量回表        → 秒级
  WHERE id>last    ：索引定位 + 20 行回表              → 毫秒级
```

> ⚠️ 易错点/陷阱：① **大分页 `LIMIT M,N` 在 M 很大时性能极差**——MySQL 要扫描前 M+N 行再丢弃前 M 行，必须用游标分页 `WHERE id > last_id LIMIT N` 或延迟关联；② `LIKE '%xxx'` 左模糊**不走索引**，只有右模糊 `LIKE 'xxx%'` 才走；③ `EXPLAIN` 的 `rows` 是**预估值**，统计信息过期会导致估值不准、优化器选错索引，必要时 `ANALYZE TABLE` 刷新统计；④ `Using filesort` 不一定真用磁盘文件（小结果集在内存完成），但仍是优化信号。

### 场景9：千万级大表CRUD慢如何优化

**场景描述**

一张订单表已 5000 万行，增删改查都变慢，单条 update 要 2 秒，count 全表几十秒。面试官问：**千万级大表怎么优化？**

**问题分析**

1. 大表慢的根因：B+ 树层级变深、索引膨胀、单表数据量大导致扫描与锁范围扩大。
2. 不能只靠加索引，要从"减少单表数据量"和"分散访问压力"两端入手。
3. CRUD 各有痛点：查慢（扫描多）、写慢（索引维护 + 锁）、删慢（标记删除不释放空间）。

**解决方案**

| 维度 | 手段 | 说明 |
|------|------|------|
| **索引优化** | 建合适索引、覆盖索引、消除全表扫描 | 见场景8，成本低、收益高，先做 |
| **冷热分离** | 热数据留在主表，冷数据归档到历史表 | 按时间/状态拆，主表变小，查询变快 |
| **数据归档** | 定期把历史数据搬到归档库/表 | `INSERT INTO order_history SELECT ... WHERE create_time < '2023-01-01'` + 删除 |
| **分库分表** | 水平拆分降低单表数据量 | 见场景5，最后手段 |
| **读写分离** | 主写从读，分散读压力 | 配合主从延迟处理（见场景11） |
| **垂直拆表** | 大字段/冷字段拆到扩展表 | 减少主表行宽，提升缓存命中 |
| **count 优化** | 维护计数表/缓存总数 | 不实时 `SELECT COUNT(*)`，用 Redis/汇总表存近似值 |
| **删除优化** | 分批小事务删除 | 避免大事务锁表、binlog 暴涨；`DELETE ... LIMIT 1000` 循环 |

冷热分离示意：

```
订单主表 (热，近 3 个月)        ←── 高频读写，索引小，查询快
   │ 归档任务（定时搬走）
   ▼
订单历史表 (冷，3 个月前)       ←── 低频查询，可放廉价存储/单独库
```

> ⚠️ 易错点/陷阱：① **大表 `DELETE` 是大忌**——删除大量行会长时间持锁、binlog 暴涨、且 InnoDB 标记删除后空间不自动回收（需 `OPTIMIZE TABLE` 重建表，期间锁表），应分批小事务删除；② `COUNT(*)` 在 InnoDB 下是全表扫描（不像 MyISAM 有计数），大表不要实时 count，维护计数表或用缓存近似值；③ 优化顺序应是 **索引 → 冷热分离 → 归档 → 读写分离 → 分库分表**，由轻到重，别一上来就分库分表。

### 场景10：高并发下安全修改同一行数据

**场景描述**

秒杀扣库存，1000 个请求同时抢 1 件商品，如何保证不超卖？面试官问：**高并发下安全修改同一行数据有哪些方案？怎么选？**

**问题分析**

1. 核心是"读-改-写"要原子，否则并发下基于旧值计算会超卖。
2. 三类方案：乐观锁（版本号/CAS）、悲观锁（`SELECT ... FOR UPDATE`）、分布式锁。
3. 选型取决于冲突概率：冲突少用乐观锁（无锁性能高），冲突多用悲观锁或分布式锁。

**解决方案**

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **乐观锁（版本号）** | `UPDATE SET stock=stock-1,version=version+1 WHERE id=? AND version=?` | 无锁、性能高、不阻塞 | 冲突多时重试多、失败率高 | 冲突少、读多写少 |
| **乐观锁（条件 CAS）** | `UPDATE SET stock=stock-1 WHERE id=? AND stock>0` | 简单、利用 DB 行锁原子性 | 仅适合简单条件 | 扣减类 |
| **悲观锁（FOR UPDATE）** | `SELECT ... FOR UPDATE` 先锁行再改 | 强一致、避免重试 | 阻塞等待、持锁久易死锁 | 冲突多、强一致 |
| **分布式锁** | 场景1，串行化访问 | 跨服务通用 | 性能最低、依赖中间件 | 跨服务资源 |

乐观锁（推荐秒杀场景）：

```sql
-- 方案一：版本号（通用）
UPDATE goods SET stock=stock-1, version=version+1
WHERE id=1 AND version=5;     -- 影响行数=0 说明被别人改过，重试

-- 方案二：条件 CAS（扣减类最简，DB 行锁保证原子）
UPDATE goods SET stock=stock-1
WHERE id=1 AND stock>0;       -- stock<=0 时影响行数=0，自然防超卖
```

悲观锁：

```sql
-- 开启事务
SELECT stock FROM goods WHERE id=1 FOR UPDATE;   -- 锁定该行
-- 应用层判断 stock>0
UPDATE goods SET stock=stock-1 WHERE id=1;
COMMIT;
-- 整个事务期间该行被锁，其他 FOR UPDATE 等待
```

```
选型决策：
  冲突率低（< 10%）     ──> 乐观锁（版本号/CAS）   无锁性能最高
  冲突率高、强一致       ──> 悲观锁 FOR UPDATE     串行化防冲突
  跨服务/跨进程资源       ──> 分布式锁             通用但性能最低
  扣减类（库存/余额）    ──> 条件 CAS（WHERE stock>0）最简最高效
```

> ⚠️ 易错点/陷阱：① **`FOR UPDATE` 是悲观锁会阻塞**其他读该行的事务（实际锁的是索引记录），高并发下大量等待，乐观锁适合冲突少的场景；② 乐观锁版本号方案在**冲突率高时重试风暴**反而更差——大量请求抢同一行，只有少数成功，其余重试又加剧冲突，此时应改悲观锁；③ 秒杀扣库存最优解往往是**条件 CAS `WHERE stock>0`**（DB 行锁天然原子，一条 SQL 搞定，无需应用层重试）+ 前置 Redis 预扣减。

### 场景11：主从延迟导致读到旧数据怎么解决

**场景描述**

写主库后立即从从库读，偶尔读到旧值（刚写入的数据查不到）。面试官问：**主从延迟怎么解决？**

**问题分析**

1. MySQL 主从复制是异步的：主库写 binlog → IO 线程拉到从库 relay log → SQL 线程回放，存在延迟（毫秒到秒级）。
2. "写后立即读"场景（如提交订单后跳转订单详情）容易命中延迟窗口，读到旧数据。
3. 根因是"读走了从库而数据还没同步"。

**解决方案**

| 方案 | 思路 | 代价 | 适用 |
|------|------|------|------|
| **强制走主库** | 写后短期内相关读强制路由到主库 | 主库压力增大 | 强一致读、读量可控 |
| **缓存过渡** | 写主库同时写 Redis，读先查缓存 | 缓存与 DB 一致性、缓存失效窗口 | 读多写少、可接受最终一致 |
| **半同步复制** | 主库等至少一个从库收到 binlog 才返回 | 写延迟略增、仍非严格一致 | 对数据安全要求高 |
| **读写判断** | 写后短暂时间内（如 1s）读主库，之后读从库 | 实现复杂、需判断窗口 | 通用折中 |
| **写后等待** | 写后 sleep/校验从库位点再读 | 增加延迟 | 不推荐，性能差 |

强制走主库示意：

```
写请求 ──> 主库 (写)
            │
            ├─ 短期内（如 3s 内）该用户的读 ──> 主库 (强一致读)
            │
            └─ 其他读 ──> 从库 (分担压力)
```

半同步复制（semi-sync）：

```
主库写 ──binlog──> 从库 ACK ──> 主库才返回客户端成功
  （至少一个从库确认收到，降低丢数据风险，但回放仍异步，读从库仍可能滞后）
```

> ⚠️ 易错点/陷阱：① 半同步复制只保证**主库 binlog 已传到从库**（不丢数据），但**从库回放仍异步**，读从库仍可能读到旧值，不要误以为半同步就解决读延迟；② 强制走主库要**限定范围**（如仅"写后 N 秒内该用户的读"），否则主库被打爆；③ 最实用的组合是"写主库 + 写缓存 + 读缓存兜底"，但要注意缓存与 DB 的一致性（见 `05-分布式系统/02-缓存策略.md` 缓存一致性）。

### 场景12：数据库连接池配置不当引发的问题

**场景描述**

高峰期接口偶发报错 `HikariPool-1 - Connection is not available, request timed out after 30000ms`，但数据库本身没压力。面试官问：**连接池怎么配？常见坑有哪些？**

**问题分析**

1. 连接池太小 → 高并发时连接耗尽，请求排队超时；连接池太大 → 数据库连接数打满、上下文切换开销大。
2. 超时配置不合理 → 连接泄漏（拿了不还）时长时间卡住，或超时太短导致正常慢查询被误杀。
3. HikariCP 是 Spring Boot 默认连接池，性能好但对配置敏感。

**解决方案**

**HikariCP 关键参数：**

| 参数 | 含义 | 建议值 |
|------|------|--------|
| `maximum-pool-size` | 最大连接数 | 公式 `(core_count * 2) + effective_spindle_count`，或经验值 10~30 |
| `minimum-idle` | 最小空闲连接 | 建议等于 maximum-pool-size（固定大小，避免动态创建开销） |
| `connection-timeout` | 获取连接超时 | 30000ms（30s），超时报错 |
| `idle-timeout` | 空闲连接超时 | 600000ms（10min），与 maxLifetime 配合 |
| `max-lifetime` | 连接最大存活时间 | 1800000ms（30min），需小于 DB 的 `wait_timeout` |
| `leak-detection-threshold` | 连接泄漏检测 | 60000ms（60s），超过未归还记日志 |
| `validation-timeout` | 连接校验超时 | 5000ms |

**连接数计算经验公式（PostgreSQL 官方推荐，MySQL 类似）：**

```
connections = ((core_count * 2) + effective_spindle_count)
  core_count            : CPU 核数
  effective_spindle_count : 磁盘数（SSD 可忽略，按 0~1 算）
例：8 核 + SSD → (8*2)+0 = 16 左右

切勿盲目调大：连接越多，DB 端上下文切换与锁竞争越严重，反而变慢
```

**常见坑与排查：**

| 现象 | 根因 | 解决 |
|------|------|------|
| `Connection is not available` 超时 | 池太小 / 慢 SQL 占连接 / 连接泄漏 | 调大池、优化慢 SQL、查泄漏 |
| 连接泄漏（拿不还） | 忘记 close / 事务未提交 / 异常未释放 | 用 try-with-resources、排查长事务（见 03-Spring全家桶/09） |
| 偶发连接断开 | DB `wait_timeout` < 连接池 maxLifetime | maxLifetime 设小于 wait_timeout |
| 启动慢 | minimumIdle 过大、建连慢 | 预热或适当调小 minimumIdle |
| 连接池配置与 DB `max_connections` 不匹配 | N 个应用实例 × 每实例 poolSize > DB max_connections | 总连接数 < DB max_connections × 80% |

> ⚠️ 易错点/陷阱：① 连接池**不是越大越好**——连接数超过 CPU 核数后，DB 端线程切换开销激增，吞吐反而下降，经验值通常 10~30；② `max-lifetime` **必须小于** MySQL 的 `wait_timeout`（默认 8 小时），否则连接被 DB 单方面关闭，连接池拿到失效连接报错；③ 连接泄漏常因**事务长时间不提交或异常未回滚**（见长事务场景），开 `leak-detection-threshold` 帮助定位；④ HikariCP 官方建议 `minimum-idle = maximum-pool-size`（固定池大小），避免动态创建/销毁连接的开销，与"最小空闲"直觉相反。

## 常见面试题

**Q1：Redis 分布式锁和 Zookeeper 分布式锁的区别？怎么选？**

Redis 是 AP，性能高但主从异步复制，故障切换瞬间可能丢锁；Zookeeper 是 CP，基于临时顺序节点，客户端宕机 session 失效自动释放，不会丢锁，但每次加锁要创建节点+watch，性能低于 Redis。选型：高并发、可容忍极端短暂不一致选 Redis；对正确性要求高、并发中等选 Zookeeper。

**Q2：Redlock 是什么？为什么有争议？**

Redlock 由 Redis 作者提出，向 N 个独立 Redis 实例（非主从）加锁，多数成功且耗时小于锁过期才算获锁，旨在降低单点主从切换丢锁风险。Martin Kleppmann 质疑其依赖时钟同步（NTP 跳变会破坏正确性）、且 GC 停顿期间持锁失效无法根治。生产中多用"主从+哨兵 + 业务幂等兜底"而非 Redlock。

**Q3：TCC 要处理哪三个问题？**

空回滚（Try 未执行就收到 Cancel，要能识别并跳过）、悬挂（Cancel 先于 Try 到达，Try 到达时要拒绝）、幂等（Confirm/Cancel 可能因重试被调用多次，需保证幂等）。

**Q4：雪花算法时钟回拨怎么处理？**

回拨小（几 ms）sleep 等待时间追平；回拨中（几 s）记录上次时间戳，当前时间小于上次则借用上次时间 +1ms（借未来时间）；回拨大抛异常或走备用机器位。机器位（workerId）需用 Zookeeper/配置中心统一分配，避免冲突。

**Q5：分库分表后跨库分页怎么办？**

传统 `LIMIT M,N` 在 M 大时要每个分片取 M+N 条再全局排序，性能极差。改用游标分页 `WHERE id > last_id LIMIT N`，记录上一页最后 ID，用索引定位，避免深翻页。无法用游标的全局排序场景，需 ES 异步聚合或各分片汇总。

**Q6：乐观锁和悲观锁怎么选？**

冲突率低（读多写少）选乐观锁（版本号/CAS），无锁性能高；冲突率高（写密集）选悲观锁 `FOR UPDATE`，串行化避免大量重试。扣减类（库存/余额）最优是条件 CAS `WHERE stock>0`，DB 行锁天然原子。乐观锁冲突多时重试风暴反而更差。

**Q7：MySQL 死锁怎么排查？**

`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段，看两个事务各持有什么锁、等什么锁、回滚了哪个。`information_schema.INNODB_TRX` / `performance_schema.data_locks` 看当前锁。常见死锁：行锁交叉更新（统一加锁顺序）、间隙锁死锁（RR 级别，切 RC 或缩小事务）。

**Q8：为什么 UUID 不适合做 MySQL 主键？**

UUID 无序，作为聚簇索引主键插入时 B+ 树频繁页分裂、写放大严重、查询局部性差（随机 IO）。建议用自增 ID 或雪花 ID（趋势递增），若必须用 UUID 选 v7（时间有序）或另起自增主键 + UUID 做业务键。

**Q9：`SELECT ... FOR UPDATE` 会不会锁表？**

走了索引（主键/唯一/普通索引）锁的是匹配的行（行锁）；**没走索引会升级为锁所有行**（实际是给所有扫描到的记录加锁，近似表锁）。所以 `FOR UPDATE` 的 WHERE 必须走索引，否则全表锁死。

**Q10：HikariCP 连接池大小怎么定？**

经验公式 `(core_count * 2) + effective_spindle_count`，8 核 + SSD 约 16。不是越大越好，超过 CPU 核数后 DB 端线程切换开销激增。总连接数（应用实例数 × poolSize）要小于 MySQL `max_connections` 的 80%。

## 资料勘误与重点提醒

> 本节集中说明分布式与数据库场景中常见资料表述不准、易混点，以及面试高频但资料常遗漏的重点。

1. **Redis 分布式锁必须设过期时间，且释放要校验 value（Lua 原子）**：
   - 加锁必须 `SET key value NX PX` 一条命令原子完成，**不能先 `setnx` 再 `expire`**（两步之间宕机会留下永不过期的死锁）。
   - 释放必须用 Lua 脚本"先 get 比较 value，相等才 del"，**不能直接 `del`**（会误删别人持有的锁）。
   - value 必须存唯一标识（UUID/requestId），不能用固定值。

2. **Redisson 看门狗续期**：
   - 默认租约 30 秒，后台定时任务每 10 秒（30/3）续期到 30 秒。
   - **仅当加锁时未指定 leaseTime 才启动看门狗**；一旦 `lock.lock(10, SECONDS)` 传了租约，看门狗不启动，到期必释放。
   - 看门狗随业务线程生命周期，业务线程挂掉则看门狗停止，锁到期自动释放。

3. **Redlock 有争议，生产慎用**：
   - Martin Kleppmann 指出 Redlock 依赖时钟同步、无法根治 GC 停顿导致的持锁失效。
   - 实际生产多用"主从+哨兵/集群 + 业务幂等兜底"，而非 Redlock。
   - 强一致需求应选 Zookeeper（CP）而非 Redlock。

4. **雪花算法时钟回拨**：
   - 是雪花算法最大风险，必须处理（sleep / 借未来时间 / 抛异常）。
   - 雪花 ID 是**趋势递增而非严格递增**，同毫秒内不同机器顺序不保证。
   - workerId 需集中分配（Zookeeper/配置中心），避免手动配置重复。

5. **`FOR UPDATE` 是悲观锁会阻塞，乐观锁适合冲突少**：
   - 走索引锁行，**没走索引锁全表**（给所有扫描记录加锁）。
   - 高并发抢同一行用乐观锁会重试风暴，此时该用悲观锁或条件 CAS。
   - 扣减类最优是 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0`（条件 CAS，DB 行锁原子）。

6. **间隙锁在 RR 隔离级别下会加，可能引发死锁**：
   - RC（读已提交）没有间隙锁，很多间隙锁死锁切 RC 即消失，但要评估是否接受幻读。
   - `UPDATE/DELETE WHERE` 无索引会锁所有间隙，极易死锁，务必走索引。
   - InnoDB 默认 `innodb_deadlock_detect=ON` 主动检测死锁并回滚一方。

7. **limit 大分页优化用游标/where id>last_id**：
   - `LIMIT 1000000,20` 要扫描 1000020 行再丢弃前 100 万，秒级慢。
   - 改 `WHERE id > last_id LIMIT 20`（游标分页）或延迟关联（先覆盖索引查 id 再 JOIN），毫秒级。
   - 游标分页要求按自增/索引列连续排序，不支持随机跳页。

8. **分布式事务 CAP 不能同时满足，BASE 是最终一致**：
   - CAP 三者不可兼得，跨网络系统 P 必选，C 与 A 二选一。
   - BASE（Basically Available + Soft state + Eventually consistent）是最终一致，**不是强一致**。
   - TCC 必须处理空回滚、悬挂、幂等三问题。
   - Seata AT 模式有全局锁，并发写同一行会串行化，不是零性能损耗。

9. **Zookeeper 分布式锁是 CP，Redis 是 AP**：
   - Zookeeper：临时顺序节点 + watch，强一致，客户端宕机 session 失效自动释放，不丢锁，但性能低于 Redis。
   - Redis：主从异步复制，性能高，但故障切换瞬间可能丢锁，需业务幂等兜底。
   - 不要误以为 Redis 锁绝对可靠，强一致场景选 Zookeeper。

10. **UUID 不适合做 MySQL 主键**：
    - 无序导致 B+ 树页分裂频繁、写放大、随机 IO，查询局部性差。
    - 若必须用 UUID 选 v7（时间有序），或另起自增/雪花主键 + UUID 做业务键。

11. **大表 DELETE 是大忌**：
    - 大事务长时间持锁、binlog 暴涨、InnoDB 标记删除后空间不自动回收。
    - 应分批小事务删除 `DELETE ... LIMIT 1000` 循环，必要时 `OPTIMIZE TABLE` 回收空间（期间锁表）。

12. **连接池不是越大越好**：
    - 经验公式 `(core_count * 2) + spindle_count`，8 核约 16。
    - 超过 CPU 核数后 DB 端线程切换开销激增，吞吐反而下降。
    - `max-lifetime` 必须小于 MySQL `wait_timeout`，否则连接被 DB 单方面关闭。
    - HikariCP 建议 `minimum-idle = maximum-pool-size`（固定池大小）。
