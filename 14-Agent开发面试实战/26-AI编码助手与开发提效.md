# 26 - AI 编码助手与开发提效

> 「用 AI 提效」本身也是面试热点。本章讲 Cursor/Claude Code/Copilot 原理对比、怎么用 AI 提效开发、MCP Server 开发、自建团队 AI 工具链。13 章讲了 ClaudeCode 原理，本章讲实战和工程化。

---

## 一、主流 AI 编码助手对比 ★

| 产品 | 出身 | 特点 | 适合 |
|------|------|------|------|
| **Claude Code** | Anthropic | 终端原生、Harness 工程化强、Skill/Hooks/子Agent/MCP 生态完整 | 复杂工程任务、Agent 化 |
| **Cursor** | Anysphere | IDE 优先、编辑器深度集成、Composer 多文件改 | 日常编码、IDE 党 |
| **GitHub Copilot** | GitHub/MS | IDE 补全+Agent、企业集成好 | 企业标准化 |
| **Cline/Roo** | 开源 | VS Code 插件、可自定义、透明 | 想可控/自研 |
| **Aider** | 开源 | 终端、git 友好、轻量 | 终端党、轻任务 |
| **Devin** | Cognition | 自主软件工程师定位、云端 | 全自动任务 |

### 1.1 共同本质

- 都是「**LLM + Harness + 工具循环**」的编码 Agent（13 章）。
- 差异在：Harness 工程化深度、产品形态（IDE/终端/云）、生态（MCP/Skill/插件）、可控性。

> 💡 **面试金句**：编码助手本质都是 LLM+Harness+工具循环的 Agent。差异在 Harness 工程化深度和产品形态。选型看团队习惯（IDE/终端）和任务复杂度（简单补全用 Copilot，复杂工程用 Claude Code）。

## 二、用 AI 提效开发的场景 ★

### 2.1 写代码

- **从需求到代码**：描述需求让 AI 生成初版，自己 review 修改。
- **样板代码**：CRUD/DTO/转换器等重复代码，AI 快速生成。
- **多语言/框架**：不熟悉的语言/框架，AI 帮写+解释。
- **要点**：描述清晰、分步给、review 为主（别盲目信任）。

### 2.2 Code Review

- 让 AI 审代码：找 Bug、安全漏洞、性能问题、规范。
- 比人工快、覆盖面广，但别全信（幻觉），关键问题人工复核。
- 可结合静态分析工具（SonarQube）+ AI 审查。

### 2.3 测试

- 生成单元测试/集成测试。
- 根据代码自动找边界情况。
- 跑测试失败让 AI 分析原因修。

### 2.4 文档

- 生成注释/API 文档/README。
- 代码解释（读不懂的老代码）。
- 技术方案/设计文档起草。

### 2.5 排障

- 贴报错让 AI 分析原因给方案。
- 日志分析、性能排查。
- 配合 Trace/日志定位。

### 2.6 重构/迁移

- 大规模重构（如升级框架版本）。
- 代码迁移（Java 8->17、单体->微服务）。
- AI + 子 Agent 并行处理多文件（13 章 Workflow）。

### 2.7 提效心法

- **描述即生产力**：Prompt 写得好，产出质量高（03 章）。
- **Review 为主**：AI 生成是初稿，人是最终责任。
- **小步快跑**：分小任务给 AI，别一次要整个系统。
- **建立项目规范**：用 CLAUDE.md/规则文件让 AI 遵循项目约定。
- **迭代修正**：不对就反馈让 AI 改（自我修正，13 章）。

> 💡 **面试金句**：AI 提效核心是「描述即生产力 + Review 为主 + 小步快跑」。AI 生成是初稿，人是最终责任。建立项目规范（CLAUDE.md）让 AI 遵循约定，配合自我修正迭代。

## 三、MCP Server 开发实战 ★

### 3.1 为什么要开发 MCP Server

- 给团队/外部提供工具能力：写一次 MCP Server，Claude Code/Cursor/你的 Agent 都能用（12 章）。
- 把内部系统（Jira/CI/监控/内部 API）接入 AI。
- 标准化工具复用，M+N 变 M+N（04 章）。

### 3.2 MCP Server 暴露三类能力（呼应 06 章）

| 原语 | 含义 | 例子 |
|------|------|------|
| **Tools** | 可执行函数 | 查 Jira、触发 CI、查监控 |
| **Resources** | 可读数据 | 读配置、查文档 |
| **Prompts** | 预置模板 | 标准任务模板 |

### 3.3 Java 开发 MCP Server

```xml
<dependency>
    <groupId>io.modelcontextprotocol.sdk</groupId>
    <artifactId>mcp-spring-webflux</artifactId>
</dependency>
```

```java
// 思路：用 MCP SDK 暴露工具
@Service
public class JiraMcpServer {
    @Tool(description = "查询Jira工单状态")
    public String getTicketStatus(@ToolParam(description="工单号") String ticketId) {
        return jiraApi.getStatus(ticketId);
    }

    @Tool(description = "创建Jira工单")
    public String createTicket(@ToolParam(description="标题") String title,
                                @ToolParam(description="描述") String desc) {
        return jiraApi.create(title, desc);
    }
}
// 配置成 MCP Server（stdio 或 HTTP 传输），Claude Code/Cursor 连接即用
```

- 用 Spring AI 的 MCP Server SDK，@Tool 注解的工具自动暴露为 MCP Tools。
- 传输：stdio（本地）或 Streamable HTTP（远程，06 章）。

### 3.4 MCP Server 开发要点

- **工具描述清晰**：和普通 @Tool 一样，描述要清楚（12 章）。
- **参数简单**：少参数+枚举约束。
- **错误可读**：失败返回可读错误。
- **权限最小**：只暴露必要能力，危险操作要服务端鉴权。
- **测试**：连上 Claude Code 实测工具是否被正确调用。

### 3.5 典型自建 MCP Server

- **Jira/项目管理**：查/建工单。
- **CI/CD**：触发构建、查部署状态。
- **监控**：查 Prometheus/SkyWalking 指标。
- **内部 API**：接内部服务。
- **数据库**：查数据（只读+白名单）。

## 四、自建团队 AI 工具链 ★

### 4.1 为什么要自建

- 通用 AI 助手不懂团队规范/内部系统。
- 自建工具链让 AI 懂团队：项目规范、内部 API、代码模板、知识库。

### 4.2 团队 AI 工具链组成

```
[项目规范] CLAUDE.md/规则文件 -- 让AI遵循团队约定
[内部知识] RAG知识库 -- 团队文档/决策/经验
[内部工具] MCP Server -- 接Jira/CI/监控/内部API
[代码模板] Skill/模板 -- 团队标准代码结构
[评测] -- 团队场景评测集
```

### 4.3 落地步骤

1. **建项目规范文件**：CLAUDE.md 定义代码规范/架构约定/常用命令。
2. **接入内部知识**：团队文档建 RAG 知识库。
3. **开发 MCP Server**：接内部系统（Jira/CI/监控）。
4. **沉淀 Skill**：把常用工作流打包成 Skill（13 章）。
5. **评测**：建团队场景评测集，验证 AI 产出质量。
6. **推广**：团队统一工具+规范+培训。

### 4.4 价值

- 新人上手快（AI 懂团队规范）。
- 代码一致性（遵循约定）。
- 经验沉淀（知识库+Skill 复用）。
- 效率提升（自动化样板任务）。

## 五、AI 提效的工程纪律

### 5.1 别盲目信任

- AI 生成是初稿，必须 review。
- 幻觉（编 API/库）、过时代码（训练截止后的 API）、安全漏洞都要防。
- 关键代码/安全相关代码人工复核。

### 5.2 安全红线

- **别让 AI 看敏感数据**：密钥/密码/PII 不贴给外部 AI。
- **代码外发合规**：公司代码能否贴外部 AI 要合规确认（数据泄露风险）。
- **私有化**：敏感场景用私有化部署的 AI 助手（16 章）。
- **生成代码审核**：AI 生成代码过安全扫描（依赖漏洞/注入）。

### 5.3 版本控制

- AI 生成代码也要走 review/PR。
- 小步提交，便于回滚。
- 别一次性让 AI 改几百行没法 review。

### 5.4 持续学习

- AI 工具迭代快，关注新特性（MCP/Skill/新模型）。
- 沉淀团队 Prompt/Skill/工具。
- 评测 AI 产出，持续优化。

## 六、生产踩坑

1. **盲目信任 AI 代码**：不 review 直接用，幻觉 API/安全漏洞。必须人工 review。
2. **贴敏感数据给外部 AI**：密钥/PII 泄露。脱敏或私有化。
3. **一次改太多**：几百行没法 review。小步快跑分提交。
4. **没项目规范**：AI 不懂团队约定乱写。建 CLAUDE.md。
5. **MCP Server 权限过大**：暴露危险能力。最小权限+鉴权。
6. **不评测 AI 产出**：不知道好不好。建团队评测集。
7. **代码外发不合规**：公司代码贴外部 AI。合规确认。

## 七、常见面试题

1. **Claude Code / Cursor / Copilot 区别？怎么选？**
   都是 LLM+Harness+工具循环的编码 Agent。Claude Code 终端原生、Harness 工程化强、MCP 生态完整，适合复杂工程；Cursor IDE 优先、Composer 多文件改，适合日常编码；Copilot 企业集成好。看团队习惯和任务复杂度选。

2. **怎么用 AI 提效开发？**
   场景：写代码（需求->初稿->review）、Code Review、测试生成、文档、排障、重构迁移。心法：描述即生产力、Review 为主（AI 是初稿人负责）、小步快跑、建项目规范（CLAUDE.md）、迭代修正。

3. **为什么开发 MCP Server？**
   给团队/外部提供工具能力，写一次 Claude Code/Cursor/Agent 都能用。把内部系统（Jira/CI/监控）接入 AI。标准化复用 M×N 变 M+N。Java 用 MCP SDK @Tool 暴露。

4. **MCP Server 怎么开发？**
   用 MCP SDK（Java 的 spring-ai-mcp-server），@Tool 注解的工具自动暴露为 MCP Tools，配 stdio/HTTP 传输。要点：描述清晰、参数简单、错误可读、权限最小、连 Claude Code 实测。

5. **自建团队 AI 工具链怎么做？**
   建项目规范（CLAUDE.md）+ 内部知识 RAG + 内部工具 MCP Server + 代码模板 Skill + 团队评测集。让 AI 懂团队规范/内部系统，新人上手快、代码一致、经验沉淀。

6. **用 AI 写代码有什么安全风险？**
   盲目信任（幻觉 API/安全漏洞）、贴敏感数据（密钥/PII 泄露）、代码外发不合规。防护：人工 review、脱敏/私有化、生成代码过安全扫描、走 PR/review。

7. **AI 生成代码要不要 review？**
   必须要。AI 生成是初稿，可能幻觉（编 API）、过时（训练截止后 API 变）、安全漏洞。人是最终责任，关键/安全代码人工复核，走 PR。

8. **怎么让 AI 遵循团队代码规范？**
   建项目规范文件（CLAUDE.md）定义代码规范/架构约定/常用命令，AI 读取遵循。配合 Skill 沉淀标准代码结构，RAG 注入团队决策，评测集验证产出。

## 八、资料勘误与重点提醒

1. **「AI 编码助手会取代程序员」是误区**：资料常渲染取代焦虑。实际是提效工具，AI 生成初稿人 review 决策，复杂架构/业务理解/责任承担仍是人。会驾驭 AI 的程序员替代不会的。
2. **「AI 代码直接用」是坑**：资料示例常默认 AI 代码对。实际有幻觉/过时/安全漏洞，必须 review。盲目信任是事故源。
3. **「贴代码给 AI 没事」有合规风险**：资料少提。公司代码贴外部 AI 可能泄露知识产权/敏感信息，要合规确认，敏感场景私有化。
4. **MCP Server 开发安全少强调**：资料讲 MCP 开发常不强调权限最小+鉴权。暴露危险能力（删数据/写操作）给 AI 是安全风险。
5. **团队工具链评测少提**：资料讲建工具链不讲评测。没评测不知道 AI 产出质量，要建团队场景评测集。
6. **项目规范价值少强调**：资料讲 AI 提效少提 CLAUDE.md/规范文件。这是让 AI 懂团队约定的关键，不建规范 AI 乱写。
