# RAG 与向量检索

> RAG（Retrieval-Augmented Generation，检索增强生成）是大模型落地企业最常用的架构。它解决三大痛点：幻觉、私有知识、时效性。本章覆盖 RAG 全流程、演进、向量数据库、GraphRAG、LlamaIndex、评测与上下文压缩。

---

## 一、核心概念

### 1.1 为什么需要 RAG

直接用 LLM 的三大问题：

| 问题 | 表现 | RAG 如何解决 |
|------|------|--------------|
| **幻觉** | 编造事实 | 把真实检索到的片段作为依据，要求「只基于上下文回答」 |
| **私有知识缺失** | 不懂企业内部文档/代码 | 离线把私有文档向量化入库，在线检索注入 |
| **时效性差** | 训练截止后的新知识不知道 | 检索实时/最新数据源 |

> ⚠️ RAG 不是「替代微调」，二者常互补：微调适合调风格/格式/领域语言习惯，RAG 适合注入可变的事实知识。

### 1.2 RAG 标准三阶段流程

```
【离线索引阶段】            【在线检索阶段】          【生成阶段】
文档 → 切分 → Embedding → 存入向量库    Query → (改写) → Embedding → 向量检索 → Rerank → 拼接 Prompt → LLM 生成
```

1. **索引（Indexing）**：文档加载 → 文本切分（Chunking）→ 向量化（Embedding）→ 存入向量数据库。
2. **检索（Retrieval）**：用户 Query 向量化 → 在库中做相似度检索（Top-K）→ 可选 Rerank 重排。
3. **生成（Generation）**：把检索到的片段拼进 Prompt（`请基于以下资料回答：{context}`）→ LLM 生成。

### 1.3 RAG 三代演进

| 代际 | 名称 | 特点 | 痛点 |
|------|------|------|------|
| 第一代 | **Naive RAG** | 简单「检索-拼接-生成」 | 切分粗糙、检索不准、无优化 |
| 第二代 | **Advanced RAG** | 检索前（查询改写/HyDE）+ 检索后（Rerank/过滤）优化 | 仍是固定流水线 |
| 第三代 | **Modular RAG** | 模块化、可编排（路由/记忆/自反思/多跳检索），可增可减 | 架构复杂 |

Advanced RAG 的常见优化点：
- **检索前（Pre-retrieval）**：查询改写、查询扩展、HyDE（让模型先「假设一个答案」再检索）、查询路由（决定查哪个库）。
- **检索后（Post-retrieval）**：Rerank 重排（用 Cross-Encoder 精排 Top-K）、去重、按相关度过滤、上下文压缩。

## 二、关键技术点

### 2.1 Chunking（文本切分）

切分质量直接决定检索质量。常见策略：
- **固定长度切分**：简单但可能切断语义。需配合**重叠（Overlap）**保留上下文。
- **按语义切分**：按段落/标题/Markdown 结构切，语义更完整。
- **递归切分**：先按大结构，超长再递归细分（LangChain 的 `RecursiveCharacterTextSplitter`）。
- **语义切分（Semantic Chunking）**：按 Embedding 相似度变化点切分，切在语义跳变处。
- **父子/小块检索大块返回（Small-to-Big）**：用小块精确匹配，返回其所属大块给 LLM（兼顾检索精度与上下文完整）。

### 2.2 Embedding（向量化）

- 把文本映射为高维向量（如 768/1536/3072 维），使「语义相近 → 向量相近」。
- 相似度度量：**余弦相似度**（最常用）、点积、欧氏距离。
- 主流 Embedding 模型：OpenAI text-embedding-3、BGE（智源，中文强）、Cohere、Jina、各开源模型。
- ⚠️ Embedding 模型和 LLM 是**两个独立模型**，可分别选型。

### 2.3 向量数据库（选型是高频面试题）

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|---------|
| **Milvus** | 专用 | 开源、云原生、支持多种索引(IVF/HNSW)、十亿级 | 大规模生产、私有化部署 |
| **Faiss** | 库 | Meta 开源库，非服务，纯内存高性能 | 原型/单机高性能检索 |
| **Pinecone** | SaaS | 全托管、易用 | 不想运维的团队 |
| **Qdrant** | 专用 | Rust 实现、过滤性能强、轻量 | 需要丰富元数据过滤 |
| **Weaviate** | 专用 | 内置混合检索/模块化 | 需要混合检索开箱即用 |
| **Chroma** | 轻量 | 嵌入式、开发友好 | 原型/小项目 |
| **pgvector** | 插件 | PostgreSQL 扩展 | 已有 PG、不想引入新组件 |

**核心索引算法**（决定检索速度与精度）：
- **HNSW**（Hierarchical Navigable Small World）：基于图，查询快、精度高、内存大，是当前主流。
- **IVF**（Inverted File）：基于倒排聚簇，可结合 PQ 乘积量化压缩内存，适合超大规模。
- **Flat**：暴力精确检索，只适合小数据。

> 面试常问「HNSW 和 IVF 怎么选」：要精度和速度选 HNSW（吃内存）；要大规模+省内存选 IVF+PQ。

### 2.4 检索方式

- **稠密检索（Dense）**：Embedding 向量相似度，擅长语义匹配。
- **稀疏检索（Sparse）**：BM25 等关键词检索，擅长精确词匹配（人名/型号/代码标识符）。
- **混合检索（Hybrid）**：Dense + Sparse 融合（如 RRF Reciprocal Rank Fusion），取长补短——这是生产推荐做法。

### 2.5 Rerank 重排

- 检索阶段用轻量 Embedding 取 Top-50（召回），再用**Cross-Encoder 重排模型**（如 bge-reranker、Cohere Rerank）对 Query-Document 两两精排取 Top-5。
- Cross-Encoder 比 Bi-Encoder 准但慢（不能预计算），所以放在检索后小范围精排。

## 三、进阶 RAG 架构

### 3.1 Self-RAG / CRAG（自适应/纠错 RAG）

- **Self-RAG**：模型自己判断「要不要检索」「检索结果相不相关」「回答支不支持」，按需检索、自我批判。
- **CRAG（Corrective RAG）**：检索后评估质量，质量低则改写查询或回退到 web 搜索，质量高才用。

### 3.2 RAPTOR（递归摘要检索）

把文档做多层级摘要建树，检索时可同时命中「细节段落」和「高层摘要」，适合需要跨文档整体理解的问题。

### 3.3 GraphRAG（Microsoft，图增强 RAG）★

- **痛点**：传统 RAG 是「局部检索」，回答「全局性/总结性」问题（如「这份文档主要讲了什么主题」）很差，因为它只捞片段。
- **GraphRAG 思路**：先用 LLM 从文档抽取**实体和关系构建知识图谱**，再对图做社区聚类（Leiden 算法）生成各社区摘要。查询时：
  - **Global Search**：用社区摘要回答全局/总结类问题。
  - **Local Search**：从相关实体出发沿图扩展回答具体问题。
- **代价**：构建图谱很贵（大量 LLM 调用），但构建一次可多次查询。

### 3.4 LightRAG

GraphRAG 的轻量化替代，构建成本更低，支持增量更新，融合图结构与向量检索。

### 3.5 Agentic RAG

把 RAG 升级为 Agent：模型自主决定查什么、查几次、要不要换库、要不要再检索，多跳检索+反思。本质是 RAG + ReAct/Reflexion。

## 四、RAG 框架

- **LlamaIndex**：专注「数据-LLM」连接的框架，RAG 索引/检索/查询引擎抽象完善，文档处理能力强。
- **LangChain**：通用 LLM 应用框架，RAG 是其重要组成，灵活但较重。
- **Haystack**（deepset）：生产级 RAG 流水线框架，流水线（Pipeline）抽象清晰。
- **RAGAS**：**RAG 评测框架**（非生成框架），见下。

> 关于用户列表中的 `AINDEX`、`LLA`：`AINDEX` 最可能指 **LlamaIndex**（RAG 框架），`LLA` 可能指 **LlamaIndex/LightRAG** 或 **LLM-as-a-Judge 评测**，已在对应章节覆盖，待用户确认后细化。

## 五、RAG 评测（RAGAS）

不能只靠感觉，要有量化指标。**RAGAS** 提出四维评测：

| 指标 | 含义 | 衡量 |
|------|------|------|
| **Faithfulness（忠实度）** | 回答是否忠于检索内容（不编造） | 越高越少幻觉 |
| **Answer Relevancy（答案相关性）** | 回答是否切题 | 越高越答非所问越少 |
| **Context Precision（上下文精确率）** | 检索的片段是否都相关 | 越高检索越准 |
| **Context Recall（上下文召回率）** | 所需信息是否都被检索到 | 越高检索越全 |

> 面试金句：**RAG 的瓶颈往往不在生成而在检索**。检索准了，生成质量自然上来。

## 六、上下文压缩（Context Compression）

> 用户知识点之一。当检索回来的上下文太长，需压缩以省 token、提速度、降噪声。

- **为什么需要**：LLM 上下文窗口有限且越长越贵越慢，检索回来几十段文档可能超限或稀释注意力。
- **方法**：
  - **抽取式**：只保留与 Query 最相关的句子（如 LLMLingua 系列用小模型打分删低相关 token，可压到原长 1/10）。
  - **生成式（摘要）**：用 LLM 对检索片段做摘要再注入。
  - **过滤式**：去重、去低分、按相关度截断。
- **位置**：在检索后、生成前插入一个压缩/重排模块。

## 七、常见面试题

1. **RAG 和微调怎么选？**
   知识频繁变、需可溯源、数据量大 → RAG；要改风格/格式/领域术语习惯、有稳定高质量指令对 → 微调；二者常组合。

2. **RAG 检索不准怎么优化？**
   优化切分（语义切分/父子块）、改进 Embedding、查询改写/HyDE、混合检索、加 Rerank、调 Top-K、加元数据过滤。

3. **向量检索为什么还要 Rerank？**
   Embedding 检索是 Bi-Encoder，快但粗（Query/Doc 分别编码再算相似度）；Rerank 用 Cross-Encoder 把 Query 和 Doc 拼一起精排，更准但慢，故只小范围精排。

4. **GraphRAG 解决了什么传统 RAG 解决不了的问题？**
   全局/总结类问题。传统 RAG 只能捞局部片段，无法回答「这批文档整体讲了什么」；GraphRAG 用社区摘要回答全局问题。

5. **HNSW 和 IVF 索引怎么选？**
   要速度精度选 HNSW（内存大）；超大规模要省内存选 IVF+PQ（牺牲少量精度）。

6. **RAGAS 的四个指标分别衡量什么阶段？**
   Context Precision/Recall 衡量检索阶段，Faithfulness/Answer Relevancy 衡量生成阶段。

7. **检索回来的上下文太长怎么办？**
   上下文压缩（LLMLingua 抽取压缩/LLM 摘要）、Rerank 截断、父子块只返回精排 Top-N、按相关度过滤。
