# 04 - 结构化输出与函数调用（Function Calling）

> 这是 Agent 从「会聊天」到「会动手」的分水岭。Function Calling 让模型能调用外部工具（查数据库、发请求、调 API），是几乎所有 Agent 的基石。本章讲透原理 + Java 实战（Spring AI / LangChain4j）+ 与 MCP 的关系。面试必考。

---

## 一、为什么需要 Function Calling

### 1.1 没有工具时模型的局限

- 模型只能基于训练数据「说话」，不能：查实时数据、算精确数学、调外部系统、访问私有数据库。
- 早期做法：用正则解析模型输出，提取「要调哪个函数」。脆弱--模型输出格式不稳定，解析经常失败。

### 1.2 Function Calling 解决什么

- 模型厂商在**模型层**提供能力：模型经过训练，能输出**结构化的工具调用请求**（函数名 + 参数 JSON），而不是自由文本。
- 框架拦截这个结构化请求，执行真实工具，把结果喂回模型。
- 这样模型就「长出手」了：能查、能算、能调 API。

> 💡 **面试金句**：Function Calling 是模型层能力--模型经过训练能输出结构化的「函数名+参数」调用请求，框架执行后把结果回灌。它让 LLM 从「只能说话」变成「能动手」，是 Agent 的基石。

## 二、Function Calling 完整流程 ★ 必考

```
1. 开发者定义工具：函数名、描述、参数 JSON Schema
2. 把工具定义随请求发给模型（作为 functions/tools 字段）
3. 模型推理，决定是否调工具：
   a. 不需要 -> 直接输出文本回答
   b. 需要 -> 输出结构化工具调用：{name:"get_weather", args:{city:"上海"}}
4. 框架拦截工具调用，执行真实函数，拿到结果
5. 把结果作为 tool/observation 消息塞回上下文
6. 模型基于结果继续推理，输出最终答案（或继续调下一个工具）
```

### 2.1 关键理解

- **模型不执行工具**：模型只是「说」要调什么，真正执行的是框架/宿主。模型是大脑，框架是手脚。
- **结果回灌是循环的引擎**：工具结果不是给用户的，是给模型继续推理的。这就是 Agent Loop 的雏形（详见 09 章）。
- **模型决定调不调、调哪个**：这是「控制权交给模型」的体现，也是 Agent 非确定性的来源。

### 2.2 一次调用示例（协议层）

```json
// 请求
{
  "model": "qwen-plus",
  "messages": [{"role":"user","content":"上海今天天气怎么样"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "查某城市天气",
      "parameters": {"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}
    }
  }]
}

// 模型返回（不直接答，而是要调工具）
{
  "role":"assistant",
  "tool_calls":[{"id":"call_1","type":"function","function":{"name":"get_weather","arguments":"{\"city\":\"上海\"}"}]
}

// 框架执行 get_weather("上海")，把结果塞回去
{"role":"tool","tool_call_id":"call_1","content":"晴，35℃"}

// 模型基于结果输出最终答案
"上海今天晴，35℃，注意防暑。"
```

## 三、Java 实战：Spring AI Tool Calling ★

### 3.1 声明式 @Tool（最简，推荐）

```java
@Component
public class WeatherTools {
    @Tool(description = "查询指定城市的实时天气")
    public String getWeather(String city) {
        // 实际调天气API
        return weatherApi.query(city);
    }

    @Tool(description = "查询订单状态")
    public Order getOrder(@ToolParam(description="订单号") String orderId) {
        return orderService.getById(orderId);
    }
}

@Service
public class AgentService {
    private final ChatClient chatClient;
    private final WeatherTools tools;

    public String ask(String question) {
        return chatClient.prompt()
            .user(question)
            .tools(tools)              // 注册工具
            .call()
            .content();                // 框架自动处理「调用-执行-回灌」循环
    }
}
```

- `@Tool` 注解声明工具，Spring AI 自动生成 JSON Schema 发给模型。
- `tools(tools)` 注册后，框架**自动**完成「模型要调工具->执行->结果回灌->模型继续」的循环，你只管拿最终结果。

### 3.2 方法返回对象（结构化）

```java
@Tool(description = "查订单")
public Order getOrder(String orderId) { ... }   // Order 会被 Schema 化，模型返回的参数自动绑定
```

- 返回复杂对象，Spring AI 序列化后回灌给模型，模型能理解结构化结果。

### 3.3 LangChain4j 的 @Tool

```java
class WeatherTools {
    @Tool("查询城市天气")
    String getWeather(@P("城市名") String city) { return ...; }
}

WeatherTools tools = new WeatherTools();
ChatLanguageModel model = OpenAiChatModel.builder()...build();

// AiServices 自动把 @Tool 注册，处理调用循环
Assistant agent = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .tools(tools)
    .build();

String answer = agent.chat("上海天气");  // 自动调工具
```

- LangChain4j 用 `AiServices` + `@Tool`，声明式，和 Spring AI 思路一致。

### 3.4 手动处理调用循环（理解原理，面试能讲）

```java
// 伪代码：手写 Function Calling 循环
List<Message> messages = new ArrayList<>();
messages.add(UserMessage.of(question));

while (true) {
    ChatResponse resp = chatModel.call(messages, tools);   // 带工具调用
    AssistantMessage am = resp.getAssistantMessage();

    if (am.hasToolCalls()) {
        // 模型要调工具
        for (ToolCall tc : am.toolCalls()) {
            String result = execute(tc.name(), tc.args());  // 执行真实函数
            messages.add(ToolMessage.of(tc.id(), result)); // 结果回灌
        }
        continue;  // 继续循环，让模型基于结果推理
    } else {
        return am.text();  // 没有工具调用，输出最终答案
    }
}
```

- 这就是 Agent Loop 的核心（09 章详解）。理解这段，Agent 原理就通了。

## 四、并行工具调用 ★ 进阶

### 4.1 什么是并行调用

- 较新模型支持一次返回**多个**工具调用（如「查上海天气」+「查北京天气」一起调）。
- 框架并行执行，减少往返延迟。

### 4.2 处理

- 模型返回的 `tool_calls` 是数组，框架并发执行后，**所有结果一起回灌**再给模型。
- Spring AI / LangChain4j 较新版本自动支持并行。
- ⚠️ 注意工具的线程安全（并行调同一工具可能并发问题）。

### 4.3 适用与限制

- 适用：多个独立查询（查多个订单、查天气+查股票）。
- 不适用：有依赖的调用（B 依赖 A 的结果，不能并行）。
- 模型要支持（老模型只串行）。

## 五、结构化输出 vs Function Calling

这两个常被混，区分清楚：

| 维度 | Structured Output | Function Calling |
|------|-------------------|-----------------|
| 目的 | 让模型输出**结构化数据** | 让模型**调工具** |
| 是否执行 | 不执行，只输出结构 | 框架执行真实函数 |
| 形式 | 给 JSON Schema，输出符合 Schema 的数据 | 输出「函数名+参数」调用请求 |
| 关系 | Function Calling 的参数本身就是 Structured Output |

- 联系：Function Calling 的参数传递用 Structured Output 保证格式。
- Spring AI 的 `entity(Class)` 是 Structured Output；`@Tool` 是 Function Calling。

## 六、Function Calling vs MCP ★ 高频

> 这是 2025 年最高频的 AI 面试题之一，必须答透。

### 6.1 区别

| 维度 | Function Calling | MCP |
|------|------------------|-----|
| 层次 | **模型层**（厂商特性） | **协议层**（开放标准） |
| 作用 | 模型输出结构化调用 | 标准化工具发现/调用/通信 |
| 复用 | 每个应用各自集成工具 | 工具写一次（MCP Server）处处可用 |
| 谁提 | 各模型厂商 | Anthropic（2024.11） |

### 6.2 关系（关键金句）

> 💡 **MCP 和 Function Calling 不冲突，是协议层和模型层的关系**：MCP Server 暴露的工具，最终通过 Function Calling 让模型调用。MCP 解决「工具怎么被发现、怎么通信标准化」，Function Calling 解决「模型怎么输出调用」。完整链路：`模型 --(Function Calling)--> Host --(MCP)--> MCP Server --> 真实工具`。

### 6.3 为什么要 MCP（M×N 问题）

- 没 MCP：M 个 Agent 框架 × N 个工具，要写 M×N 份集成。
- 有 MCP：Agent 实现 MCP Client，工具实现 MCP Server，变 M+N，即插即用。类比「AI 应用的 USB-C」。

### 6.4 MCP 架构（简版，详见 12 章）

```
Host（Claude Code / 你的Agent）
  └─ Client（每个Server一个）
        │ MCP协议
        ▼
    MCP Server（文件系统/数据库/GitHub...）  暴露 Tools/Resources/Prompts
```

## 七、工具设计工程要点 ★

### 7.1 描述即接口

- 模型靠 `description` 选工具。描述不清就会选错或不用。
- ❌ `@Tool(description = "查询")` -- 查什么？模型懵。
- ✅ `@Tool(description = "根据订单号查询订单的物流状态，返回当前位置和预计送达时间")`。

### 7.2 参数要简单

- 参数越少越好，能默认就默认。复杂参数模型容易填错。
- 用枚举/约束（`@ToolParam`）限制取值，减少出错。
- 参数也要有 description，模型才知道填什么。

### 7.3 错误要可读

- 工具失败别返回 `null` 或 stacktrace，要返回**可读的错误**，让模型能据此修正重试。
- ❌ 抛异常让循环崩。
- ✅ 返回 `{"error":"订单号不存在，请确认订单号格式（如 ORD 开头）"}`，模型会修正参数重试。

### 7.4 工具不宜过多

- 工具太多模型会选错（注意力稀释）。
- 按场景分组、按需加载（Skill 机制，见 05 章/07 章）。
- 经验：单次暴露的工具不超过 10~20 个，多了要分组或路由。

## 八、生产踩坑

1. **模型不调工具**：检查工具 description 是否清晰、参数是否太复杂、模型是否支持 Function Calling（小模型可能不支持）。
2. **参数填错**：参数描述不清或类型复杂。加 `@ToolParam(description=...)`、用枚举、简化参数。
3. **循环不终止**：模型反复调同一工具。加最大步数兜底（详见 09 章）、检测重复调用。
4. **工具异常导致崩**：工具要 catch 异常返回可读错误，别让异常冒泡打断循环。
5. **并行调用线程安全**：工具可能被并发调，注意共享状态安全（用线程安全集合/无状态）。
6. **工具结果太大**：返回几十 KB 的 JSON 灌回上下文，费 token 还稀释注意力。工具结果要裁剪（只返回关键字段）。
7. **权限缺失**：危险工具（删数据/发钱/外发）必须加确认（人在环），不能让模型自主执行。

## 九、常见面试题

1. **Function Calling 的流程是什么？**
   开发者定义工具（名/描述/参数 Schema）-> 随请求发给模型 -> 模型决定是否调，要调则输出「函数名+参数」-> 框架执行真实函数 -> 结果作为 tool 消息回灌上下文 -> 模型基于结果继续推理或给最终答案。模型不执行工具，框架执行。

2. **Function Calling 和 Structured Output 什么关系？**
   Structured Output 是让模型输出结构化数据（不执行），Function Calling 是让模型调工具（框架执行）。联系：Function Calling 的参数传递用 Structured Output 保证格式。Spring AI 的 entity(Class) 是 Structured Output，@Tool 是 Function Calling。

3. **Function Calling 和 MCP 什么关系？冲突吗？**
   不冲突，是模型层和协议层关系。Function Calling 是模型能力（输出结构化调用），MCP 是协议标准（工具发现/调用/通信标准化）。MCP Server 暴露的工具最终靠 Function Calling 让模型调。MCP 把 M×N 集成变 M+N。

4. **模型为什么有时不调工具？**
   工具 description 不清晰、参数太复杂、模型能力不足（小模型不支持 FC）、或模型判断不需要调。排查：优化描述、简化参数、换支持 FC 的模型。

5. **并行工具调用怎么处理？有什么限制？**
   模型一次返回多个 tool_calls，框架并行执行后所有结果一起回灌。限制：只适合独立调用（有依赖的不能并行）、模型要支持、注意工具线程安全。Spring AI/LangChain4j 新版自动支持。

6. **工具太多模型选错怎么办？**
   按场景分组、按需加载（Skill 机制）、描述写清晰、用路由 Agent 先分流。单次暴露工具建议不超过 10~20 个。

7. **工具失败怎么处理？**
   别返回 null 或抛异常崩循环，返回可读错误（如「订单号不存在，格式应为 ORD 开头」），让模型据错误修正参数重试。这是 Agent 自我修正的基础。

8. **你项目里怎么用 Function Calling 的？**
   （参考）用 Spring AI @Tool 声明工具（查订单/查库存/查天气），ChatClient.tools() 注册，框架自动处理调用-执行-回灌循环。危险工具（下单/退款）加人在环确认。工具结果裁剪只返回关键字段控 token。

## 十、资料勘误与重点提醒

1. **「Function Calling 是模型执行函数」是错的**：模型只输出「要调什么」，真正执行的是框架/宿主。资料偶尔表述含糊导致误解。模型是大脑，框架是手脚。
2. **「Structured Output = Function Calling」是混淆**：两者不同。Structured Output 只输出结构化数据不执行，Function Calling 是调工具由框架执行。联系是 FC 的参数用 Structured Output 保证格式。
3. **「MCP 取代 Function Calling」是误解**：资料或营销话术可能暗示 MCP 替代 FC。实际是互补：MCP 是协议层，FC 是模型层，MCP 工具仍靠 FC 让模型调。
4. **「工具越多越强大」是误区**：工具过多模型选错（注意力稀释）。要分组/按需加载。单次暴露 10~20 个为宜。
5. **「并行调用总是更快」不严谨**：只对独立调用快，有依赖的不能并行（B 需要 A 的结果）。资料常不提这个限制。
6. **小模型不一定支持 FC**：资料示例默认模型支持。实际小模型/老模型可能不支持 Function Calling 或支持不好，生产要选支持 FC 的模型（如 qwen-plus、deepseek-chat 等）。
