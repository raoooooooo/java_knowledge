# 虚拟机类加载机制

> 📌 **一句话理解**：JVM把".class"字节码文件从磁盘加载到内存，并对数据进行校验、解析和初始化，最终形成可以被JVM直接使用的Java类型，这个过程就是**类加载机制**。

---

## 核心概念

### 一、先搞懂：类加载到底在做什么？

**举个生活化的例子：**

想象你开了一家餐厅：
- **菜谱配方** = Class文件（存在磁盘上，只是一张纸）
- **餐厅后厨** = JVM内存
- **厨师培训** = 类加载过程

餐厅开门前，你需要：
1. 把菜谱从保险柜里拿出来 → **加载**
2. 确认菜谱是真的、没有写错 → **验证**
3. 准备好所有食材的初始分量 → **准备**
4. 把"油"、"盐"这些名称对应到真实的油瓶、盐罐 → **解析**
5. 厨师记住所有菜的做法，随时可以接单 → **初始化**

完成这5步，餐厅才算真正"准备好营业"，可以开始做菜（创建对象、调用方法）了。

**核心要点：**
> ✅ 类加载是在**运行期间**完成的，不是编译期！
> ✅ 不是一次性把所有类都加载，而是"用到的时候才加载"（懒加载）
> ✅ 同一个类只会被加载一次，加载后会被缓存起来

---

### 二、类加载的时机：什么时候触发加载？

#### 1. 类的生命周期

```
[加载] → [验证] → [准备] → [解析] → [初始化] → [使用] → [卸载]
        └───────────────────────────┘
                连接阶段
```

**说明：**
- 这几个阶段是**按顺序开始**，但不一定是按顺序完成（可能交叉进行）
- 解析阶段在某些情况下可以在初始化之后开始（为了支持Java的动态绑定）

#### 2. 触发初始化的5种场景（有且仅有这5种！）

这就是著名的**"有且仅有"原则**，面试必背！

| 场景 | 说明 | 举例 |
|------|------|------|
| **1. new对象** | 使用new关键字实例化对象 | `new Student()` |
| **2. 访问静态成员** | 读取或设置类的静态字段（被final修饰、编译期已把结果放入常量池的静态字段除外） | `Student.maxAge` |
| **3. 调用静态方法** | 调用类的静态方法 | `Student.sayHello()` |
| **4. 反射** | 使用`java.lang.reflect`包的方法对类进行反射调用 | `Class.forName("Student")` |
| **5. 初始化子类** | 初始化一个类时，如果父类还没初始化，先初始化父类 | `class Son extends Father`，new Son()会先初始化Father |

**补充：** 对于主类（包含main方法的那个类），JVM启动时会自动初始化它。

#### 3. 重要：什么情况不会触发初始化？（常考）

**场景1：通过子类引用父类的静态字段，只会触发父类初始化，不会触发子类初始化**
```java
// 父类
class Father {
    public static int value = 123;
    static {
        System.out.println("Father初始化了！");
    }
}

// 子类
class Son extends Father {
    static {
        System.out.println("Son初始化了！");
    }
}

// 测试
public static void main(String[] args) {
    System.out.println(Son.value);  // 只会打印"Father初始化了！"，不会打印Son的
}
```

**结论：** 对于静态字段，只有直接定义这个字段的类才会被初始化。

---

**场景2：通过数组定义来引用类，不会触发类的初始化**
```java
public static void main(String[] args) {
    Student[] students = new Student[10];  // 不会触发Student的初始化
}
```

**说明：** 这里只是创建了一个数组对象，数组的类型是`[LStudent`，这是JVM自动生成的、直接继承于Object的类，不是Student类本身。

---

**场景3：访问类的静态常量（final + static + 编译期确定）**
```java
class Const {
    public static final String HELLO = "Hello World";  // 编译期就能确定
    static {
        System.out.println("Const初始化了！");
    }
}

public static void main(String[] args) {
    System.out.println(Const.HELLO);  // 不会触发Const的初始化！
}
```

**为什么？** 因为编译阶段，这个常量就被放到了调用类的常量池中，本质上调用类并没有直接引用到定义常量的类。

> ⚠️ 注意：如果常量的值**编译期无法确定**（比如`public static final int RANDOM = new Random().nextInt()`），还是会触发类初始化！

### 三、类加载的5个阶段详解 ⭐⭐⭐

#### 阶段1：加载（Loading）

**概念：** "加载"只是"类加载"的第一个阶段，别搞混了！

**加载阶段JVM做3件事：**
1. **定位**：通过类的全限定名（如 `com.example.Student`）找到对应的Class文件
2. **读取**：把Class文件的二进制字节流读入内存
3. **转换**：把字节流代表的静态存储结构转换成方法区的运行时数据结构，并在堆中生成一个代表这个类的`java.lang.Class`对象

**关键点：**
- Class文件不一定非得从磁盘读，可以来自：ZIP包（Jar/War）、网络、动态生成（动态代理）、数据库、加密文件等等
- 数组类比较特殊，它不是由类加载器创建的，而是由JVM直接在内存中动态构造的
- 加载阶段和连接阶段的部分内容是交叉进行的（比如字节码文件格式验证可能在加载还没完成就开始了）

**举个例子：**
你要做一道菜，第一步就是找到菜谱，然后把菜谱内容抄写到后厨的黑板上（方法区），然后再做一个菜谱目录卡片（Class对象）放在前台（堆），方便后续查找。

---

#### 阶段2：验证（Verification）

**概念：** 确保Class文件的字节流中包含的信息符合当前JVM的要求，并且不会危害JVM自身的安全。

**为什么需要验证？**
因为Class文件不一定是由Java源码编译来的，你可以自己用十六进制编辑器写一个Class文件，如果JVM不校验，直接执行恶意代码就会崩溃！

**验证的4个步骤：**

| 验证阶段 | 检查内容 | 举例 |
|----------|----------|------|
| **1. 文件格式验证** | 魔数是否正确、版本号是否支持、常量池类型是否合法等 | 检查前4字节是不是0xCAFEBABE |
| **2. 元数据验证** | 语义分析，是否符合Java语法规范 | 这个类有没有父类？final类被继承了吗？抽象方法有没有实现？ |
| **3. 字节码验证** | 最复杂，分析程序的数据流和控制流，确保方法是合法的 | 不会出现"操作数栈是int，但却按long类型来加载" |
| **4. 符号引用验证** | 确保解析动作能正常执行，类/方法/字段是否存在、访问权限是否合法 | 引用的类`com.example.A`真的存在吗？私有方法能被外部调用吗？ |

**举个例子：**
验证就像是餐厅的卫生检查：
1. 先看食材是不是真的（不是塑料做的）→ 文件格式验证
2. 食材本身有没有毒 → 元数据验证
3. 烹饪过程是不是安全（不会着火）→ 字节码验证
4. 用到的调料是不是都有 → 符号引用验证

**验证阶段可以关闭吗？**
可以！用 `-Xverify:none` 参数关闭大部分验证，加快类加载速度。但生产环境不建议关，除非你确认所有类都是安全的。

---

#### 阶段3：准备（Preparation）⭐

**概念：** 为**类变量**（static修饰的变量）分配内存，并设置初始值。

**两个关键点：**
1. **只给static变量分配内存**，不包括实例变量（实例变量会在对象实例化时随对象一起分配在堆中）
2. **初始值通常是"零值"**，不是代码中写的值！

**零值表：**

| 类型 | 零值 |
|------|------|
| int | 0 |
| long | 0L |
| float | 0.0f |
| double | 0.0d |
| boolean | false |
| char | '\\u0000' |
| 引用类型 | null |

**举个例子：**
```java
public static int value = 123;
```

准备阶段过后，`value`的值是 `0`，不是 `123`！
`123` 要等到**初始化阶段**才会被赋值。

**特殊情况：static + final 常量**
```java
public static final int VALUE = 123;
```

对于这种编译期就能确定的常量，准备阶段就会直接赋值为 `123`，不需要等到初始化阶段。

> 💡 面试常考：static变量和static final常量在准备阶段的区别！

---

#### 阶段4：解析（Resolution）

**概念：** JVM将常量池内的**符号引用**替换为**直接引用**的过程。

这两个术语听起来很抽象，用例子理解：

**符号引用 vs 直接引用**

| 引用类型 | 是什么 | 举例 |
|----------|--------|------|
| **符号引用** | 用一组符号来描述目标，只是一个"名字"，和JVM内存布局无关 | "我要找一个叫 `java/io/PrintStream.println` 的方法" |
| **直接引用** | 可以直接指向目标的指针、偏移量或者句柄，已经是内存地址了 | "那个方法在内存0x12345678的位置，直接跳过去就行" |

**举个生活化的例子：**
- 符号引用 = 你手机通讯录里的"张三"（只是一个名字，不是张三本人）
- 直接引用 = 张三的手机号/住址（可以直接找到他）

解析过程就是：把通讯录里的名字，翻译成实际的联系方式。

**解析主要针对4类符号引用：**
1. **类或接口**的解析
2. **字段**的解析
3. **类方法**的解析
4. **接口方法**的解析

**为什么需要解析？**
因为Class文件编译的时候，并不知道引用的类/方法/字段实际在内存的哪个位置，所以只能先用符号引用占位。等到类加载的时候，才知道具体的内存地址，这时候把符号替换成真正的内存地址。

---

#### 阶段5：初始化（Initialization）⭐

**概念：** 真正开始执行类中定义的Java程序代码（字节码），执行类构造器`<clinit>()`方法的过程。

#### 什么是`<clinit>()`方法？

`<clinit>()` = **class init**，是编译器自动生成的，不是你写的。

它由两部分内容合并而成：
1. 所有**static变量**的赋值动作
2. **静态代码块**（static{}）中的语句

**举个例子：**
```java
public class Test {
    static {
        value = 10;   // 可以赋值，定义在后面也可以！
        // System.out.println(value);  // 但不能访问（非法前向引用）
    }
    
    public static int value = 1;
    
    public static void main(String[] args) {
        System.out.println(value);  // 输出什么？答案：1
    }
}
```

**执行顺序：**
编译器按语句在源文件中出现的顺序收集，所以执行顺序是：
1. `value = 10` （静态代码块）
2. `value = 1` （变量赋值）
→ 最终value = 1

#### `<clinit>()`方法的重要特性：

| 特性 | 说明 |
|------|------|
| **自动执行** | 不需要手动调用，JVM自动调用 |
| **父类优先** | 子类的`<clinit>()`执行前，父类的`<clinit>()`已经执行完了 |
| **不是必须** | 类中没有static变量和静态代码块，就不会生成`<clinit>()` |
| **线程安全** | JVM保证`<clinit>()`在多线程环境下被正确加锁和同步，只有一个线程执行 |

**面试常考：** 为什么静态代码块只能访问定义在它之前的变量？

因为`<clinit>()`是按顺序执行的，如果静态代码块在变量定义之前，执行代码块时变量还没被赋值，所以只能赋值，不能读取。

---

#### 【重要补充】`<clinit>` vs `<init>`：类初始化 vs 对象初始化

很多人在这里混淆！**类加载的初始化阶段只处理static的东西**，实例变量和构造方法不归它管。

| 对比项 | `<clinit>()` 类构造器 | `<init>()` 实例构造器 |
|--------|---------------------|---------------------|
| **处理内容** | static变量 + 静态代码块 | 实例变量 + 构造代码块 + 构造方法 |
| **执行时机** | 类加载的初始化阶段 | 每次new对象的时候 |
| **执行次数** | 整个程序运行期间只执行**一次** | new几次就执行几次 |
| **执行顺序** | 父类`<clinit>()`先执行，子类`<clinit>()`后执行 | 同一个类中：实例变量赋值 → 构造代码块 → 构造方法<br>父子类中：父类完整`<init>()`先执行完，才执行子类`<init>()` |

**为什么这么设计？**
> static是"整个类共用"的，只需要准备一次；实例变量是"每个对象自己的"，每个对象创建时单独初始化。
>
> 类加载的时候还没有任何对象呢！怎么能给对象的属性赋值呢？

**完整执行顺序口诀：**
```
静态的先执行，父类先执行，只执行一次；
实例的后执行，每次new都执行。
```

### 四、类加载器（ClassLoader）⭐⭐⭐

#### 1. 什么是类加载器？

**概念：** 实现"通过类的全限定名来获取描述这个类的二进制字节流"这个动作的代码模块，就是**类加载器**。

简单说：类加载器就是负责把Class文件从各种地方（磁盘、网络、数据库等）读到内存里的那个"搬运工"。

#### 2. 两个重要概念

**概念1：类和类加载器共同确定唯一性**

> 🔴 **重要结论：** 比较两个类是否"相等"，只有在这两个类是由**同一个类加载器**加载的前提下才有意义。
>
> 哪怕是同一个Class文件，被不同的类加载器加载，这两个类也一定不相等！

**代码演示：**
```java
public class Test {
    public static void main(String[] args) throws Exception {
        // 自定义一个简单的类加载器
        ClassLoader myLoader = new ClassLoader() {
            @Override
            public Class<?> loadClass(String name) throws ClassNotFoundException {
                try {
                    String fileName = name.substring(name.lastIndexOf(".") + 1) + ".class";
                    InputStream is = getClass().getResourceAsStream(fileName);
                    if (is == null) {
                        return super.loadClass(name);
                    }
                    byte[] b = new byte[is.available()];
                    is.read(b);
                    return defineClass(name, b, 0, b.length);
                } catch (IOException e) {
                    throw new ClassNotFoundException(name);
                }
            }
        };

        Object obj = myLoader.loadClass("Test").newInstance();
        
        System.out.println(obj.getClass());                 // class Test
        System.out.println(obj instanceof Test);            // false！！！
        System.out.println(Test.class.getClassLoader());    // sun.misc.Launcher$AppClassLoader@...
        System.out.println(obj.getClass().getClassLoader());// Test$1@... （我们自定义的）
    }
}
```

**为什么`instanceof`返回false？**
因为虽然是同一个Class文件，但：
- `Test.class` 是由**系统类加载器**加载的
- `obj` 是由**我们自定义的类加载器**加载的
→ 两个来自不同类加载器的类，JVM认为它们是不同的类型！

---

**概念2：双亲委派模型（Parents Delegation Model）⭐⭐⭐**

这是Java中类加载器的默认工作模式，面试100%问！

#### 3. JVM中的三种类加载器

从JDK 1.2开始，Java一直保持着三层类加载器的架构：

```
                    ┌─────────────────────────┐
                    │   Bootstrap ClassLoader │  启动类加载器
                    │   （C++实现，不是Java对象）│  加载 <JAVA_HOME>/lib 目录
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │  Extension ClassLoader  │  扩展类加载器
                    │      （Java实现）        │  加载 <JAVA_HOME>/lib/ext 目录
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │   Application ClassLoader │  应用程序类加载器
                    │      （Java实现）        │  加载 classpath 上的类
                    └─────────────────────────┘
                                 │
                                 ▼
                          自定义类加载器
```

**三种类加载器详解：**

| 类加载器 | 负责加载的路径 | 说明 |
|---------|---------------|------|
| **启动类加载器**<br>Bootstrap | `JAVA_HOME/jre/lib` 目录下的核心类库 | 用C++实现，是虚拟机的一部分，在Java代码中获取不到，打印出来是null |
| **扩展类加载器**<br>Extension | `JAVA_HOME/jre/lib/ext` 目录 | 用Java实现，继承自ClassLoader |
| **应用程序类加载器**<br>Application（又叫System） | classpath下的类 | 我们程序中默认使用的类加载器，`ClassLoader.getSystemClassLoader()`返回的就是它 |
| **自定义类加载器** | 自定义路径 | 自己实现，可以加密、热加载等 |

#### 4. 双亲委派模型的工作过程

**一句话总结：** 类加载器收到加载请求，先不自己加载，而是**把请求委派给父类加载器去完成**，每一层都是如此，直到最顶层的启动类加载器。只有父类反馈"我加载不了这个类"，子类才会自己尝试加载。

**流程图：**

```
收到类加载请求
        ↓
是不是已经加载过了？ → 是 → 返回
        ↓ 否
让父类加载器去加载
        ↓
父类加载成功了吗？ → 是 → 返回
        ↓ 否
自己尝试加载
        ↓ 成功了吗？ → 是 → 返回
        ↓ 否
抛出 ClassNotFoundException
```

**为什么叫"双亲"而不是"父类"？**
因为"双亲"是翻译的问题，英文是"Parents"，实际上是"委派给父（级）加载器"，不是继承关系中的父类。它们之间是**组合关系**，不是继承关系！

```java
// 每个类加载器都持有父加载器的引用
public abstract class ClassLoader {
    private final ClassLoader parent;  // 父加载器，组合关系！不是继承！
    
    protected Class<?> loadClass(String name, boolean resolve) 
            throws ClassNotFoundException {
        // 1. 先检查是不是已经加载过了
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 让父类加载器去加载
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 没有父加载器，说明是Bootstrap，调用native方法
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父类加载不了，什么也不做，继续往下
            }
            
            if (c == null) {
                // 4. 父类加载不了，自己尝试加载
                c = findClass(name);
            }
        }
        return c;
    }
}
```

#### 5. 为什么要用双亲委派模型？（好处）⭐

**好处1：避免类的重复加载**

同一个类只会被最顶层的那个类加载器加载一次，不会出现多个类加载器都加载同一个类的情况，保证了类的唯一性。

**好处2：安全，防止核心API被篡改**

比如有人想写一个假的`java.lang.String`类来替换JDK的真正String：
- 按照双亲委派，加载请求先到Bootstrap类加载器
- BootStrap一看，`java.lang.String`这个类我已经加载过了（在rt.jar里）
- 直接返回已有的String类，不会再加载你那个假的
- 这样就保证了Java核心API不会被篡改！

**举个例子：**
如果没有双亲委派，每个人都可以自己写一个`java.lang.String`，那JVM里就会有多个String版本，程序就乱套了。

### 五、破坏双亲委派模型 ⭐

虽然双亲委派是推荐的模型，但它不是一个"必须遵守的约束"，在某些场景下是可以被打破的。

**历史上破坏双亲委派的3次大型事件：**

#### 1. 第一次破坏：JDK 1.2之前

因为双亲委派模型是在JDK 1.2才引入的，之前没有这个模型，用户可以直接重写`loadClass()`方法。

#### 2. 第二次破坏：JNDI、JDBC等SPI场景

这是最经典的破坏场景！

**问题背景：**
Java的SPI（Service Provider Interface）机制，比如JDBC：
- JDK核心库定义了`java.sql.Driver`接口（由Bootstrap类加载器加载）
- 具体的数据库驱动实现（如MySQL的`com.mysql.jdbc.Driver`）是第三方jar包，放在classpath下（由Application类加载器加载）

**问题来了：**
`DriverManager`是JDK核心类，由Bootstrap类加载器加载。当它要加载MySQL的Driver实现类时：
- 按照双亲委派，Bootstrap类加载器找不到classpath下的类
- 它也不能委派给Application类加载器（因为它是最顶层，没有父类了）

**解决方案：**
引入**线程上下文类加载器（Thread Context ClassLoader）**。
当需要加载SPI实现类时，`DriverManager`从线程上下文中拿到上下文类加载器（默认是Application类加载器），用它来加载实现类。

这就打破了双亲委派的层级结构，等于父类加载器请求子类加载器去完成类加载动作。

**举个生活化的例子：**
董事长（Bootstrap）需要一份具体的产品说明书，但是他自己找不到（那是底层部门的文档），所以他把这个任务交给部门经理（Application）去完成。

#### 3. 第三次破坏：热部署、热加载

典型场景：OSGi、Tomcat等Web容器。

**需求：**
一个Tomcat上可以部署多个Web应用，每个应用需要：
- 各自独立的类库（A应用用Spring 4，B应用用Spring 5，互不干扰）
- 可以热部署（修改代码不用重启Tomcat）

**如何实现？**
每个Web应用有自己的类加载器，一个应用要卸载/重新部署时，把它的类加载器整个换掉就行！

在OSGi中，类加载不再是严格的树状结构，而是变成了**网状结构**：每个bundle（模块）有自己的类加载器，需要某个类时，先在自己的bundle里找，找不到再去其他bundle找。

#### 5.4 实战场景：APM探针（SkyWalking/Pinpoint/OTel）是怎么玩转类加载器的？ ⭐⭐⭐

这是一个**非常实用的场景**，你在学习SkyWalking/Pinpoint时肯定会遇到"类可见性"、"为什么要打破双亲委派"这些问题。这里用最通俗的方式讲清楚！

---

##### ① 先搞懂：什么是"类可见性"？

**一句话：父加载器加载的类，看不到子加载器加载的类！**

```
                    ┌─────────────────────────┐
                    │   Bootstrap ClassLoader   │  ← 最顶层，权力最大
                    │   java.lang.String    │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │  Application ClassLoader │  ← 你的业务类在这里
                    │  UserService、OrderService│
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │  AgentClassLoader       │  ← SkyWalking/Pinpoint的类在这里
                    │  TraceSegment、Span     │
                    └─────────────────────────┘
```

**父子关系决定了"看得到 / 看不到**：
- ✅ 子加载器能看到父加载器的类（儿子能看到爸爸的东西）
  → AgentClassLoader里的类，能看到UserService
- ❌ 父加载器看不到子加载器的类（爸爸看不到儿子的东西）
  → Bootstrap里的类，看不到AgentClassLoader里的Span

**这就是"类可见性"问题的根源！父子关系是单向的，不是双向的！

---

##### ② 灵魂拷问：为什么Pinpoint必须打破双亲委派，而SkyWalking不需要？

这道题可以拆成两个问题：**"我增强谁？" 和 "谁来加载我？"

| APM | 增强什么类？ | 谁来加载被增强的类？ | 会遇到什么问题？ | 解决方案？ |
|------|------------|-------------------|----------------|----------|
| **Pinpoint** | 增强**一切**，包括JDK核心类（`java.net.Socket`、`java.sql.Connection`） | 被增强的类由**Bootstrap**加载 | Bootstrap看不到AgentClassLoader的拦截器类 | 把Agent核心类**注入到Bootstrap**！让所有类加载器都能看到 |
| **SkyWalking** | 只增强**框架入口点**（`@RestController`、Dubbo、MySQL驱动） | 被增强的类由**AppClassLoader**加载 | AppClassLoader和AgentClassLoader是父子关系，能看到 | 不需要打破，遵循双亲委派就行！ |
| **OTel** | 增强范围中等，可选JDK类 | 各种类加载器都可能 | 干脆不玩类加载器这套 | Maven Shade把所有依赖重命名，从根源避免冲突 |

##### ③ 场景还原：Pinpoint为什么必须注入Bootstrap？

```
Pinpoint想增强java.net.Socket（所有网络调用都要监控）
  ↓
Socket这个类是由Bootstrap ClassLoader加载的
  ↓
增强后Socket的方法里要调用Pinpoint的拦截器类（Interceptor）
  ↓
问题来了：Interceptor是放在AgentClassLoader里的
  ↓
按照双亲委派的可见性规则：Bootstrap是父，看不到子加载器的类！
  ↓
结果：ClassNotFoundException！增强失败！
```

**这就好比：** 你（Socket）是公司董事长（Bootstrap）的直属下属，你想调用一个外包员工（Interceptor）的方法，但这个外包员工是某个子公司（AgentClassLoader）的人，董事长根本不认识这个人，所以你找不到他！

**Pinpoint的解决办法：** 把这个外包员工正式入职到总公司（Bootstrap），这样全公司所有层级的人都能找到他了！

##### ④ 为什么Tomcat场景：为什么Tomcat要故意打破双亲委派？

Tomcat的WebAppClassLoader是**故意打破双亲委派**的，原因很现实：

```
一台Tomcat上要部署10个Web应用：
  - App1 用 Spring 4.3 + MyBatis 3.2
  - App2 用 Spring 5.0 + MyBatis 3.5
  - ...
  
如果遵循双亲委派：
  Spring的类先让父加载器去加载
  → 只能加载一个版本的Spring
  → 10个应用只能用同一个Spring版本！
  → 这怎么可能？老板会疯掉的！
```

**Tomcat的解决办法：** 每个Web应用有自己的类加载器，加载的时候**先在自己的WebApp里找，找不到再问父加载器要！这样每个应用可以用自己版本的Spring，互不干扰！

**这就是Pinpoint为什么更难的原因：** Tomcat自己就打破了双亲委派，Pinpoint要在已经打破的基础上，再做一次类加载隔离，相当于在坑上面再建一座桥！

##### ⑤ 生活化类比总结（看完忘不了！）

把类加载器的层级想象成**公司组织架构**：

| 类加载器 | 公司角色 | 说明 |
|---------|---------|------|
| **Bootstrap** | 董事长 | 管理核心业务（JDK核心类），权力最大 |
| **Extension** | 总监 | 管理扩展业务 |
| **Application** | 部门经理 | 管理部门业务（你的业务代码） |
| **AgentClassLoader** | 外包团队 | 做APM监控（SkyWalking/Pinpoint） |

**公司规则（双亲委派）：**
- 遇到任务先上报给上级，上级搞不定再自己搞
- 上级（父）看不到下级（子）手里具体有什么人

**三个APM的策略：

| APM | 策略 | 类比 |
|------|------|------|
| **Pinpoint** | 把外包团队成员**正式入职到董事长办公室** | 这样全公司所有人都能找到他们，哪怕是最底层的员工也能调他们 | 极致兼容，风险最高（万一外包到董事长身边，万一出问题就是公司直接倒闭） |
| **SkyWalking** | 外包团队就在部门层面干活 | 只跟部门经理级别的人打交道，不需要董事长认识 | 最平衡，风险低，稳定性好 |
| **OTel** | 把外包团队所有人都**改名换姓** | 干脆不跟公司任何人重名，公司人都不冲突 | 兼容性最好，就是名字怪了点 |

#### 5.5 实战场景：Tomcat 是怎么打破双亲委派模型的？ ⭐⭐⭐

这是面试**超高频考点**！Tomcat 打破双亲委派是教科书级的案例，理解了这个，类加载器就算真正入门了。

---

##### ① 先搞懂：Tomcat 为什么要打破双亲委派？

**核心原因：一台 Tomcat 要部署多个 Web 应用，这些应用的依赖库版本可能不同，必须互相隔离！**

```
一台 Tomcat 服务器上部署了 3 个 Web 应用：

  Web应用 A（电商系统）
    └── 依赖 Spring 4.3 + MyBatis 3.2 + Guava 20.0

  Web应用 B（物流系统）
    └── 依赖 Spring 5.2 + MyBatis 3.5 + Guava 30.0

  Web应用 C（CRM系统）
    └── 依赖 Spring 6.0 + MyBatis 3.5 + Guava 31.0

如果遵循双亲委派模型会发生什么？
  Spring 的类先委派给父加载器加载
  -> 父加载器只能加载一个版本的 Spring
  -> 3 个应用只能共用一个 Spring 版本！
  -> 电商用 Spring 4.3 的 API，CRM 用 Spring 6.0 的 API，必然有一个会报错！
```

**两个硬性需求，注定了 Tomcat 必须打破双亲委派：**

| 需求 | 说明 | 双亲委派能解决吗？ |
|------|------|------------------|
| **多应用依赖隔离** | 不同 Web 应用用不同版本的同一个库 | ❌ 双亲委派只能加载一个版本 |
| **热部署** | 重新部署某个应用时不用重启整个 Tomcat | ❌ 双亲委派的类会被缓存，无法重新加载 |

---

##### ② 如果不打破双亲委派，后果是什么？

**后果1：应用之间依赖冲突，根本跑不起来**

```
假设 Tomcat 遵循双亲委派，把所有公共库放到 CommonClassLoader：

  CommonClassLoader
    └── Spring 4.3（最先被加载，固化了）

  Web应用A（要 Spring 4.3）✅ 能跑
  Web应用B（要 Spring 5.2）❌ 加载到的是 Spring 4.3，调用 5.2 的新方法 -> NoSuchMethodError
  Web应用C（要 Spring 6.0）❌ 加载到的是 Spring 4.3，调用 6.0 的新方法 -> NoSuchMethodError
```

**后果2：热部署失效**

```
双亲委派下，类一旦被加载就会被缓存。
你重新部署 Web应用A，但是 Spring 4.3 的类还在父加载器里缓存着
-> 根本无法重新加载新版本的类
-> 只能重启整个 Tomcat！
```

**后果3：JSP 热更新失效**

```
JSP 会被编译成 Servlet 类。
你修改了 index.jsp，Tomcat 要重新编译成新的 index_jsp.class
如果遵循双亲委派，旧的 index_jsp 类被缓存
-> 新版本加载不到
-> JSP 修改不生效，必须重启 Tomcat！
```

---

##### ③ Tomcat 是怎么打破的？类加载器层次结构

Tomcat 自己搞了一套**独立的类加载器层次**，每个 Web 应用有自己的类加载器：

```
                    ┌─────────────────────────────┐
                    │   Bootstrap ClassLoader     │  ← JVM 启动类加载器
                    │   （加载 JDK 核心类）        │
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │   Extension ClassLoader      │
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │   Application ClassLoader    │  ← 加载 Tomcat 启动类
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │   Common ClassLoader         │  ← 加载 Tomcat 公共库
                    │   （$CATALINA_HOME/lib）     │     所有 Web 应用共享
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │   WebApp ClassLoader         │  ← 关键！每个Web应用一个
                    │   （打破双亲委派的地方）      │     加载 WEB-INF/classes、lib
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │   JasperLoader / JSP Loader  │  ← 加载编译后的 JSP
                    └─────────────────────────────┘
```

**关键角色：WebAppClassLoader**

每个 Web 应用有自己的 WebAppClassLoader，**它的加载顺序是反过来的**：

```
传统双亲委派的顺序（自上而下）：
  1. 先委派给父加载器
  2. 父加载器加载不了，自己才加载

WebAppClassLoader 的顺序（自下而上，打破双亲委派！）：
  1. 先检查本地缓存
  2. 先在自己的 WEB-INF/classes 加载（自己的类）
  3. 再在 WEB-INF/lib 加载（自己的 jar 包）
  4. 都找不到，才委派给父加载器（Common ClassLoader）
  5. 父加载器还找不到，才委派给 Application、Extension、Bootstrap
```

---

##### ④ 为什么是这个顺序？详解 Tomcat 的设计智慧

**先自己加载，再问父加载器**--这是打破双亲委派的核心动作，但 Tomcat 做得非常巧妙：

```java
// Tomcat 的 WebAppClassLoader.loadClass() 伪代码

protected Class<?> loadClass(String name, boolean resolve) {

    // 1. 先检查本地缓存
    Class<?> clazz = findLoadedClass(name);
    if (clazz != null) return clazz;

    // 2. ⚠️ 关键！先自己加载（WEB-INF/classes 和 WEB-INF/lib）
    try {
        clazz = findClass(name);  // 先自己找！打破了双亲委派！
        if (clazz != null) return clazz;
    } catch (ClassNotFoundException e) {
        // 自己找不到，继续往下
    }

    // 3. 自己找不到，才委派给父加载器（标准双亲委派）
    try {
        clazz = super.loadClass(name, resolve);
    } catch (ClassNotFoundException e) {
        // 父加载器也找不到，抛异常
    }

    return clazz;
}
```

**为什么这样设计？**

```
场景：Web应用B 依赖 Spring 5.2

  1. Web应用B 的代码里 new ClassPathXmlApplicationContext()
  2. 触发加载 org.springframework.context.support.ClassPathXmlApplicationContext
  3. WebAppClassLoader-B 先自己找
  4. 在 WEB-INF/lib/spring-context-5.2.jar 里找到了！加载 Spring 5.2 版本 ✅
  5. 不会委派给 CommonClassLoader，避免加载到错误的版本

结果：每个 Web 应用用自己的 Spring 版本，互不干扰！
```

---

##### ⑤ 例外情况：Tomcat 还是保留了部分双亲委派

Tomcat 不是完全抛弃双亲委派，而是**有选择地打破**：

```
Tomcat 对以下类仍然遵循双亲委派（先问父加载器）：
  1. Java 核心类（java.*、javax.*）-> 必须由 Bootstrap 加载，保证安全
  2. org.xml.sax.*、org.w3c.dom.* -> XML 相关，避免冲突
  3. org.apache.tomcat.*、org.apache.jasper.* -> Tomcat 自己的类
  4. javax.servlet.* -> Servlet 规范的类，必须统一版本
```

**为什么要保留这些？**

```
如果 Web 应用自己也能加载一个 java.lang.String：
  -> 业务代码里的 String 和 JDK 的 String 不是同一个类
  -> instanceof 判断失效
  -> 整个 Java 体系崩溃！

所以核心 API 必须由 Bootstrap 统一加载，这部分不能打破！
```

##### ⑥ 生活化类比：商场的专柜模式（看完忘不了！）

把 Tomcat 想象成一个**大型商场**，把 Web 应用想象成**专柜**：

| Tomcat 概念 | 商场类比 | 说明 |
|------------|---------|------|
| **Bootstrap** | 商场的水电系统 | 所有专柜共用，绝对统一（JDK 核心类） |
| **Common ClassLoader** | 商场的公共设施 | 所有专柜共用（如洗手间，对应公共库） |
| **WebAppClassLoader** | 每个专柜的独立仓库 | 每个专柜自己的货（应用自己的依赖） |
| **Web 应用** | 专柜 | 独立经营，有自己的货品 |

**传统双亲委派（商场统一采购）：**
- 所有专柜的货都由商场总仓库统一采购
- 总仓库只能进一个品牌的货（比如只进 Spring 4.3）
- 专卖 Spring 5.2 的专柜没货卖
- 后果：专柜倒闭（应用跑不起来）

**Tomcat 的做法（专柜独立采购 + 共享公共设施）：**
- 每个专柜有自己的仓库，自己进自己的货（先自己加载）
- 商场只提供水电、洗手间等公共设施（核心类走父加载器）
- 专柜之间互不干扰，各卖各的 ✅

---

##### ⑦ 总结：Tomcat 打破双亲委派的要点

| 要点 | 说明 |
|------|------|
| **为什么打破** | 多应用依赖隔离 + 热部署 + JSP 热更新 |
| **怎么打破** | WebAppClassLoader 先自己加载（WEB-INF/classes、WEB-INF/lib），再委派父加载器 |
| **不打破的后果** | 应用依赖冲突跑不起来 + 热部署失效 + JSP 修改不生效 |
| **保留了什么** | Java 核心类（java.*、javax.*）仍然走双亲委派，保证安全 |

> **🔥 面试必杀句：** Tomcat 打破双亲委派是为了实现 Web 应用之间的类库隔离和热部署。每个 Web 应用有自己的 WebAppClassLoader，它先在本地（WEB-INF/classes 和 WEB-INF/lib）加载类，找不到才委派给父加载器。但对 Java 核心类（java.*、javax.*）仍然保留双亲委派，防止核心 API 被篡改。如果不打破，多个应用共用同一版本的库会导致依赖冲突，热部署和 JSP 热更新也无法实现。

### 六、自定义类加载器

#### 什么时候需要自定义类加载器？

1. **加密解密**：Class文件加密，自定义类加载器解密后加载（防止反编译）
2. **热部署**：修改代码不重启，重新加载类
3. **从非标准来源加载**：从数据库、网络、加密文件等加载Class
4. **类隔离**：不同模块加载各自的类，互不干扰

#### 如何实现自定义类加载器？

很简单，两步：
1. 继承`java.lang.ClassLoader`
2. 重写`findClass()`方法（JDK 1.2之后不建议重写loadClass()，否则会破坏双亲委派）

**代码示例：**
```java
public class MyClassLoader extends ClassLoader {
    private String classPath;

    public MyClassLoader(String classPath) {
        this.classPath = classPath;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            // 1. 从指定路径读取class文件字节
            byte[] classBytes = loadClassBytes(name);
            if (classBytes == null) {
                throw new ClassNotFoundException();
            }
            // 2. 调用defineClass把字节数组转成Class对象
            return defineClass(name, classBytes, 0, classBytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    private byte[] loadClassBytes(String name) throws IOException {
        // 从classPath读取class文件的字节...
        // 这里也可以做解密操作！
    }
}
```

## 常见面试题

### 1. 简述一下类加载的过程？

**回答思路：**
> 类加载分为5个阶段：加载、验证、准备、解析、初始化。
>
> 1. **加载**：通过全限定名找到Class文件，读入内存，生成Class对象
> 2. **验证**：确保Class文件的安全性和合法性（4步验证）
> 3. **准备**：为static变量分配内存，设置零值（注意static final常量的特殊情况）
> 4. **解析**：把常量池的符号引用替换成直接引用
> 5. **初始化**：执行`<clinit>()`方法，真正执行static赋值和静态代码块
>
> 注意：这5个阶段是按顺序开始，但不一定按顺序完成（比如解析可能在初始化之后）。

---

### 2. 什么是双亲委派模型？为什么要设计双亲委派？

**回答思路：**
> **工作过程：** 类加载器收到加载请求，先不自己加载，而是委派给父类加载器，逐层往上，直到最顶层的Bootstrap。只有父类加载不了，子类才自己加载。
>
> **两大好处：**
> 1. **避免重复加载**：同一个类只会被加载一次，保证唯一性
> 2. **安全**：防止核心API被篡改，比如有人自己写java.lang.String也不会被加载，因为Bootstrap已经加载过了
>
> **注意：** 类加载器之间是组合关系，不是继承关系！

---

### 3. 准备阶段和初始化阶段的区别是什么？static变量在哪个阶段赋值？

**回答思路：**
> **准备阶段**：为static变量分配内存，设置**零值**（int=0, boolean=false, reference=null）
>
> **初始化阶段**：执行`<clinit>()`方法，给static变量赋**代码里写的值**，执行静态代码块
>
> **特殊情况**：如果是`static final`修饰且编译期就能确定的常量（如`123`、`"abc"`），准备阶段就直接赋值了，不用等到初始化。
>
> 例子：`public static int value = 123` → 准备后是0，初始化后才是123！

---

### 4. 符号引用和直接引用的区别是什么？

**回答思路：**
> - **符号引用**：只是一个"名字"，用字符串描述目标，和内存布局无关
> - **直接引用**：是真正的内存指针/偏移量，可以直接定位到目标
>
> 举例：符号引用 = 通讯录里的"张三"；直接引用 = 张三的手机号。
>
> 解析阶段就是把"名字"翻译成"实际地址"的过程。

---

### 5. 为什么要破坏双亲委派模型？举几个破坏的场景

**回答思路：**
> 双亲委派不是强制的，某些场景下需要打破：
>
> 1. **SPI场景（JDBC/JNDI）**：核心类（由Bootstrap加载）需要调用第三方实现类（由Application加载），这时候用线程上下文类加载器打破
> 2. **热部署/热加载**：Tomcat、OSGi等，每个应用有自己的类加载器，实现模块隔离和热部署
> 3. **自定义类加载器**：加密、非标准来源加载等场景
>
> 核心原因：双亲委派是"自上而下"的加载，但有些场景需要"底层实现由上层调用"，这就需要打破。

---

### 6. 两个对象的class相同，equals一定返回true吗？

**回答思路：**
> 不一定！
>
> 类的唯一性是由**类本身** + **加载它的类加载器** 共同确定的。即使是同一个Class文件，如果被两个不同的类加载器加载，生成的两个Class对象也不相等，对应的对象做equals比较也会返回false。
>
> 这是因为每个类加载器都有独立的类名称空间。

---

### 7. `<init>`和`<clinit>`的区别是什么？

**回答思路：**
> | 方法 | 是什么 | 什么时候执行 | 内容来源 |
> |------|--------|-------------|----------|
> | `<init>` | 实例构造器 | new对象的时候 | 成员变量赋值 + 构造函数代码 + 构造代码块 |
> | `<clinit>` | 类构造器 | 类初始化的时候 | static变量赋值 + 静态代码块 |
>
> 补充：
> - `<clinit>`是类层面的，每个类只会执行一次
> - `<init>`是对象层面的，每次new对象都会执行
> - 执行顺序：先执行父类的`<clinit>`，再执行子类的`<clinit>`；`<init>`也是父类先执行

---

### 8. 什么是主动引用和被动引用？

**回答思路：**
> 主动引用 = 会触发类初始化的5种场景（new、访问静态成员、调用静态方法、反射、初始化子类）
>
> 被动引用 = 不会触发类初始化的场景：
> 1. 通过子类引用父类的静态字段，只会触发父类初始化
> 2. 通过数组定义引用类（`new Student[10]`）
> 3. 访问编译期确定的静态常量（`static final`）
>
> 面试常考：给出代码，问会不会触发类初始化，输出什么。

### 9. （开放题）SkyWalking和Pinpoint都要做类加载隔离，为什么Pinpoint要把类注入到Bootstrap？

这是一道**综合应用题**，考察你是否真的理解了类可见性和双亲委派的本质，而不是死记硬背！

**回答思路：**
> 核心原因是：**两者的增强范围不同，对类可见性的要求不同！

> 1. **Pinpoint的增强范围**：要增强JDK核心类（如`java.net.Socket`、`java.sql.Connection`）。这些类是由**Bootstrap ClassLoader**加载的。
>    - 按照双亲委派的可见性规则：父加载器看不到子加载器的类
>    - 如果Pinpoint的拦截器放在AgentClassLoader（子加载器），Bootstrap加载的Socket就看不到拦截器类
>    - 结果：ClassNotFoundException，增强失败！
>
> 2. **SkyWalking的增强范围**：只增强框架入口点（`@RestController`、Dubbo、MySQL驱动）。这些类是由**Application ClassLoader**加载的。
>    - AgentClassLoader是Application的子加载器
>    - 子加载器能看到父加载器的类，父加载器也能看到子加载器的类吗？不，这里正好反过来
>    - 等等，SkyWalking是用ByteBuddy把拦截器注入到被增强类的类加载器里，不是直接跨加载器调用
>    - 所以不需要注入Bootstrap，遵循双亲委派就够了！
>
> 3. **一句话总结**：Pinpoint要增强JDK核心类，这些类在Bootstrap里，所以拦截器必须也放在Bootstrap里；SkyWalking只增强业务层/框架层的类，这些类在AppClassLoader里，不需要搞那么复杂。

### 10. Tomcat 是怎么打破双亲委派模型的？为什么要打破？

**回答思路：**
> **为什么要打破？** 两个核心需求：
> 1. **多应用依赖隔离**：一台 Tomcat 部署多个 Web 应用，它们依赖的库版本可能不同（如 A 用 Spring 4.3，B 用 Spring 5.2），必须互相隔离。双亲委派下父加载器只能加载一个版本，无法满足。
> 2. **热部署 + JSP 热更新**：重新部署应用或修改 JSP 后，需要重新加载类。双亲委派的类一旦加载就被缓存，无法重新加载。
>
> **怎么打破？** 每个 Web 应用有自己的 WebAppClassLoader，它**先自己加载**（WEB-INF/classes、WEB-INF/lib），找不到才委派给父加载器--顺序和双亲委派正好相反。
>
> **不打破的后果：**
> 1. 多个应用共用一个版本的库，必然有应用因为 NoSuchMethodError 跑不起来
> 2. 热部署失效，改代码必须重启整个 Tomcat
> 3. JSP 修改不生效，必须重启
>
> **保留什么？** 对 Java 核心类（java.*、javax.*）仍然走双亲委派，防止核心 API 被篡改导致 instanceof 失效、Java 体系崩溃。

## 本章学习建议

1. **先记大框架**：5个阶段是什么，每个阶段大概做什么
2. **重点突破**：准备阶段、初始化阶段、双亲委派模型，这三个是必考的
3. **代码验证**：自己写代码测试"被动引用"的三个场景，看输出结果，加深理解
4. **理解为什么**：不要只记"是什么"，多想"为什么要这么设计"（比如为什么需要双亲委派？为什么要打破？）

> 💡 **学习心法**：类加载机制本质上就是"把磁盘上的Class文件，变成JVM里可用的类型"的全过程。把它想象成"把食材从仓库搬到厨房，检查、清洗、切好、配齐，随时可以下锅"，理解起来就简单了！
