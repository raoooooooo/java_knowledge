# 10 - 上下文工程实战

> Agent 跑着跑着上下文就满了--多轮对话、工具结果、检索片段越堆越多。怎么管上下文是 Agent 能否稳定长跑的关键。本章讲窗口管理、压缩、隔离、长上下文工程。13 章讲了原理，本章讲 Java 落地和踩坑。

---

## 一、上下文工程 vs 提示工程

### 1.1 区别

- **提示工程（Prompt Engineering）**：优化「单次提问」。
- **上下文工程（Context Engineering）**：优化「整个 Agent 运行过程中，每一轮塞给 LLM 的完整上下文」--系统提示、记忆、历史、工具结果、检索内容、当前状态。

### 1.2 为什么重要

- **Agent 能力上限很大程度取决于上下文工程而非模型本身**。同样的模型，上下文管得好则 Agent 聪明稳定，管得差则跑偏、超限、遗忘。
- 长任务里上下文是动态的，每轮都在变，需要主动管理而非放任堆积。

> 💡 **面试金句**：上下文工程比提示工程更高一层--优化的是 Agent 整个运行周期每轮的完整上下文。Agent 能力上限很大程度取决于上下文工程而非模型本身。

---

## 二、上下文工程的五个核心动作

| 动作 | 含义 | 目的 |
|------|------|------|
| **写入（Write）** | 把重要信息写进上下文/记忆 | 后续可用 |
| **选择（Select）** | 每轮决定把哪些信息放进上下文 | 防止爆炸 |
| **压缩（Compress）** | 对冗长内容做摘要/抽取 | 省 token、提速度 |
| **隔离（Isolate）** | 子任务用独立子上下文 | 防噪声污染主上下文 |
| **遗忘/淘汰（Forget）** | 主动丢弃过时/无用信息 | 聚焦当前任务 |

这五个动作贯穿下面所有策略。

---

## 三、上下文窗口管理策略

### 3.1 滑动窗口

- 只保留最近 N 轮对话，旧的丢弃。
- 简单但会丢早期重要信息。
- 适合简单多轮对话。

### 3.2 自动压缩（Auto-Compact）★ 重点

- 当上下文逼近窗口上限时，**自动把旧内容总结成摘要**，保留要点，腾出空间。
- Claude Code 的 `/compact` 就是此机制。

```
[第1-20轮对话] --接近上限--> 自动压缩成摘要 --> [摘要 + 第21轮起] 继续工作
```

### 3.3 关键信息锚定

- 系统提示、任务目标、关键约束**始终保留在上下文头部**，不被压缩/截断丢失。
- 压缩时这些「锚定」内容不参与压缩。
- 例：`CLAUDE.md` 项目指令、任务目标、用户核心需求要锚定。

### 3.4 选择性保留

- 不是所有历史都同等重要。工具调用结果（可能很长）可以只留摘要，用户指令要留全文。
- 按信息价值分级保留。

## 四、子 Agent 上下文隔离 ★ 高频

### 4.1 痛点

- 大搜索/大读取产生海量中间细节，全灌回主上下文 -> 爆炸 + 注意力稀释。
- 例：Agent 让工具搜了 50 篇文档，每篇几千 token，全塞主上下文立刻超限。

### 4.2 子 Agent 隔离

- 把子任务交给**子 Agent**，子 Agent 用**独立上下文**处理（不污染主上下文），只把**最终结论**回传主 Agent。
- 主上下文只多一条「子任务结论」，保持干净。

```
主Agent上下文：[任务 + 子任务结论]   <- 干净
                    ↑ 只回传结论
子Agent上下文：[海量搜索细节]          <- 隔离，用完即弃
```

### 4.3 价值

- 防爆炸：海量细节隔离在子上下文。
- 防污染：子任务的噪声不进主上下文。
- 可并行：多个子任务各自独立上下文并行跑。

> 💡 **面试金句**：子 Agent 隔离是上下文「隔离」动作的工程实现--子任务用独立上下文处理海量细节，只回传结论，主上下文保持干净。防爆炸+防污染+可并行。

## 五、长上下文工程 ★

### 5.1 长上下文模型的出现

- Claude/Gemini/Qwen 都支持百万级 token 上下文。
- 一个直觉：上下文大了是不是就不需要 RAG 了？**不是**（见 5.3）。

### 5.2 Lost in the Middle（中间丢失问题）

- 即使上下文窗口很大，模型对**中间位置**的内容注意力会下降，关键信息放中间容易被忽略。
- U 型注意力：开头和结尾关注度高，中间低。
- 启示：重要信息放**开头或结尾**，别埋中间。

### 5.3 长上下文 vs RAG

| 维度 | 长上下文 | RAG |
|------|---------|-----|
| 实现 | 直接全塞 | 检索相关片段 |
| 准确性 | 中间易丢、注意力稀释 | 聚焦相关片段，更准 |
| 成本 | 高（全塞 token 贵） | 低（只塞相关） |
| 速度 | 慢（长输入） | 快 |
| 知识更新 | 要重新塞 | 改库即可 |

> 💡 **面试金句**：长上下文 ≠ 能用好。存在 Lost in the Middle、注意力稀释、成本高、速度慢。RAG 只检索相关片段，更准更省更快，知识可随时更新。长上下文适合「一次读全」场景，RAG 适合「海量知识库按需检索」，常配合用。

### 5.4 长上下文的正确用法

- 适合：单次长文档理解（「总结这份 200 页报告」）、代码库全局理解。
- 不适合：替代 RAG 做海量知识库检索（贵且中间丢失）。
- 配合：用 RAG 检索 + 长上下文容纳检索结果，兼顾两者。

// 思路：实现 Advisor，在上下文超阈值时触发压缩
public class CompactAdvisor implements BaseAdvisor {
    public AdvisedRequest before(AdvisedRequest req) {
        if (tokenCount(req.messages()) > THRESHOLD) {
            // 调小模型把旧消息摘要，保留系统提示+最近N轮
            req = compactOldMessages(req);

        return req;
    }

## 七、生产踩坑

1. **上下文无限堆积**：每轮消息全留不裁剪，长任务必爆。要滑动窗口/压缩。
2. **压缩丢了关键信息**：压缩把任务目标/约束摘要丢了，Agent 跑偏。关键信息锚定不参与压缩。
3. **工具结果全量回灌**：工具返回大 JSON 全塞上下文。裁剪只留关键字段。
4. **重要信息埋中间**：Lost in the Middle。关键内容放头/尾。
5. **用长上下文硬塞替代 RAG**：贵且不准。海量知识库还是 RAG。
6. **压缩本身费 token**：压缩要调 LLM，频繁压缩也有成本。设合理阈值，别每轮都压。
7. **子任务细节泄漏到主上下文**：子 Agent 实现不当把中间细节回传了。严格只回传结论。

## 八、常见面试题

1. **上下文工程和提示工程什么区别？为什么重要？**
   提示工程优化单次提问；上下文工程优化 Agent 整个运行周期每轮的完整上下文（含记忆、工具结果、状态）。Agent 能力上限很大程度取决于上下文工程而非模型本身。

2. **Agent 上下文快满了怎么办？**
   多策略：自动压缩旧内容成摘要腾空间、滑动窗口截断、关键信息锚定保留、子 Agent 隔离子任务只回传结论、裁剪工具返回结果。不是简单截断，是分级管理。

3. **什么是 Lost in the Middle？**
   模型对长上下文中间位置内容注意力下降，呈 U 型（头尾高、中间低）。重要信息别埋中间，放头/尾。这也是长上下文不能完全替代 RAG 的原因之一。

4. **长上下文有了还要 RAG 吗？**
   要。长上下文存在中间丢失、注意力稀释、成本高、速度慢、知识更新难。RAG 只检索相关片段更准更省更快，知识可随时更新。长上下文适合单次长文档理解，RAG 适合海量知识库检索，常配合。

5. **子 Agent 上下文隔离解决什么问题？**
   大搜索/大读取产生海量中间细节，灌回主上下文会爆炸+稀释。子 Agent 用独立上下文处理，只回传结论，主上下文保持干净。防爆炸+防污染+可并行。

6. **怎么压缩上下文不丢关键信息？**
   关键信息锚定（系统提示/任务目标/核心约束始终保留不参与压缩）、摘要保留要点、选择性保留（用户指令留全文、工具结果留摘要）。压缩后验证关键约束还在。

7. **上下文工程有哪些核心动作？**
   写入（记重要信息）、选择（每轮放哪些）、压缩（摘要冗长）、隔离（子任务独立上下文）、遗忘（淘汰过时）。五个动作贯穿上下文管理。

8. **工具返回结果太长怎么处理？**
   裁剪只留关键字段（别全量回灌）、用结构化输出限制返回量、必要时先摘要再回灌。工具结果是最容易撑爆上下文的，要重点管控。

## 九、资料勘误与重点提醒

1. **「上下文越大越好用」是误区**：资料常暗示大窗口就能全塞。实际有 Lost in the Middle、注意力稀释、成本高。大上下文要会用，不是越大越好。
2. **「长上下文取代 RAG」是误解**：资料偶尔说「百万 token 就不用 RAG 了」。实际长上下文贵、慢、中间丢失，海量知识库仍需 RAG。两者配合最优。
3. **「压缩就是截断」不严谨**：压缩是摘要/抽取保留要点，截断是直接丢弃，两者不同。截断会丢信息，压缩（做好锚定）能保关键。
4. **「子 Agent 隔离一定更好」漏了成本**：子 Agent 要额外 LLM 调用，有开销。简单任务直接处理更快，复杂/大任务才用子 Agent 隔离。资料常不说代价。
5. **「重要信息随便放」是错的**：因 Lost in the Middle，重要信息放中间易被忽略。资料少提，实际要锚定放头/尾。
6. **压缩频率**：资料讲压缩不讲阈值。频繁压缩本身费 token，要设合理阈值（如接近窗口 80% 才压），不是每轮都压。
