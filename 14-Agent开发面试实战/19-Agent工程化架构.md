# 19 - Agent 工程化架构

> 从「能跑的 Demo」到「能上线的系统」差的就是工程化。本章把 Agent 架构落到生产级：无状态运行时、会话持久化、Agent as a Service、异步长任务、高可用。这是 Java 工程师的主场--分布式系统的经验直接迁移。13 章讲了架构概念，本章讲 Java 落地。

---

## 一、Demo 到生产的鸿沟

| Demo 够用 | 生产必须补 |
|-----------|-----------|
| 单轮跑通 | 高可用、并发、状态持久化、会话恢复 |
| 内存状态 | 状态外置（DB/缓存/向量库） |
| 同步阻塞 | 异步长任务 + 队列 |
| 单实例 | 水平扩展 + 负载均衡 |
| 无限流 | 限流、熔断、降级 |
| 无版本 | 注册中心、版本管理、灰度回滚 |

> 💡 **面试金句**：Demo 到生产差一个工程化。核心是「无状态运行时 + 有状态存储外置」--Agent 运行时无状态可水平扩展，会话状态/记忆外置到 DB/向量库。这是分布式系统老套路，直接迁移。

## 二、无状态运行时 + 有状态存储 ★ 核心

### 2.1 为什么要无状态

- 有状态的实例无法水平扩展（某用户的状态在某实例，请求到别的实例就丢）。
- 无状态运行时：实例不存会话状态，任何实例都能处理任何请求，可随意扩缩容。

### 2.2 状态外置到哪

| 状态类型 | 存储 | 说明 |
|---------|------|------|
| **会话历史** | Redis / DB | 多轮对话历史，按 sessionId |
| **长期记忆** | 向量库 / DB | 用户偏好、事实、决策（11 章） |
| **任务状态** | DB / 工作流引擎 | 长任务进度、断点（17 章 Checkpoint） |
| **向量数据** | 向量库 | RAG 知识库 |
| **配置/Prompt** | 配置中心 | 动态刷新（Nacos/Apollo） |

### 2.3 架构

```
[负载均衡] -> [无状态Agent运行时 实例1..N]  <- 可水平扩展
                    ↓ 状态读写
            [Redis 会话][DB 任务][向量库 记忆/知识]
```

- 运行时实例挂了任意一个不影响，别的实例接管（从外置存储恢复会话）。
- 这和传统微服务无状态化一个思路。

## 三、会话持久化与断点恢复 ★

### 3.1 会话持久化

- 每轮对话后把历史存 Redis/DB（按 sessionId）。
- 下次请求带 sessionId，运行时从存储加载历史恢复上下文。
- Spring AI 的 ChatMemory 可换持久化实现（Redis/JDBC）。

```java
// 思路：ChatMemory 持久化到 Redis
@Bean
public ChatMemory chatMemory(RedisTemplate redis) {
    return new RedisChatMemory(redis);  // 自定义持久化实现
}
// 按 conversationId 隔离，加载/保存历史
```

### 3.2 断点恢复

- 长流程（Graph 编排）每步 Checkpoint 到 DB。
- 中途失败/重启，从最近 Checkpoint 续跑（17 章）。
- 价值：长任务可靠性，不重跑省钱。

### 3.3 会话超时与清理

- 会话不能无限存（存储成本）。设 TTL（如 7 天无活动清理）。
- 长期记忆和短期会话历史分开存（会话历史可清，长期记忆保留）。

## 四、Agent as a Service / API 网关 ★

### 4.1 Agent as a Service

- 把 Agent 封装成 API 对外提供：`POST /agent/run`，支持同步/流式（SSE）。
- 会话用 sessionId 关联多轮。
- 业务系统像调普通微服务一样调 Agent。

### 4.2 Agent 网关（类比 API 网关）

> 这是 Java 工程师的舒适区--Spring Cloud Gateway / APISIX 的经验直接用。

统一入口承担：

| 职责 | 说明 |
|------|------|
| **鉴权** | API Key / OAuth / JWT |
| **限流** | 按租户/用户限流，防滥用和成本失控 |
| **熔断降级** | 模型超时/限流自动降级（22 章） |
| **路由** | 按任务路由到不同 Agent/模型 |
| **审计** | 记录谁调了什么、输入输出（脱敏） |
| **多模型适配** | 屏蔽厂商 API 差异，统一对内接口 |
| **可观测** | 埋点 Trace/Token/延迟（20 章） |

```yaml
# Spring Cloud Gateway 代理 Agent 服务
spring:
  cloud:
    gateway:
      routes:
        - id: agent-service
          uri: lb://agent-service
          predicates: [Path=/api/agent/**]
          filters:
            - name: RequestRateLimiter   # 限流
            - name: Retry                # 重试
```

> 💡 **面试金句**：Agent 网关就是 API 网关--鉴权、限流、熔断、路由、审计、多模型适配。Spring Cloud Gateway 的经验直接迁移。限流尤其重要：LLM 调用贵且慢，不限流成本失控。

## 五、异步长任务与队列 ★

### 5.1 为什么要异步

- Agent 任务可能跑几十秒到几分钟（多步循环 + 工具调用 + LLM 推理）。
- 同步阻塞 HTTP 连接会超时、占资源、体验差。
- 长任务要异步化：提交任务立即返回 taskId，完成后回调/查询。

### 5.2 架构

```
客户端 POST /agent/task  -> 立即返回 taskId
                    ↓ 入队
              [消息队列 RocketMQ/Kafka]
                    ↓ 消费
              [异步 Agent Worker]  跑任务
                    ↓ 完成存结果
              [DB 结果]  <- 客户端轮询/回调查结果
```

### 5.3 流式 vs 异步

- **流式（SSE）**：实时看进度，适合几秒~几十秒的任务。
- **异步队列**：提交后台跑，适合几分钟以上的长任务。
- 两者可结合：异步任务 + SSE 推送进度。

### 5.4 Java 实现

```java
// 提交异步任务
@PostMapping("/agent/task")
public String submitTask(@RequestBody TaskRequest req) {
    String taskId = uuid();
    rocketMQTemplate.asyncSend("agent-task", req.withTaskId(taskId));
    return taskId;  // 立即返回
}

// Worker 消费跑任务
@RocketMQMessageListener(topic = "agent-task")
public class AgentWorker {
    public void onMessage(TaskRequest req) {
        String result = agent.run(req);
        resultStore.save(req.taskId, result);  // 存结果
        // 可选：SSE 推送完成通知
    }
}
```

## 六、高可用与水平扩展

### 6.1 高可用

- **运行时多副本**：无状态实例多副本，挂一个不影响。
- **模型多模型降级**：主模型挂切备用（22 章）。
- **存储高可用**：Redis/DB/向量库各自的 HA（集群/副本）。
- **限流熔断**：保护系统不被打挂。

### 6.2 水平扩展

- 运行时无状态，按 QPS/负载水平扩展（K8s HPA）。
- 扩展瓶颈：模型 API 限流（厂商 QPM/TPM 限制）、向量库性能、存储 IO。
- ⚠️ 模型 API 是外部依赖，扩展受厂商限流制约，不是加实例就能无限扩。

### 6.3 容量规划

- 估算：QPS × 平均 token × 单价 = 成本。
- 模型 API 限流决定上限，提前申请提额。
- 向量库按数据量和检索 QPS 规划。

## 七、生产踩坑

1. **运行时有状态**：会话状态存实例内存，无法扩展/重启丢。必须外置。
2. **同步跑长任务**：HTTP 超时、占连接、体验差。长任务异步化。
3. **没限流**：LLM 贵且慢，无限流成本失控 + 模型限流 429。必须按租户限流。
4. **模型 API 是外部单点**：厂商挂了全挂。要有降级/多模型（22 章）。
5. **会话无限存**：存储成本。设 TTL 清理。
6. **扩展只加实例**：模型 API 限流是外部瓶颈，加实例解决不了，要提额/多模型分流。
7. **无审计**：出问题没法查谁调了什么。网关层记录审计。

## 八、常见面试题

1. **Agent 怎么做生产架构？**
   无状态运行时 + 有状态存储外置：Agent 运行时无状态可水平扩展，会话历史/记忆/任务状态外置到 Redis/DB/向量库。加 Agent 网关（鉴权限流熔断审计多模型适配）+ 异步长任务队列 + 多副本高可用。分布式系统老套路迁移。

2. **Agent 运行时为什么无状态？**
   有状态实例无法水平扩展（某用户状态在某实例，请求到别的实例丢）。无状态运行时任何实例处理任何请求，可随意扩缩容，挂一个不影响。状态外置到 Redis/DB/向量库。

3. **Agent 会话怎么持久化？**
   每轮对话历史存 Redis/DB（按 sessionId），下次带 sessionId 加载历史恢复上下文。Spring AI 的 ChatMemory 可换持久化实现。设 TTL 清理过期会话。长期记忆和会话历史分开存。

4. **长任务怎么处理？**
   异步化：提交任务立即返回 taskId 入队（RocketMQ/Kafka），Worker 消费跑任务存结果，客户端轮询/回调查。流式（SSE）适合几秒~几十秒，异步队列适合分钟以上长任务。可结合异步+SSE 推进度。

5. **Agent 网关做什么？**
   和 API 网关一样：鉴权（API Key/OAuth/JWT）、限流（按租户防成本失控）、熔断降级、路由、审计、多模型适配、可观测埋点。Spring Cloud Gateway 经验直接迁移。限流尤其重要，LLM 贵且慢。

6. **Agent 怎么高可用和水平扩展？**
   运行时多副本无状态可扩展、模型多模型降级、存储各自 HA、限流熔断保护。水平扩展按 QPS 扩实例（K8s HPA）。瓶颈常在模型 API 限流（外部制约，加实例解决不了，要提额/多模型分流）。

7. **Agent 服务怎么做断点恢复？**
   长流程每步 Checkpoint 到 DB（17 章 Graph），失败/重启从最近 Checkpoint 续跑。会话历史持久化，实例重启后从存储恢复。这是无状态化的附带收益。

8. **你项目 Agent 架构怎么设计的？**
   （参考）无状态 Spring Boot 运行时多副本，会话历史 Redis、长期记忆向量库、任务状态 DB。Agent 网关用 Spring Cloud Gateway 鉴权限流审计。长任务走 RocketMQ 异步。多模型降级。K8s 部署 HPA 扩展。

## 九、资料勘误与重点提醒

1. **「Agent 架构很特殊」是误区**：资料常把 Agent 架构说得很神秘。实际就是分布式系统老套路--无状态运行时+状态外置+网关+队列+多副本。Java 工程师经验直接迁移。
2. **「同步调用够了」是坑**：资料示例常同步调 LLM。生产长任务同步会超时/占连接/体验差，必须异步化。资料少讲异步。
3. **「加实例就能扩」漏了外部瓶颈**：模型 API 有厂商限流（QPM/TPM），加实例解决不了，要提额或模型分流。资料常不提这个外部制约。
4. **「会话状态存内存」是严重坑**：资料示例常存实例内存。生产重启丢、无法扩展，必须外置 Redis/DB。
5. **限流重要性**：资料讲架构少强调限流。LLM 贵且慢，无限流成本失控+被厂商限流 429。Agent 网关限流是生产必备。
6. **审计合规**：资料少提审计。Agent 能行动，出问题要能查谁调了什么做了什么，网关层审计日志是合规和排障必备。
