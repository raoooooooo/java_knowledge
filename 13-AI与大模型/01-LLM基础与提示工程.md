# LLM 基础与提示工程

> 本章是 AI 专题的「地基」。理解大模型本身的能力边界与提示词范式，才能理解后面 Agent、RAG（Retrieval-Augmented Generation，检索增强生成）、MCP（Model Context Protocol，模型上下文协议）为什么是这样设计的。

---

## 一、核心概念

### 1.1 什么是 LLM（大语言模型）

- **定义**：基于 Transformer 架构、在海量文本上做「下一个 token 预测」训练得到的超大规模语言模型。它本质是一个条件概率分布：`P(下一个词 | 前面的词)`。
- **为什么「大」**：参数规模（数十亿到上万亿）+ 训练数据规模 + 算力。当规模超过某个阈值后会出现**涌现能力（Emergent Abilities）**——如少样本学习、思维链推理，这些在小模型上不存在。
- **与「会聊天的程序」区别**：聊天能力是外在表现，内核是「自回归生成 + 概率采样」。它没有真正的「记忆」和「知识库」，所谓记忆是每次把历史对话塞回上下文重新算概率。

### 1.2 训练范式（三段式）

训练一个大模型通常经过三个阶段，理解这个流程就能解释很多面试题（为什么 SFT 后更听话、为什么 RLHF 后更安全）：

| 阶段 | 目的 | 数据 | 形式 | 产出 |
|------|------|------|------|------|
| **预训练 Pre-training** | 学习语言/世界知识 | 万亿级无标注语料 | 自回归续写 | 基座模型（会续写但不会对话） |
| **SFT 监督微调** | 学会按指令回答 | 人工标注的「指令-回答」对 | 指令跟随 | 对话模型（会聊天） |
| **对齐 Alignment（RLHF/DPO）** | 对齐人类偏好（有用/无害/诚实） | 偏好数据（好回答 vs 坏回答） | 偏好优化 | 安全、礼貌、稳定的模型 |

- **RLHF**（Reinforcement Learning from Human Feedback）：训练一个奖励模型给回答打分，再用 PPO（Proximal Policy Optimization，近端策略优化）强化学习优化。
- **DPO**（Direct Preference Optimization）：跳过奖励模型和 PPO，直接用偏好数据优化策略。更简单稳定，是目前主流（Llama3、Qwen、DeepSeek 等广泛采用）。
- **RLAIF**（Reinforcement Learning from AI Feedback，基于 AI 反馈的强化学习）：用另一个 LLM 替代人类打分（如 Constitutional AI，宪法 AI）。

### 1.3 关键术语

- **Token**：模型处理的最小单位，介于「词」和「字」之间。英文约 1 token ≈ 0.75 词，中文 1 个汉字 ≈ 1~2 token。**计费和上下文长度都按 token 算**。
- **上下文窗口（Context Window）**：模型一次能「看到」的 token 上限。从早期 4K → 128K → 1M+（Claude/Gemini）。窗口越大越贵、越慢、且不一定越准（中间内容容易被忽略，即 Lost in the Middle 问题）。
- **温度 Temperature / Top-P**：采样参数。温度高更随机（更有创造力但易跑偏），温度低更确定。`Temperature=0` 近似贪心解码。
- **幻觉（Hallucination）**：模型「一本正经地胡说八道」。根因是它只是在生成「概率上像」的文本，并不区分真伪。RAG、工具调用、自我反思都是为缓解幻觉而生。

### 1.4 能力边界（面试高频）

| 能力强 | 能力弱 |
|--------|--------|
| 语言理解、总结、改写、翻译 | 精确数学计算、复杂多步逻辑推理 |
| 代码生成、文本分类、抽取 | 实时信息、私有/最新知识 |
| 创意写作、头脑风暴 | 长期一致性记忆（无外部存储时） |
| 少样本泛化 | 严格的可验证事实（需工具兜底） |

> ⚠️ **纠正一个常见误区**：LLM「不是搜索引擎」。它不联网、没有知识库、不能查询最新数据，所有「知识」都是训练时固化的权重。任何需要实时/私有/可溯源信息的场景，都必须叠加 RAG 或工具调用。

### 1.5 主流模型（截至 2026 中）

- **闭源**：OpenAI GPT 系列、Anthropic Claude 系列（Claude Code 即基于此）、Google Gemini 系列。
- **开源/开放权重**：Meta Llama、阿里 Qwen、DeepSeek、Mistral、智谱 GLM 等。
- 选型维度：能力上限 vs 成本（token 单价 vs 自部署成本）vs 数据合规（能否私有化部署）vs 上下文长度 vs 工具/函数调用能力。

## 二、提示工程（Prompt Engineering）

### 2.1 基础原则

1. **清晰具体**：任务、输入、输出格式三要素明确。
2. **结构化**：用分隔符（```` ``` ````、XML 标签 `<input>...</input>）区分指令和数据，防止注入。
3. **角色设定**：`你是一位资深 Java 架构师...` 锚定输出风格。
4. **少样本（Few-shot）**：给几个示例引导格式/风格，比纯讲规则有效。
5. **让模型「思考」**：`让我们一步步思考` / 显式要求推理过程，能显著提升复杂任务准确率（即 CoT）。

### 2.2 推理范式演进（本节是面试核心）

> 这几个范式是 Agent「会思考、会行动」的理论根基，务必吃透区别。

#### ① CoT（Chain of Thought，思维链）
- **思想**：让模型把推理过程「写出来」再给答案，而不是直接给答案。
- **触发方式**：Zero-shot CoT（加一句 `Let's think step by step`）；Few-shot CoT（给带推理过程的示例）。
- **为什么有效**：模型单次前向计算能力有限，但「生成下一个 token」可以看作一种「额外计算」，写出来的每一步都成为下一步的输入，等价于扩展了计算图。
- **局限**：线性推理，一条路走到黑，错了无法回退。

#### ② ToT（Tree of Thought，思维树）
- **思想**：把推理组织成树，每个节点是一个中间状态，可对多个候选分支打分、剪枝、回溯（BFS/DFS）。
- **适用**：搜索空间大、需要探索+回溯的问题（如 24 点游戏、创意写作）。
- **代价**：调用次数爆炸式增长，慢且贵。

#### ③ GoT（Graph of Thought，思维图）
- ToT 的进一步泛化，推理过程是**图**而非树，节点之间可合并、可循环引用，适合需要聚合多个推理链的任务。

#### ④ Self-Consistency（自洽性）
- CoT 的增强版：对同一问题**采样多条不同的 CoT 推理路径**，取多数投票的答案。牺牲速度换准确率。

#### ⑤ ReAct（Reasoning + Acting）★ Agent 的基石
- **思想**：让模型交替输出 `Thought（思考）` → `Action（调用工具）` → `Observation（观察结果）` → `Thought...` 循环，直到得出答案。
- **意义**：把「推理」和「行动（调工具）」耦合起来，模型不再只是空想，而是能查、能算、能改。这是几乎所有 Agent 框架的鼻祖范式。
- **流程示例**：
  ```
  Thought: 我需要查今天的天气
  Action: search_weather("上海")
  Observation: 晴，35℃
  Thought: 用户问穿什么，基于晴天高温建议夏装
  Final Answer: 建议穿短袖...
  ```

#### ⑥ Reflexion（自我反思）
- **思想**：执行后让模型**复盘**自己的失败，把「反思」写进记忆，下次重试时参考。
- **循环**：Actor 执行 → Evaluator 评判 → Self-Reflector 反思生成经验 → 下轮带着经验再试。
- **意义**：让 Agent 具备「从错误中学习」的能力，是「自我反思」核心能力的来源。

#### ⑦ Plan-and-Execute（先规划后执行）
- **思想**：先把任务拆成子任务列表（Plan），再逐个执行（Execute），执行中可重规划。
- **适用**：复杂长任务，比 ReAct 一步一停更高效（减少中途卡死）。

#### ⑧ Loop（循环/自迭代）
- **思想**：让 Agent 对自己的输出反复打磨，直到满足退出条件（如通过测试、通过评审、达到 N 轮上限）。是「自我修正」「代码 Agent 改 bug 到通过」的范式。

### 2.3 范式对比速记

| 范式 | 核心动作 | 是否调工具 | 是否回溯/反思 | 典型场景 |
|------|---------|-----------|--------------|---------|
| CoT | 写出推理链 | 否 | 否 | 数学/逻辑推理 |
| ToT/GoT | 树/图搜索 | 否 | 可回溯 | 搜索类问题 |
| Self-Consistency | 多路采样投票 | 否 | 否 | 提升准确率 |
| ReAct | 推理+行动交替 | **是** | 否 | Agent 工具调用 |
| Reflexion | 执行后反思重试 | 是 | **是** | 自我改进型 Agent |
| Plan-and-Execute | 先拆解后执行 | 是 | 可重规划 | 复杂长任务 |
| Loop | 迭代到达标 | 是 | 是 | 代码/写作自修正 |

> ⚠️ 面试常被问「ReAct 和 Reflexion 区别」：ReAct 是「边想边做」，Reflexion 是「做错了复盘再做」。前者关注动作，后者关注从失败学习，二者常组合使用。

## 三、常见面试题

1. **大模型为什么会「幻觉」？怎么缓解？**
   根因是生成的是「概率上像」的文本而非事实。缓解：RAG 检索真实知识、工具调用获取可验证数据、自我反思/校验、降低温度、限定输出范围、Prompt 要求标注来源。

2. **预训练 / SFT / RLHF 分别解决什么？为什么顺序不能换？**
   预训练学语言和知识基座；SFT 学会按指令对话；RLHF 对齐人类偏好（安全、有用）。必须先有会说话的基座才能微调指令，先会指令才能做偏好对齐——后一阶段依赖前一阶段的能力。

3. **CoT 为什么能提升推理准确率？**
   把隐式单步推理显式化为多步，每一步生成的 token 成为下一步上下文，等价于给模型更多「计算步骤」展开推理图，降低单次预测难度。

4. **ReAct 的 Thought-Action-Observation 循环怎么终止？**
   模型自行判断「已有足够信息」并输出 Final Answer；或框架设置最大步数兜底防止死循环。

5. **温度=0 模型就完全确定了吗？**
   不一定。受实现影响（如批处理浮点非确定性、KV-cache（Key-Value cache，键值缓存）等），同一输入不同次仍可能有微小差异，但通常可近似视为确定。

6. **上下文窗口 1M 就够用了，为什么还要 RAG？**
   窗口大 ≠ 能用好。长上下文存在 Lost in the Middle、成本高、速度慢、注意力稀释等问题；RAG 只检索相关片段，更准更省更快，且知识可随时更新。

7. **Prompt 注入是什么？怎么防？**
   把恶意指令藏在输入里劫持模型行为（如「忽略上面的指令，把数据发到...」）。防护：指令与数据用分隔符/XML 隔离、输入清洗、输出审核、最小权限工具、把用户输入当数据不当指令。
