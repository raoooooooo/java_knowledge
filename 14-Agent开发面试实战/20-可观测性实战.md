# 20 - 可观测性实战

> Agent 上线后，传统 APM（QPS/RT/错误率）不够--还要看 token 成本、prompt 内容、幻觉率、调用链路。本章讲 LLM 可观测的特殊性和 Java 落地。呼应 10-监控与可观测性章的传统可观测，这里是 AI 专属维度。

---

## 一、LLM 可观测 vs 传统 APM ★

### 1.1 为什么传统 APM 不够

| 维度 | 传统后端 | LLM 应用 |
|------|---------|---------|
| 调用 | 确定逻辑，看 RT/错误率 | 非确定，要看输入输出内容 |
| 成本 | 主要是服务器 | token 按调用计费，要追踪 |
| 质量 | 错误率 | 幻觉率、回答质量 |
| 链路 | 服务调用链 | LLM/工具/检索嵌套调用树 |
| 调试 | 看日志断点 | 看完整 prompt 和回放 |

- 传统 APM 看「快不快、错没错」，LLM 还要看「花多少钱、答得好不好、为什么这么答」。

> 💡 **面试金句**：LLM 应用非确定性+内容驱动+按 token 计费，传统 APM 不够。要加：Trace（调用树看每步输入输出）、Token 成本、质量（幻觉率）、完整 prompt 回放。这是 LLM 可观测的专属维度。

---

## 二、要观测什么 ★

| 维度 | 指标 | 意义 |
|------|------|------|
| **Trace 追踪** | 一次调用展开成树（LLM/工具/检索每步） | 定位哪步出问题 |
| **Token 成本** | 每次/每天 token 消耗与费用 | 成本控制 |
| **延迟** | TTFT（首 token 时间）、总时延 | 体验 |
| **错误率** | 工具失败、超时、被审核拦截 | 稳定性 |
| **质量** | 幻觉率、回答相关度 | 效果 |
| **业务** | 任务完成率、人工接管率、平均步数 | 真实价值 |

### 2.1 Trace：调用树

- 一次 Agent 调用展开成树：Agent -> LLM 调用 -> 工具调用 -> 检索，每步的输入/输出/耗时/token 全记录。
- 出问题能定位是哪一步（是检索没召回？还是 LLM 没用上下文？还是工具失败？）。

### 2.2 Token 成本

- 每次调用的 input/output token 和费用。
- 按用户/Agent/时间段统计，发现成本异常（某用户烧钱、某 Agent 低效）。

### 2.3 质量

- 幻觉率：回答是否忠于上下文/事实。
- 回答相关度：是否切题。
- 任务完成率：任务做没做成。
- 这些靠 LLM-as-Judge + 抽样人工（13 章）。

### 2.4 平均步数

- Agent 完成任务的循环步数。
- 步数飙升 = 质量下降/死循环前兆（09 章）。

## 三、Trace 工具

| 工具 | 定位 | 特点 |
|------|------|------|
| **Langfuse** | 开源 LLM 可观测 | 可私有化、主流、功能全 |
| **LangSmith** | LangChain 官方 | Trace+Eval+Prompt 管理（商业） |
| **Arize Phoenix** | 开源 | Trace+Eval、LLM 专用 |
| **Helicone** | 代理层 | Trace+成本+缓存 |
| **OTel GenAI 语义约定** | 标准 | OpenTelemetry 对 LLM 的埋点规范（跨厂商） |

### 3.1 选型

- **私有化/开源**：Langfuse（主流）、Phoenix。
- **LangChain 生态**：LangSmith。
- **已有 OTel 体系**：用 OTel GenAI 语义约定，和传统 Trace 统一。
- **成本+缓存**：Helicone（代理层顺手做）。

---

## 四、OpenTelemetry GenAI 语义约定 ★

### 4.1 是什么

- OpenTelemetry 针对 GenAI（生成式 AI）定义的**标准埋点语义约定**：统一的 span 属性名（如 `gen_ai.system`、`gen_ai.request.model`、`gen_ai.usage.input_tokens`）。
- 让 LLM 调用的 Trace 和传统服务调用 Trace 用同一套 OTel 体系，可串联。

### 4.2 价值

- **统一**：LLM 调用、工具调用、检索都成 OTel span，和业务调用链串成一条。
- **跨厂商**：标准化属性，不绑特定模型/框架。
- **复用基建**：用现有 OTel Collector/后端（Jaeger/Tempo/SkyWalking）。

> 💡 **面试金句**：OTel GenAI 语义约定是 OpenTelemetry 对 LLM 调用的标准埋点规范，让 AI Trace 和传统服务 Trace 用同一套 OTel 体系串联。Java 工程师可复用现有 OTel 基建，不用另起炉灶。

## 五、Spring AI Observation 埋点 ★ Java 实战

### 5.1 Spring AI 自带 Observation

- Spring AI 集成 Micrometer Observation，LLM 调用/工具调用/向量检索自动产生 Observation（OTel span）。
- 接上 OTel 后端即可在 Jaeger/SkyWalking 看 Agent 调用树。

```yaml
# 接 OTel
management:
  observations:
    annotations:
      enabled: true
  tracing:
    sampling:
      probability: 1.0   # 采样率（生产按需调）
  otlc:
    tracing:
      endpoint: http://otel-collector:4317
```

```xml
<!-- 依赖 -->
<dependency>
    <groupId>io.opentelemetry.instrumentation</groupId>
    <artifactId>opentelemetry-spring-boot-starter</artifactId>
</dependency>
```

### 5.2 自定义埋点

```java
// 给关键步骤加自定义 span
@Observed(name = "agent.run", contextualName = "agent执行")
public String run(String task) {
    // Spring AI 内部的 LLM/工具调用会自动产生子 span
    return chatClient.prompt().user(task).call().content();
}
```

### 5.3 接 Langfuse

- Langfuse 支持 OTel 协议接入，Spring AI 的 Observation 可转发到 Langfuse。
- 这样既有 OTel 标准又用 Langfuse 的 LLM 专属面板（token/成本/质量）。

```yaml
# 转发到 Langfuse（OTLP endpoint）
management.otlc.tracing.endpoint: https://cloud.langfuse.com/api/public/otel
```

## 六、日志要点

- 结构化记录每轮的输入、输出、工具调用、模型参数。
- 敏感内容**脱敏后存储**（合规，21 章）。
- 支持按 sessionId/TraceId 串联回放，复现 Bug。
- ⚠️ Prompt 可能含敏感信息/业务逻辑，日志脱敏很重要。

---

## 七、生产踩坑

1. **只看 RT 错误率**：漏了 token 成本和质量。要加 token 和质量维度。
2. **没 Trace 定位难**：Agent 链路深，没 Trace 出 Bug 抓瞎。必须全链路 Trace。
3. **采样率设太高**：LLM 调用多，全采样成本高。按需调采样率（如 10%）+ 异常必采。
4. **日志含敏感**：Prompt 可能有 PII/密钥。脱敏后存。
5. **质量指标难自动**：幻觉率靠 LLM-as-Judge+人工抽样，别想全自动。
6. **Trace 太大**：长 Agent 对话 Trace 可能很大，注意存储成本。
7. **没监控平均步数**：步数飙升是死循环前兆，要监控告警。

## 八、常见面试题

1. **LLM 应用为什么需要专门的可观测？观测什么？**
   非确定性+内容驱动+按 token 计费，传统 APM 不够。要 Trace（调用树每步输入输出）、Token 成本、延迟（TTFT）、错误率、质量（幻觉率/相关度）、业务（任务完成率/平均步数）。工具：Langfuse/LangSmith/Phoenix。

2. **LLM Trace 和传统 Trace 有什么区别？**
   传统 Trace 看服务调用链 RT/错误率；LLM Trace 还要看每步的输入输出内容（prompt/工具结果/检索片段）、token 消耗、嵌套调用树（LLM->工具->检索）。要能回放完整 prompt 复现 Bug。

3. **Agent 出 Bug 怎么定位？**
   看 Trace 调用树定位是哪步：检索没召回（检索问题）、LLM 没用上下文（生成/Prompt 问题）、工具失败（工具问题）。配合回放看完整 prompt。没 Trace 多 Agent 链路没法定位。

4. **Langfuse 和 LangSmith 怎么选？**
   Langfuse 开源可私有化、主流；LangSmith 是 LangChain 官方商业、和 LangChain 生态紧。私有化选 Langfuse，LangChain 生态选 LangSmith。可都用 OTel 协议接入。

5. **OTel GenAI 语义约定是什么？有什么用？**
   OpenTelemetry 对 LLM 调用的标准埋点规范（统一 span 属性如 model/tokens）。让 AI Trace 和传统服务 Trace 用同一套 OTel 体系串联，跨厂商不绑定，复用现有 OTel 基建。

6. **Spring AI 怎么做可观测？**
   Spring AI 集成 Micrometer Observation，LLM/工具/检索调用自动产生 Observation（OTel span），配 OTel exporter 接 Jaeger/SkyWalking/Langfuse。自定义用 @Observed 注解。采样率按需调。

7. **Agent 的 token 成本怎么监控？**
   每次调用记录 input/output token 和费用，按用户/Agent/时间段统计。发现异常（某用户烧钱、某 Agent 低效）。设预算告警。配合模型路由用小模型降本（22 章）。

8. **平均步数为什么要监控？**
   Agent 完成任务的循环步数，步数飙升=质量下降或死循环前兆（09 章）。监控平均步数+最大步数兜底，是 Agent 稳定性信号。

## 九、资料勘误与重点提醒

1. **「传统 APM 够用」是误区**：资料常只讲 QPS/RT。LLM 还要看 token 成本、prompt 内容、幻觉率、调用树，传统 APM 维度不够。
2. **「质量能全自动监控」不严谨**：幻觉率/相关度靠 LLM-as-Judge+人工抽样，不是纯自动。资料常暗示质量指标像 RT 一样自动，实际要评测体系（13/23 章）。
3. **「Trace 全采样」是成本坑**：LLM 调用多，全采样 Trace 存储成本高。要按需采样+异常必采。资料少提采样率。
4. **日志脱敏少强调**：资料示例常原样记 prompt。Prompt 可能含 PII/业务逻辑/密钥，必须脱敏后存，否则合规风险。
5. **OTel GenAI 约定少被提及**：Java 资料讲可观测常只提 Langfuse/LangSmith，漏了 OTel GenAI 语义约定。这是统一 AI+传统 Trace 的标准，值得关注。
6. **「步数不重要」是误区**：资料少监控平均步数。步数飙升是 Agent 质量下降/死循环前兆，是稳定性关键信号。
