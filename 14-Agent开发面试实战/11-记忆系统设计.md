# 11 - 记忆系统设计

> 上下文窗口是「短期记忆」，容量有限。要让 Agent 跨会话记住用户偏好、历史决策、经验教训，需要长期记忆系统。本章讲记忆类型、向量记忆库、写入/检索/遗忘策略、Spring AI 会话记忆实战。面试「Agent 记忆怎么实现」必考。

---

## 一、为什么需要记忆

### 1.1 只有上下文窗口不够

- 上下文窗口是「短期记忆」，容量有限、会随压缩/截断丢失。
- 跨会话场景（「上次说的那个方案」）上下文清空就忘了。
- 需要「长期记忆」：上下文之外的持久化存储，按需检索注入。

### 1.2 记忆是 Agent「像人」的关键

- 没记忆的 Agent 每次都从零开始，体验差、无法个性化。
- 有记忆的 Agent 能记住用户偏好、历史决策、失败教训，越用越懂用户。

---

## 二、记忆类型分层（参考认知科学）

| 类型 | 内容 | 生命周期 | 工程对应 |
|------|------|---------|---------|
| **工作记忆** | 当前任务上下文 | 单次会话 | 上下文窗口 |
| **短期记忆** | 当前对话历史 | 单次会话 | 上下文窗口/会话历史 |
| **情景记忆** | 具体事件/对话 | 可持久、按场景检索 | 向量记忆库 |
| **语义记忆** | 事实/知识 | 长期 | 向量库/知识库/RAG |
| **程序记忆** | 技能/操作经验 | 长期、可复用 | Skill/工具库 |

- 类比人：工作记忆=正在想的事；情景记忆=上次那件事；语义记忆=知识点；程序记忆=会骑自行车。

> 💡 **面试金句**：记忆分短期（上下文窗口）和长期（外部存储）。长期又分情景（具体事件）、语义（事实知识）、程序（技能经验）。工程上：短期=上下文/会话历史；情景/语义=向量库/RAG；程序=Skill/工具库。

---

## 三、短期记忆（会话内）

### 3.1 载体

- 上下文窗口内的当前对话历史。
- 快、即时，但容量有限、会随压缩/截断丢失。

### 3.2 会话历史管理

- 多轮对话要把历史塞回去（每轮累积，越聊越贵）。
- 策略：滑动窗口保留最近 N 轮、自动压缩旧消息、关键信息锚定（呼应 10 章）。

---

## 四、长期记忆（跨会话）★ 核心

### 4.1 常见实现

| 方式 | 原理 | 适用 |
|------|------|------|
| **向量记忆库** | 把过往对话/事实向量化，按语义检索注入 | 通用，主流 |
| **知识图谱** | 结构化存储实体关系 | 精确回忆关联信息 |
| **键值数据库** | 存用户偏好、结构化事实 | 高频读写、精确查询 |
| **文件系统** | 笔记/结论写文件 | 离线、大段结论（如 Claude Code memory 目录） |
| **关系数据库** | 结构化记忆（用户表/偏好表） | 业务关联记忆 |

### 4.2 向量记忆库（主流）★

- 本质：**RAG 应用于「记忆」**。
- 把过往对话/事实/决策向量化入库，需要时按当前任务语义检索相关记忆注入上下文。
- 「回忆」= 向量检索。

```
新对话开始
  ↓
Query: 当前任务语义 -> 检索向量记忆库 -> Top-K 相关记忆
  ↓
注入上下文: "你之前和这个用户讨论过X，偏好Y"
  ↓
LLM 带着记忆回答
```

### 4.3 记忆的检索

- 和 RAG 检索同理：向量化 + 相似度检索 + 可选 Rerank。
- 区别：检索的是「历史记忆」而非「知识库文档」。
- 检索质量决定记忆有没有用--检索不准等于没记忆。

## 五、记忆管理三问 ★ 必考

### 5.1 写什么（Encoding）

- **不是所有对话都存**。全存会噪音爆炸、费存储、检索不准。
- 值得存的：
  - 用户偏好（喜欢简洁回答、技术栈是 Java）
  - 关键决策（用户选择了方案 A）
  - 事实（用户的公司/角色/项目背景）
  - 失败教训（上次这么做错了）
- 用 LLM 判断「这条值不值得记」+ 提炼成简洁记忆条目。

### 5.2 怎么找（Retrieval）

- 按当前任务语义检索相关记忆注入。
- 检索不准=记忆用不上。和 RAG 一样要优化检索（混合检索/Rerank/元数据过滤）。
- 可按用户 ID/会话 ID 过滤（只检索该用户的记忆）。

### 5.3 何时忘（Forgetting/Reflection）

- **主动淘汰过时信息**：时效性数据过期就删。
- **反思机制**：定期对记忆做总结/合并/泛化。
  - 例：「昨天吃面、前天吃面」-> 抽象成「最近常吃面」。
  - 压缩冗余、提炼规律，防记忆膨胀。
- **合规要求**：GDPR「被遗忘权」，用户要求删除其记忆必须能删。

> 💡 **面试金句**：记忆管理三问：写什么（只记有价值的，不是全存）、怎么找（语义检索注入，检索质量决定记忆有没有用）、何时忘（淘汰过时+反思合并泛化，防膨胀+合规）。全存会噪音爆炸。

## 六、Java 实战：Spring AI 会话记忆

### 6.1 ChatMemory（短期/会话内）

```java
// Spring AI 内置会话记忆
@Configuration
public class MemoryConfig {
    @Bean
    public ChatMemory chatMemory() {
        return MessageWindowChatMemory.builder()
            .maxMessages(20)           // 滑动窗口保留最近20条
            .build();
    }
}

// 按会话ID隔离（conversationId）
String reply = chatClient.prompt()
    .user(question)
    .advisors(advisor -> advisor.param(ChatMemory.CONVERSATION_ID, sessionId))
    .call()
    .content();
// 框架自动管理该会话的历史，下次同 sessionId 能续上
```

- `MessageWindowChatMemory`：滑动窗口，保留最近 N 条。
- 可换持久化实现（Redis/JDBC），跨重启保持会话。

### 6.2 长期记忆（向量库）

```java
// 思路：对话结束/关键节点，把值得记的内容向量化存入向量库
@Service
public class LongTermMemoryService {
    private final VectorStore memoryStore;   // 专用记忆向量库
    private final ChatModel model;

    // 写入：LLM 判断+提炼值得记的内容
    public void remember(String userId, String conversation) {
        String memory = model.call("从以下对话提炼值得长期记忆的事实/偏好，简洁：" + conversation);
        Document doc = new Document(memory, Map.of("userId", userId, "time", now()));
        memoryStore.add(List.of(doc));
    }

    // 检索：按当前任务+用户过滤检索
    public List<Document> recall(String userId, String currentTask) {
        return memoryStore.similaritySearch(
            SearchRequest.builder()
                .query(currentTask)
                .filterExpression("userId == '" + userId + "'")
                .topK(5)
                .build());
    }
}
```

### 6.3 LangChain4j 记忆

```java
ChatMemory memory = MessageWindowChatMemory.withMaxMessages(20);
// AiServices 自动管理记忆，按 memoryId 隔离
Assistant agent = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .chatMemoryProvider(memoryId -> MessageWindowChatMemory.withMaxMessages(20))
    .build();
```

## 七、生产踩坑

1. **全存对话**：噪音爆炸、检索不准、费存储。只存有价值的，用 LLM 提炼。
2. **记忆不隔离**：A 用户的记忆被 B 检索到。必须按 userId 隔离（多租户安全）。
3. **检索不准等于没记忆**：记忆检索和 RAG 一样要优化，不然召不回。
4. **不遗忘导致膨胀**：记忆无限增长，存储和检索成本上升。要淘汰+反思合并。
5. **敏感记忆未脱敏**：记忆里可能有 PII，要脱敏/加密存储。
6. **记忆和会话历史混淆**：会话历史是短期（上下文），记忆是长期（外部存储）。别混。
7. **合规风险**：用户要求删记忆必须能删（被遗忘权），记忆要可按用户批量清除。

## 八、常见面试题

1. **Agent 的短期记忆和长期记忆怎么实现？**
   短期=上下文窗口内的对话历史（快但有限、会丢）；长期=外部存储（向量库/图谱/KV/文件），按需检索注入。长期主流用向量记忆库（RAG 应用于记忆）。检索质量决定长期记忆有没有用。

2. **记忆管理三问是什么？**
   写什么（只记有价值的偏好/决策/事实/教训，不是全存）、怎么找（语义检索注入，要优化检索）、何时忘（淘汰过时+反思合并泛化防膨胀+合规删除）。全存会噪音爆炸。

3. **向量记忆库是什么？**
   把过往对话/事实向量化入库，需要时按当前任务语义检索相关记忆注入上下文。「回忆」=向量检索。本质是 RAG 应用于记忆。

4. **Agent 记忆怎么隔离？**
   按 userId/tenantId 过滤，多用户场景 A 的记忆不能被 B 检索到。向量库用元数据过滤（filterExpression）实现。多租户安全必备。

5. **怎么决定什么值得记？**
   不是全存。用 LLM 判断+提炼：用户偏好、关键决策、事实背景、失败教训值得记，闲聊不记。提炼成简洁记忆条目再存。

6. **记忆怎么防止无限膨胀？**
   主动遗忘：淘汰过时信息（时效数据过期删）+ 反思机制（定期总结合并泛化，如「昨天吃面、前天吃面」->「最近常吃面」）+ 合规删除（被遗忘权）。防止存储和检索成本上升。

7. **Spring AI 怎么实现会话记忆？**
   ChatMemory 抽象，MessageWindowChatMemory 滑动窗口保留最近 N 条，按 conversationId 隔离会话。可换 Redis/JDBC 持久化实现跨重启。长期记忆用 VectorStore 存记忆条目按 userId 过滤检索。

8. **记忆和 RAG 什么关系？**
   记忆的向量库实现本质是 RAG 应用于「记忆」--都是向量化+检索注入。区别：RAG 检索的是外部知识库文档，记忆检索的是用户历史对话/偏好。技术栈相通。

## 九、资料勘误与重点提醒

1. **「记忆就是把对话全存下来」是误区**：全存噪音大、检索不准、费存储。资料常暗示「存越多记越多」越好，实际要选择性记忆（只记有价值的）+ 反思提炼。
2. **「记忆和会话历史是一回事」是混淆**：会话历史是短期（上下文窗口内），记忆是长期（外部持久化存储）。资料偶尔混用导致概念不清。
3. **「记忆检索不需要优化」是错的**：记忆检索和 RAG 一样要混合检索/Rerank/元数据过滤。检索不准等于没记忆。资料常只讲存不讲检索质量。
4. **「长期记忆一定用向量库」不全面**：向量库适合语义记忆，但结构化事实（用户偏好/订单）用 KV/关系库更高效，关联记忆用图谱。要按记忆类型选存储。
5. **「记忆不隔离也行」是严重安全坑**：多用户场景不按 userId 隔离会导致 A 看到 B 的记忆，隐私事故。资料常省略多租户隔离。
6. **被遗忘权**：资料少提。GDPR/合规要求用户可要求删除其记忆，记忆系统必须支持按用户批量清除，否则合规风险。
