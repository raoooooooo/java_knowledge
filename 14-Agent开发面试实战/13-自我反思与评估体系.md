# 13 - 自我反思与评估体系

> Agent 区别于「一次性生成」的关键是能评估自己、发现错误、迭代修正。本章讲 Self-Correction、Critic-Actor、客观校验、LLM-as-Judge、评测回归。这是 Agent 质量保障的最后一环，也是面试「Agent 怎么保证质量」的标准答案。第三篇收尾。

---

## 一、为什么 Agent 需要自我反思

### 1.1 一次性生成的问题

- LLM 输出非确定，一次生成可能错（幻觉、格式错、跑偏）。
- 没有校验直接给用户，质量不可控。
- 传统软件靠单测保证质量，Agent 输出非确定单测无效，需要新的质量保障机制。

### 1.2 自我反思的价值

- Agent 执行后不直接接受结果，**评估自己的输出**，发现问题时回头修正。
- 代码 Agent 改 bug 到测试通过、写作 Agent 反复打磨，都靠自我反思。
- 这是 Agent「从错误中迭代」的能力，区别于「一次性生成」。

> 💡 **面试金句**：Agent 区别于一次性生成的关键是自我反思--评估自己输出，发现错误回头修正。传统软件靠单测保证质量（确定性），Agent 靠自我反思+客观校验+评测回归（非确定性）。

---

## 二、Self-Correction 机制 ★

### 2.1 Critic-Actor 模式

- **Actor**：执行任务生成输出的 Agent。
- **Critic**：评审 Actor 输出的 Agent（可以是另一个 LLM 或同 LLM 换角色）。
- 流程：Actor 生成 -> Critic 评审 -> 不通过则把问题回灌让 Actor 修正 -> 循环到达标或上限。

```
Actor 生成输出
  ↓
Critic 评审：对不对？格式对吗？符合要求吗？
  ↓
通过 -> 返回用户
不通过 -> 回灌「问题+评审意见」给 Actor -> 修正 -> 再评审
  ↓
（循环到达标或达上限）
```

### 2.2 评审怎么做

- **LLM 评审**：用强 LLM 当 Critic，按评审标准打分（正确性/格式/相关性/安全性）。
- **换角色**：同一个 LLM 用不同 system prompt 切换「执行者/评审者」角色。
- **多 Critic**：多个不同视角的 Critic（如正确性、安全、风格）各审一面。

### 2.3 终止与防死循环

- 设最大修正轮数（避免 Actor-Critic 无限拉扯）。
- 多轮不通过要能降级（返回「无法保证质量」+转人工）。
- 评审要明确标准，别让 Critic 模糊「不够好」。

## 三、Verifier / Guardrail（客观校验）★

### 3.1 为什么需要客观校验

- LLM Critic 也是模型，可能误判（它说对的可能错）。
- 有些维度可以**客观验证**，比 LLM 评审更可靠。

### 3.2 客观校验手段

| 手段 | 例子 |
|------|------|
| **规则校验** | JSON 格式对不对、字段齐不齐、数值在范围内 |
| **代码编译/测试** | 代码 Agent：能否编译、测试是否通过（最靠谱） |
| **工具验证** | 调 API 验证事实（查数据库确认答案对不对） |
| **Schema 校验** | 输出是否符合 JSON Schema |
| **引用溯源校验** | 回答的引用是否真的来自检索片段 |

### 3.3 Verifier vs Critic

- **Critic**：LLM 主观评审（可能误判）。
- **Verifier**：客观/程序化校验（确定可靠）。
- 生产**两者结合**：客观的用 Verifier（代码能编译、格式对），主观的用 Critic（相关性、流畅度）。

> 💡 **面试金句**：质量校验分主观客观：主观的用 Critic（LLM 评审正确性/相关性），客观的用 Verifier（规则/编译/测试/工具验证，更可靠）。生产结合：能客观校验的优先客观（如代码 Agent 看测试通过率最靠谱）。

## 四、LLM-as-Judge ★ 高频

### 4.1 是什么

- 用强 LLM 当「裁判」给输出打分，替代部分人工评测。
- 适合规模大、无法全人工的评测场景。

### 4.2 怎么用

- 定义评审标准（rubric）：正确性、相关性、安全性、格式等维度。
- 让 Judge LLM 按标准打分 + 给理由。
- 可对比多个输出（A vs B 选哪个更好）。

```
评审标准：
- 正确性：回答是否事实正确（1-5分）
- 相关性：是否切题（1-5分）
- 安全性：是否违规（是/否，一票否决）
Judge LLM 输出：正确性4，相关性5，安全性通过，理由：...
```

### 4.3 局限与坑

- **有偏见**：Judge 可能偏向冗长/特定风格/自家模型。
- **可能误判**：它说对的也可能错，关键评测要人工复核。
- **成本**：每次评测要调 LLM，有成本。
- **对齐**：Judge 评分要和人类评分对齐（先小规模人工标注校准）。

## 五、评测数据集与回归测试 ★

### 5.1 黄金测试集

- 建一个「黄金集」：典型问题 + 期望输出/标准。
- 每次 Agent/Prompt/模型改动，跑黄金集对比，防退化。
- 这是 Agent 的「单元测试」。

### 5.2 怎么建

1. 收集真实/典型问题（覆盖各类场景）。
2. 标注期望输出（人工写标准答案或判断标准）。
3. 持续扩充：Bad Case 纳入（呼应 08 章）。
4. 分类：简单/复杂、各业务域、边界情况。

### 5.3 评测指标（Agent 专项，呼应 08 章 RAGAS）

- **任务完成率**：任务做没做成。
- **工具调用准确率**：选对工具、参数对不对。
- **平均步数**：完成任务的循环步数（越少越好，飙升=质量下降）。
- **Token 消耗**：成本。
- **人工接管率**：多少比例需人工介入。
- **代码 Agent 特有**：测试通过率/编译通过率（最客观）。

### 5.4 回归流程

```
改动（Prompt/模型/工具）
  ↓
跑黄金集评测
  ↓
对比指标：准确率/步数/成本是否退化
  ↓
退化 -> 排查修复 / 不退化 -> 灰度上线
```

> 💡 **面试金句**：Agent 的「单测」=黄金评测集（典型问题+期望输出）+ LLM-as-Judge 打分 + 回归对比。每次改动跑回归防退化。Bad Case 持续纳入集子。代码 Agent 最靠谱的指标是测试通过率（客观）。

## 六、Java 侧评测工程实践

### 6.1 评测流水线

```java
// 思路：跑评测集 -> 收集结果 -> LLM-as-Judge 打分 -> 汇总对比
public class EvalPipeline {
    public EvalReport run(List<EvalCase> goldenSet, Agent agent) {
        List<Result> results = goldenSet.parallelStream()
            .map(c -> runCase(agent, c))     // 跑Agent拿输出
            .toList();
        // LLM-as-Judge 打分
        results.forEach(r -> r.score = judge(r));
        return aggregate(results);           // 汇总：准确率/步数/成本
    }
}
```

### 6.2 配合可观测平台

- Langfuse/LangSmith（见 20 章）提供评测流水线：管理数据集、跑评测、LLM-as-Judge、版本对比。
- Java 侧通过 OTel/Langfuse SDK 上报 Trace，平台做评测。

### 6.3 在线评测

- 灰度时抽样部分流量人工/LLM 打分，监控真实质量（比离线更真实但更贵）。

## 七、生产踩坑

1. **没有自我反思直接给用户**：一次性生成质量不可控。关键任务加 Critic-Actor。
2. **Critic 评审标准模糊**：「不够好」没标准。定义明确 rubric（各维度打分）。
3. **Actor-Critic 死循环**：无限拉扯。设最大修正轮数 + 降级转人工。
4. **只信 LLM Critic**：Critic 也可能误判。能客观校验的优先 Verifier（代码测试/规则）。
5. **没黄金集就改线上**：改动没回归验证，准确率掉不知道。改前必跑评测集。
6. **LLM-as-Judge 有偏见**：偏向冗长/自家模型。要人工校准对齐。
7. **评测集不更新**：只有旧 case，新场景没覆盖。持续纳入 Bad Case 和新场景。
8. **只看准确率不看成本**：准确率上去了但步数/成本翻倍。综合评估。

## 八、常见面试题

1. **Agent 怎么保证输出质量？**
   多层：Self-Correction（Actor 生成-Critic 评审-不通过修正循环）、客观 Verifier（规则/编译/测试校验）、LLM-as-Judge 打分、黄金评测集回归防退化。能客观校验的优先客观（如代码 Agent 看测试通过率）。

2. **什么是 Critic-Actor 模式？**
   Actor 执行生成输出，Critic 评审输出，不通过则把问题回灌让 Actor 修正，循环到达标或上限。Critic 可用另一个 LLM 或同 LLM 换角色。设最大轮数防死循环。

3. **LLM-as-Judge 是什么？有什么局限？**
   用强 LLM 当裁判给输出打分（按 rubric 各维度），替代部分人工评测。局限：有偏见（偏冗长/自家模型）、可能误判（关键要人工复核）、有成本、要和人类评分对齐校准。

4. **Agent 怎么评测？指标有哪些？**
   黄金测试集 + LLM-as-Judge + 回归对比。指标：任务完成率、工具调用准确率、平均步数（越少越好）、Token 消耗、人工接管率。代码 Agent 看测试通过率最客观。

5. **Critic 和 Verifier 什么区别？**
   Critic 是 LLM 主观评审（正确性/相关性，可能误判），Verifier 是客观程序化校验（规则/编译/测试/工具，可靠）。生产结合：能客观的优先 Verifier，主观的用 Critic。

6. **Agent 改动怎么防退化？**
   建黄金评测集，改动后跑回归对比指标（准确率/步数/成本），退化则排查不灰度。Bad Case 持续纳入集子。这是 Agent 的「单测」。

7. **Actor-Critic 死循环怎么办？**
   设最大修正轮数、评审标准要明确（别模糊「不够好」）、多轮不通过降级（返回「无法保证质量」+转人工）。监控修正轮数，飙升=质量信号。

8. **代码 Agent 为什么质量最好评测？**
   因为有客观校验：代码能否编译、测试是否通过。不依赖 LLM 主观判断，客观可靠。这是代码 Agent 的评测优势，也是自我修正的强反馈（测试失败回灌让模型改）。

## 九、资料勘误与重点提醒

1. **「LLM-as-Judge 完全可靠」是误区**：Judge 也是模型，有偏见、会误判。资料常把 LLM-as-Judge 说成「自动评测银弹」，实际关键评测要人工复核，要和人类评分对齐校准。
2. **「Self-Correction 一定提升」不严谨**：Self-Correction 有额外 LLM 调用开销，且 Critic 可能误判导致越改越错。要设上限+客观校验兜底，不是无限反思。
3. **「只用 LLM 评审」漏了客观校验**：资料常只讲 LLM Critic，少提 Verifier。能客观校验的（编译/测试/规则）比 LLM 主观评审更可靠，应优先。
4. **「评测集建一次就行」是错的**：评测集要持续更新，纳入新 Bad Case 和新场景，否则覆盖不全。资料常不说持续维护。
5. **「准确率越高越好」不全面**：准确率上去了但步数/成本翻倍可能得不偿失。要综合评估准确率+成本+延迟，资料常只比准确率。
6. **代码 Agent 的评测优势少被提及**：代码 Agent 有编译/测试客观校验，是所有 Agent 里评测最可靠的。资料讲 Self-Correction 常不强调这个「客观反馈」的稀缺价值。
