# 23 - Agent 评测与灰度发布

> Agent 非确定，传统软件的单测+灰度套路要改造。本章讲评测体系、黄金数据集、灰度发布、注册中心回滚。呼应 13 章（自我反思评估）和 08 章（RAGAS），讲生产发布流程。面试「Agent 怎么保证质量、怎么上线」必考。

---

## 一、Agent 评测体系 ★

### 1.1 为什么要评测

- Agent 输出非确定，改个 Prompt/模型可能准确率掉 20%，没评测就改线上是事故。
- 上线后要持续监控质量（在线评测），不能只靠离线。
- 评测是 Agent 的「单元测试」+「集成测试」。

### 1.2 评测层次（呼应 13 章）

| 层次 | 方法 | 说明 |
|------|------|------|
| **离线评测** | 评测集 + 指标 | 改动前先验证不退化 |
| **LLM-as-Judge** | 强模型当裁判打分 | 自动化、规模大、有偏见 |
| **规则/程序校验** | 断言、正则、测试通过率 | 客观可验证（代码 Agent） |
| **人工评测** | 标注员评分 | 金标准但慢贵 |
| **在线 A/B** | 灰度对比真实指标 | 最终真相 |

### 1.3 Agent 专项指标（呼应 13 章）

- **任务完成率**：任务做没做成。
- **工具调用准确率**：选对工具、参数对不对。
- **平均步数**：越少越好（飙升=质量下降，09 章）。
- **Token 消耗**：成本。
- **人工接管率**：多少比例需人工介入。
- **代码 Agent 特有**：测试通过率/编译通过率（最客观）。
- **RAG 专项**：RAGAS 四指标（08 章）。

## 二、黄金数据集与回归 ★

### 2.1 黄金测试集

- 典型问题 + 期望输出/判断标准。
- 覆盖各类场景（简单/复杂、各业务域、边界情况、历史 Bad Case）。
- 持续扩充：上线后 Bad Case 纳入（08 章）。

### 2.2 怎么建

1. 收集真实/典型问题（覆盖各类场景）。
2. 标注期望输出（人工标准答案或判断标准）。
3. 分类：按业务域/难度/边界。
4. 持续扩充：Bad Case、新场景纳入。
5. 版本化：数据集也要版本管理。

### 2.3 回归测试

```
改动（Prompt/模型/工具/流程）
  ↓
跑黄金集评测
  ↓
对比指标：准确率/步数/成本是否退化
  ↓
退化 -> 排查修复 / 不退化 -> 灰度上线
```

- 每次 Prompt 改动、模型升级、工具调整都要跑回归。
- 配合 LLM-as-Judge 自动打分 + 关键指标人工复核。

> 💡 **面试金句**：Agent 的「单测」=黄金评测集（典型问题+期望输出）+ LLM-as-Judge 打分 + 回归对比。每次改动跑回归防退化。Bad Case 持续纳入集子。代码 Agent 最客观的指标是测试通过率。

## 三、在线 A/B 与灰度 ★

### 3.1 在线 A/B

- 新老版本各跑一部分流量，对比真实指标（完成率/成本/接管率/用户满意度）。
- 比离线更真实（真实用户/真实问题），但更贵慢。

### 3.2 灰度发布

- 新版本小流量先上（如 5% -> 20% -> 50% -> 100%）。
- 每阶段监控指标，达标才扩量，不达标回滚。
- 配合评测集（离线已验证）+ 在线指标（真实表现）双保险。

### 3.3 发布流程

```
1. 开发 -> 离线评测集验证不退化
2. 注册新版本到注册中心，打版本号
3. 小流量灰度（5%），监控指标
4. 达标扩量（20% -> 50%）
5. 全量
6. 出问题一键回滚到老版本
```

## 四、注册中心与版本管理 ★

### 4.1 Agent 注册中心（呼应 13 章）

- 类比微服务注册中心，但注册的是 **Agent 元信息**：
  - 名称、能力、版本、端点。
  - 依赖的模型/工具/MCP Server/数据源。
  - Schema（输入输出）。
- 调用方从中心发现可用 Agent。

### 4.2 版本管理

- 多版本共存：v1（老）、v2（新灰度）。
- 灰度按版本路由流量。
- 出问题一键切回老版本（回滚）。

### 4.3 依赖管理

- 记录 Agent 依赖哪些模型/工具/MCP Server。
- 依赖变更（模型升级/工具改）要评估影响、跑评测。
- A2A 的 Agent Card 是去中心化形式（13 章）。

### 4.4 配置动态化

- Prompt/参数/工具配置放配置中心（Nacos/Apollo）。
- 不重启即可改配置、切换版本、灰度。
- 配合权限：谁能在什么时候改什么。

## 五、回滚

### 5.1 什么时候回滚

- 质量指标退化（完成率掉、接管率涨、人工投诉）。
- 成本异常飙升（token 爆）。
- 安全事件（泄露/违规）。
- 依赖故障（模型/工具挂）。

### 5.2 回滚机制

- 版本可配置，一键切回老版本（配置中心改路由）。
- Prompt 模板版本化，回滚就是切回老模板。
- 数据库变更要可逆（向前兼容 schema）。
- 回滚要快：监控告警 -> 决策 -> 切版本，分钟级。

## 六、生产踩坑

1. **没评测就改线上**：改 Prompt/模型不跑回归，准确率掉不知道。改前必跑评测集。
2. **评测集不更新**：只有旧 case，新场景没覆盖。持续纳入 Bad Case。
3. **只看准确率**：漏了成本/步数/接管率。综合评估。
4. **灰度没监控**：灰度时不盯指标，出问题不知道。每阶段监控。
5. **回滚慢**：出问题要改代码部署回滚，慢。配置中心切版本分钟级。
6. **LLM-as-Judge 有偏见**：偏向冗长/自家模型。关键指标人工复核。
7. **版本不可共存**：新版本 schema 不兼容老，回滚困难。向前兼容。

## 七、常见面试题

1. **Agent 怎么评测？**
   多层次：离线评测集+指标、LLM-as-Judge 自动打分、规则/程序校验（代码 Agent 测试通过率最客观）、人工评测、在线 A/B。指标：任务完成率、工具准确率、平均步数、Token 消耗、人工接管率。RAG 用 RAGAS。

2. **什么是黄金数据集？怎么建？**
   典型问题+期望输出/判断标准。覆盖各类场景+历史 Bad Case，持续扩充、版本化。每次改动跑回归对比指标防退化。是 Agent 的「单测」。

3. **Agent 怎么灰度发布？**
   离线评测验证 -> 注册新版本到注册中心 -> 小流量灰度（5%->20%->50%）监控指标 -> 达标全量，不达标回滚。配置中心动态切版本不重启。

4. **Agent 注册中心是干什么的？**
   注册 Agent 元信息（能力/版本/端点/依赖模型工具/Schema），支持发现、版本管理、灰度、回滚。类比微服务注册中心，A2A 的 Agent Card 是去中心化形式。

5. **什么情况回滚？怎么回滚？**
   质量退化、成本异常、安全事件、依赖故障。回滚要快：配置中心切老版本分钟级。Prompt 模板版本化切回老模板，schema 向前兼容，数据库变更可逆。

6. **Agent 改动怎么防退化？**
   黄金评测集跑回归：改动后对比准确率/步数/成本，退化则排查不灰度。Bad Case 持续纳入集子。代码 Agent 看测试通过率最客观。配合在线 A/B 验证真实表现。

7. **LLM-as-Judge 有什么局限？**
   有偏见（偏冗长/自家模型）、可能误判、有成本、要和人类评分对齐校准。关键评测要人工复核，不是全自动。

8. **你项目 Agent 怎么发布的？**
   （参考）黄金评测集+LLM-as-Judge 离线验证 -> 注册到 Nacos 配置中心打版本 -> 小流量灰度监控完成率/成本/接管率 -> 达标全量。出问题切老版本回滚。Prompt 模板版本化管理在配置中心。

## 九、资料勘误与重点提醒

1. **「Agent 不需要单测」是误区**：资料常暗示 Agent 非确定没法测。实际要黄金评测集+LLM-as-Judge 做回归，是 Agent 的「单测」，防退化必备。
2. **「灰度只看准确率」不全面**：资料讲灰度常只比准确率。实际还要看成本（token）、延迟、人工接管率、用户满意度，综合评估。
3. **「LLM-as-Judge 完全可靠」是误区**：Judge 有偏见会误判。资料常说成自动评测银弹，实际关键要人工复核+对齐校准。
4. **回滚机制少强调**：资料讲发布少讲回滚。Agent 出问题概率比传统软件高，回滚要快（配置中心切版本分钟级），不是改代码部署。
5. **版本共存少提及**：资料讲版本管理常不说多版本共存+向前兼容。实际灰度要新老版本共存，schema 不兼容老版本回滚困难。
6. **依赖管理少提**：资料讲 Agent 注册少讲依赖（模型/工具/MCP）。依赖变更要评估影响跑评测，否则牵一发动全身。
