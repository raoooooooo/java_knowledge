# 12 - 工具调用工程化

> 04 章讲了 Function Calling 原理和基础用法。本章从「能用」到「好用」：工具怎么设计模型才选得对、工具多了怎么治理、错误怎么处理、MCP 怎么集成。这是 Agent 工程化的核心一环。13 章讲了 MCP 协议，本章讲 Java 落地。

---

## 一、工具设计三原则 ★ 必考

### 1.1 描述即接口（Description）

- 模型靠 `description` 选工具。描述不清就选错或不用。
- 描述要说清：**做什么、什么时候用、返回什么**。

```java
// ❌ 差：模型不知道何时用、查什么
@Tool(description = "查询")
String query(String input) { ... }

// ✅ 好：说清做什么、何时用、返回什么
@Tool(description = "根据订单号查询订单的物流状态，返回当前位置和预计送达时间。用于用户询问订单到哪了、什么时候到")
String getLogistics(@ToolParam(description="订单号，格式ORD开头") String orderId) { ... }
```

### 1.2 参数要简单（Simple Params）

- 参数越少越好，能默认就默认。复杂参数模型容易填错。
- 用枚举/约束限制取值，减少出错。
- 参数必须有 description，模型才知道填什么。

```java
@Tool(description = "搜索商品")
String search(
    @ToolParam(description = "搜索关键词") String keyword,
    @ToolParam(description = "排序方式", required = false) SortOrder sort  // 枚举+可选+默认
) { ... }
```

### 1.3 错误要可读（Readable Errors）

- 工具失败别返回 null 或抛异常崩循环，返回**可读错误**让模型修正重试。
- 错误信息要告诉模型「怎么改」而不只是「错了」。

```java
@Tool(description = "查订单")
public String getOrder(String orderId) {
    if (!orderId.startsWith("ORD")) {
        return "{\"error\":\"订单号格式错误，应以ORD开头，请确认订单号\"}";  // 可读+提示怎么改
    }
    Order order = orderService.getById(orderId);
    if (order == null) {
        return "{\"error\":\"订单不存在，请确认订单号是否正确\"}";
    }
    return toJson(order);
}
```

> 💡 **面试金句**：工具设计三原则：描述即接口（说清做什么/何时用/返回什么）、参数要简单（少+枚举约束+默认值）、错误要可读（返回可读错误让模型修正重试，不是 null/异常崩循环）。

## 二、工具治理 ★ 工具多了的问题

### 2.1 工具过多的危害

- **注意力稀释**：模型在几十个工具里选容易选错。
- **上下文占用**：每个工具的 schema 都占 token。
- **混淆**：功能相似的工具模型分不清。

### 2.2 治理手段

| 手段 | 说明 |
|------|------|
| **按场景分组** | 工具按业务域分组，按需加载某组 |
| **按需加载** | 平时只给索引，需要时才展开（Skill 机制） |
| **路由分流** | 先用路由 Agent/分类器判断类型，再加载对应工具集 |
| **功能合并** | 相似工具合并成一个带参数的 |
| **限制数量** | 单次暴露工具建议不超过 10~20 个 |

### 2.3 Skill 机制（渐进式披露）

- 平时只给 Agent 一个「工具索引」（名字+一句话描述），Agent 判断需要时才加载完整工具定义。
- 省 token、减干扰、可扩展。
- Claude Code 的 Skill 就是此机制（13 章已讲）。

## 三、错误处理与自我修正

### 3.1 分层错误处理

| 错误类型 | 处理 |
|---------|------|
| 参数错误 | 返回可读错误让模型改参重试 |
| 依赖服务失败 | 重试 + 降级（返回缓存/默认值） |
| 权限不足 | 返回「无权限」让模型换策略或告知用户 |
| 超时 | 超时重试，多次失败放弃 |
| 业务规则不满足 | 返回业务原因让模型理解 |

### 3.2 让模型自我修正

- 工具失败不是简单重试，是把错误回灌让模型**据错误调整**。
- 例：订单号格式错 -> 模型下次会修正格式；无权限 -> 模型可能换「查公开信息」工具。
- 设重试次数上限，避免无限重试。

### 3.3 幂等性

- 工具可能被重复调用（模型重试/循环），写操作要幂等：
  - 下单：用业务幂等键，重复调用不重复下单。
  - 发消息：用 requestId 去重。
- 非幂等写操作必须加确认（人在环）。

## 四、MCP 集成实战 ★

### 4.1 为什么用 MCP

- 04 章讲过：MCP 是工具标准协议，把 M×N 集成变 M+N。
- MCP Server 写一次，任何支持 MCP 的 Agent（Claude Code/Cursor/你的 Agent）都能用。
- 官方有大量预置 Server：文件系统、GitHub、数据库、Slack 等。

### 4.2 MCP 架构回顾（呼应 06 章）

```
Host（你的Agent应用）
  └─ Client（每个Server一个，一对一）
        │ MCP协议(stdio/Streamable HTTP)
        ▼
    MCP Server（暴露 Tools/Resources/Prompts）
        │
        ▼
    真实工具（文件/DB/API）
```

### 4.3 Java 侧 MCP 集成

```java
// Spring AI 的 MCP Client 支持
// 配置一个 MCP Server（如本地文件系统Server）
@Bean
public McpSyncClient fileSystemMcpClient() {
    return McpClient.sync()
        .stdio("npx", "@modelcontextprotocol/server-filesystem", "/data")
        .build();
}

// 把 MCP Server 的工具注册给 ChatClient
@Bean
public ToolCallbackProvider mcpTools(List<McpSyncClient> clients) {
    return SyncMcpToolCallbackProvider.from(clients);
}

// 使用：MCP Server 暴露的 Tools 自动可用
chatClient.prompt().user(question).tools(mcpTools).call();
```

- Spring AI 提供 MCP Client，stdio/HTTP 传输都支持。
- MCP Server 的 Tools 自动转成 Spring AI 的 ToolCallback，和本地 `@Tool` 一样用。

### 4.4 自己开发 MCP Server

- 需要给团队/外部提供工具能力时，开发 MCP Server。
- 用 Java MCP SDK（spring-ai-mcp-server）或 Python/TS SDK。
- 暴露 Tools（函数）/Resources（数据）/Prompts（模板）。

> 💡 **面试金句**：MCP 让工具即插即用--Server 写一次处处可用。Spring AI 的 MCP Client 把 MCP Server 的 Tools 自动转成 ToolCallback，和本地 @Tool 统一使用。自建团队工具链时开发 MCP Server 是趋势。

## 五、动态工具发现

### 5.1 静态 vs 动态

- **静态**：工具在编译时固定（`@Tool` 注解）。
- **动态**：运行时从 MCP Server / 配置中心 / 数据库加载工具定义。
- 动态适合：工具经常变、多租户不同工具集、插件化场景。

### 5.2 实现

```java
// 从配置中心/DB 动态加载工具定义
List<ToolDefinition> tools = toolRegistry.loadByTenant(tenantId);
// 动态注册给 ChatClient
chatClient.prompt().user(question).tools(dynamicTools).call();
```

- 配合 MCP 天然支持动态：连上新 Server，工具自动可用。

## 六、Spring AI / LangChain4j @Tool 实战对比

### 6.1 Spring AI

```java
@Component
public class OrderTools {
    @Tool(description = "查订单物流状态")
    public String getLogistics(@ToolParam(description="订单号") String orderId) { ... }
}
// chatClient.prompt().user(q).tools(orderTools).call()
```

### 6.2 LangChain4j

```java
class OrderTools {
    @Tool("查订单物流状态")
    String getLogistics(@P("订单号") String orderId) { ... }
}
// AiServices.builder().tools(new OrderTools()).build()
```

- 两者思路一致：注解声明工具，框架自动生成 schema 处理循环。
- Spring AI 集成 Spring 生态更顺（`@Component` 注入）；LangChain4j 更轻量灵活。

## 七、生产踩坑

1. **描述不清模型不用工具**：描述太简单模型不知何时用。描述说清做什么/何时用/返回什么。
2. **参数复杂填错**：参数多/类型复杂模型易填错。减少参数、用枚举、加默认值。
3. **工具异常崩循环**：异常冒泡打断。catch 返回可读错误让模型修正。
4. **工具太多选错**：单次暴露太多。分组/按需加载/路由分流，控制在 10~20 个。
5. **非幂等写操作重复执行**：模型重试导致重复下单/发消息。写操作幂等 + 危险操作确认。
6. **工具返回太大**：大 JSON 全回灌费 token。裁剪只留关键字段。
7. **危险工具无确认**：删数据/发钱/外发让模型自主执行。必须人在环确认。
8. **MCP Server 不可用没降级**：MCP Server 挂了导致工具全失效。要降级/重试/告警。

## 八、常见面试题

1. **工具设计有哪些原则？**
   三原则：描述即接口（说清做什么/何时用/返回什么）、参数要简单（少+枚举约束+默认值+参数描述）、错误要可读（返回可读错误让模型修正重试，不是 null/异常崩循环）。

2. **工具太多模型选错怎么办？**
   按场景分组、按需加载（Skill 机制）、路由 Agent 先分流、功能合并、限制单次暴露数量（10~20 个）。工具过多注意力稀释。

3. **工具失败怎么处理？**
   catch 异常返回可读错误（含怎么改的提示），让模型据错误修正参数重试。设重试次数上限。不是简单重试也不是崩循环。写操作要幂等防重复执行。

4. **MCP 在工程里怎么用？**
   Spring AI 的 MCP Client 连接 MCP Server，Server 暴露的 Tools 自动转成 ToolCallback 和本地 @Tool 统一使用。stdio 本地/HTTP 远程。自建团队工具链时开发 MCP Server，写一次处处可用。

5. **Function Calling 和 MCP 什么关系？**
   互补。Function Calling 是模型层（输出结构化调用），MCP 是协议层（工具发现/调用标准化）。MCP Server 的工具最终靠 Function Calling 让模型调。MCP 把 M×N 集成变 M+N。

6. **工具为什么要幂等？**
   模型可能重试/循环调用同一工具，非幂等写操作（下单/发消息）会重复执行。用业务幂等键/requestId 去重。非幂等危险操作必须加人在环确认。

7. **动态工具发现是什么？什么时候用？**
   运行时从 MCP Server/配置中心/DB 加载工具定义（非编译时固定）。适合工具经常变、多租户不同工具集、插件化场景。MCP 天然支持动态（连新 Server 工具自动可用）。

8. **你项目里工具怎么设计的？**
   （参考）Spring AI @Tool 声明，描述说清做什么/何时用，参数用枚举约束+默认值，错误返回可读 JSON 让模型修正。危险工具（下单/退款）加人在环。工具结果裁剪控 token。接了 MCP Server 复用通用工具（文件/Git）。

## 九、资料勘误与重点提醒

1. **「工具越多越强大」是误区**：资料常把「支持上百工具」当卖点。实际工具过多模型选错（注意力稀释），要分组/按需加载。单次 10~20 个为宜。
2. **「工具失败重试就行」是传统思维**：Agent 应把错误回灌让模型自我修正，不是原样重试。资料常只讲重试不讲回灌错误让模型改。
3. **「工具返回越全越好」是错的**：返回大 JSON 全回灌费 token 稀释注意力。要裁剪只留关键字段。资料示例常返回完整对象不裁剪。
4. **「MCP 取代 @Tool」是误解**：MCP 和本地 @Tool 是互补的工具来源，Spring AI 统一成 ToolCallback。资料偶尔暗示 MCP 后不用写本地工具，不对。
5. **「写操作不用幂等」是严重坑**：模型重试导致重复下单/发消息是真实事故。资料常不提幂等性，生产写操作必须幂等。
6. **「危险工具让模型自主」是安全事故**：删数据/发钱/外发必须人在环确认。资料示例常让 Agent 直接执行危险操作，生产绝不行。
