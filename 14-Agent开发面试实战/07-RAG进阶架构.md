# 07 - RAG 进阶架构

> 普通 RAG 是「检索-拼-答」固定流水线，进阶架构让它更聪明：能判断要不要检索、能纠错、能回答全局问题、能多跳推理。这些是面试区分度题，答上来明显加分。

---

## 一、Self-RAG（自适应 RAG）

### 1.1 普通 RAG 的问题

- 不管什么问题都去检索（浪费：简单问题不必检索）。
- 不管检索结果好不好都用（错：检索到垃圾也硬答，导致幻觉）。

### 1.2 Self-RAG 思路

- 让模型**自己判断**：
  - 这个问题要不要检索？（事实类要，闲聊不要）
  - 检索结果相不相关？
  - 回答有没有被检索内容支持？
- 用「反思 token」控制：retrieve / relevant / support 等标记。
- 按需检索、自我批判，检索不到或质量差就换策略或坦诚说「不知道」。

> 💡 **面试金句**：Self-RAG 让模型自己判断「要不要检索、结果相不相关、回答有没有支撑」，按需检索、自我批判，避免无脑检索和硬答幻觉。

---

## 二、CRAG（Corrective RAG，纠错 RAG）

### 2.1 思路

- 检索后**评估检索质量**：
  - 质量高（相关）-> 直接用。
  - 质量低（不相关）-> 改写查询重试，或回退到 **web 搜索**补充。
- 三档：correct / ambiguous / incorrect，对应不同处理。

### 2.2 价值

- 检索到垃圾时不再硬答，而是纠错（改写/换源/web 搜索），降低幻觉。
- 比 Self-RAG 更聚焦「检索后纠错」这一环节。

> 💡 **面试金句**：CRAG 检索后评估质量，质量低则改写查询或回退 web 搜索，避免用垃圾上下文硬答。Self-RAG 关注全流程自适应，CRAG 聚焦检索后纠错。

---

## 三、RAPTOR（递归摘要检索）

### 3.1 痛点

- 普通 RAG 只检索叶子层（具体段落），回答「整体讲了什么主题」这种全局问题很差--因为只捞片段，没全局视角。

### 3.2 RAPTOR 思路

- 把文档做**多层级摘要建树**：叶子是原文段落，往上是摘要，再往上是摘要的摘要。
- 检索时可同时命中「细节段落」和「高层摘要」。
- 适合需要跨文档整体理解、全局总结的问题。

```
[根摘要：整篇主题]        <- 全局问题命中这里
   /        \
[摘要层1]  [摘要层1]
  / \        / \
[段落][段落][段落][段落]   <- 细节问题命中这里
```

---

## 四、GraphRAG ★ 高频进阶

### 4.1 痛点

- 传统 RAG 是「局部检索」，回答**全局性/总结性**问题（如「这批文档主要讲什么主题」「A 和 B 什么关系」）很差--它只捞片段，拼不出全局。

### 4.2 GraphRAG（Microsoft）思路

1. 用 LLM 从文档**抽取实体和关系，构建知识图谱**。
2. 对图做**社区聚类**（Leiden 算法），生成各社区摘要。
3. 查询时：
   - **Global Search**：用社区摘要回答全局/总结类问题。
   - **Local Search**：从相关实体出发沿图扩展回答具体问题。

### 4.3 价值与代价

- 价值：能回答全局性问题（传统 RAG 的盲区），多跳关系推理强。
- 代价：构建图谱极贵（大量 LLM 调用），但建一次可多次查询。

### 4.4 LightRAG

- GraphRAG 的轻量替代：构建成本更低、支持增量更新、融合图结构+向量检索。
- 适合预算有限但要图增强能力的场景。

> 💡 **面试金句**：GraphRAG 解决传统 RAG 答不了「全局/总结」问题的盲区--先抽实体关系建知识图谱+社区摘要，全局问题用社区摘要答，局部问题沿图扩展答。代价是建图贵。

---

## 五、Agentic RAG ★ 趋势热点

### 5.1 思路

- 把 RAG 升级为 **Agent**：模型自主决定查什么、查几次、要不要换库、要不要再检索、检索结果够不够。
- 多跳检索+反思：第一轮检索不够，Agent 自己改写 Query 再查，直到信息够了才答。
- 本质：RAG + ReAct/Reflexion（Agent 范式，见 09 章）。

### 5.2 和普通 RAG 的区别

| 维度 | 普通 RAG | Agentic RAG |
|------|---------|-------------|
| 检索次数 | 固定 1 次 | 自主多次 |
| 查询 | 用户原始 Query | 自主改写 |
| 是否换源 | 固定 | 自主路由 |
| 是否反思 | 否 | 检索不够会再查 |
| 复杂度 | 简单 | 高（调用多、慢、贵） |

### 5.3 适用

- 复杂多跳问题（「A 公司去年收购的那家，其 CEO 之前在哪工作」要查多次）。
- 简单问答用普通 RAG 即可，别过度设计。

> 💡 **面试金句**：Agentic RAG 是 RAG + Agent：模型自主决定查什么、查几次、换不换库、够不够，多跳检索+反思。复杂多跳问题才用，简单问答普通 RAG 足够，别过度设计。

---

## 六、多跳检索与多源融合

### 6.1 多跳检索

- 问题需要多步推理，每步依赖上一步结果再检索。
- 例：「这个病的常用药的副作用」-> 先查病->查药->查副作用，三跳。
- Agentic RAG 天然适合多跳（Agent 自主迭代）。

### 6.2 多源融合

- 一个问题可能要查多个源：文档库+数据库+API+web。
- 查询路由决定查哪个源，结果融合后给 LLM。
- 注意不同源结果的相关性可比性（用 RRF 或 LLM 判断）。

---

## 七、选型建议（别过度设计）

```
简单问答             -> 普通 RAG（混合检索+Rerank）
要判断要不要检索      -> Self-RAG
检索质量不稳要纠错     -> CRAG
要回答全局/总结问题    -> GraphRAG / RAPTOR
复杂多跳问题          -> Agentic RAG
```

- ⚠️ **最大陷阱**：复杂度上去了但收益没上去。多数业务问题普通 RAG（混合+Rerank）就够，Agentic RAG/GraphRAG 贵且慢，只在确有需要时用。

---

## 八、生产踩坑

1. **过度设计**：简单问答上 GraphRAG/Agentic RAG，贵慢还可能更差。按问题复杂度选架构。
2. **GraphRAG 建图成本爆炸**：抽取实体关系大量 LLM 调用，大文档库建一次很贵。评估 ROI，可能只对核心文档建图。
3. **Agentic RAG 死循环**：Agent 一直「信息不够」反复查。加最大跳数/超时兜底。
4. **Self-RAG 判断不准**：模型可能误判「要不要检索」。要有兜底（关键事实强制检索）。
5. **多跳检索误差累积**：每跳都可能错，错误向后放大。每跳设置信度阈值，低置信度回退或坦诚。
6. **CRAG 回退 web 搜索**：web 内容质量不可控，要审核，别直接用 web 结果答敏感问题。

## 九、常见面试题

1. **Self-RAG 和普通 RAG 什么区别？**
   普通 RAG 无脑检索硬答；Self-RAG 让模型自己判断要不要检索、结果相不相关、回答有没有支撑，按需检索、自我批判，避免无脑检索和硬答幻觉。

2. **CRAG 解决什么问题？**
   检索质量差时不用垃圾上下文硬答。检索后评估质量，质量低则改写查询或回退 web 搜索，纠错后再答。聚焦检索后纠错，比 Self-RAG 更专。

3. **GraphRAG 解决了什么传统 RAG 解决不了的问题？**
   全局/总结性问题。传统 RAG 只捞局部片段答不了「这批文档整体讲什么」「A 和 B 什么关系」；GraphRAG 抽实体关系建知识图谱+社区摘要，全局问题用摘要答，局部问题沿图扩展答。代价是建图贵。

4. **Agentic RAG 是什么？什么时候用？**
   RAG + Agent：模型自主决定查什么、查几次、换不换库、够不够，多跳检索+反思。适合复杂多跳问题。简单问答普通 RAG 够，别过度设计。

5. **RAPTOR 解决什么？**
   传统 RAG 只检索叶子层段落，答不了全局问题。RAPTOR 建多层级摘要树，检索时同时命中细节段落和高层摘要，适合跨文档整体理解。

6. **这些进阶架构怎么选？**
   按问题复杂度：简单问答用普通 RAG（混合+Rerank）；要判断检索用 Self-RAG；检索质量不稳用 CRAG；答全局问题用 GraphRAG/RAPTOR；复杂多跳用 Agentic RAG。多数业务普通 RAG 够，别过度设计。

7. **GraphRAG 和 LightRAG 区别？**
   GraphRAG（微软）功能全但建图贵；LightRAG 是轻量替代，构建成本低、支持增量更新、融合图+向量检索，适合预算有限场景。

8. **多跳检索怎么实现？有什么坑？**
   Agent 迭代：每跳基于上一步结果改写 Query 再检索。坑：误差累积（每跳可能错，错误放大），要设置信度阈值；死循环（一直说信息不够），要加最大跳数兜底。

## 十、资料勘误与重点提醒

1. **「进阶架构一定更好」是误区**：资料常把 GraphRAG/Agentic RAG 说成「升级版」。实际它们贵且慢，多数业务普通 RAG 够用。按问题复杂度选，别过度设计。
2. **「Self-RAG 完全避免幻觉」不严谨**：Self-RAG 靠模型自我判断，判断本身可能错。是降低非杜绝，要有兜底（关键事实强制检索）。
3. **「GraphRAG 取代传统 RAG」是误解**：GraphRAG 擅长全局/关系问题，局部细节问题传统 RAG 更直接高效。两者常共存：局部用向量 RAG，全局用图。
4. **「CRAG 回退 web 就安全」有坑**：web 内容质量不可控、可能有错误/有害信息。资料少提，实际要审核 web 结果，敏感场景慎用。
5. **「Agentic RAG 检索越多越准」不严谨**：多跳可能误差累积反而更错。每跳要置信度评估，够就停，别无限查。
6. **LightRAG 不是「阉割版 GraphRAG」**：资料偶尔贬低 LightRAG。实际它增量更新+图向量融合是正交优势，适合数据频繁变更场景，不是单纯阉割。
