# 17 - 复杂流程编排

> 简单 Agent 用 Advisor 链或 AiServices 够了，但复杂业务（多分支、循环、人在环、断点恢复）需要更强的编排能力。本章讲 LangGraph 的状态图思想，以及 Java 侧怎么落地。面试「复杂流程怎么编排」区分度题。

---

## 一、为什么需要流程编排

### 1.1 简单 Agent 的局限

- Spring AI 的 Advisor 链是线性的（前置->LLM->后置），适合单步增强。
- 但真实业务常需要：
  - **条件分支**：根据结果走不同路径。
  - **循环**：不够好就重来。
  - **并行**：多个子任务同时跑。
  - **人在环**：关键步骤暂停等人确认。
  - **断点恢复**：中途失败能从断点续跑。
- 这些超出线性 Advisor 能力，需要**状态图编排**。

### 1.2 编排的核心抽象

- **把流程显式化为图**：节点（Agent/步骤）+ 边（流转）+ 状态（共享数据）。
- 类比：工作流引擎（Activiti/Camunda）的思路用到 AI 编排。

> 💡 **面试金句**：简单 Agent 用线性 Advisor 链；复杂业务（条件/循环/并行/人在环/断点恢复）要状态图编排--把流程显式化为节点+边+共享状态，可精确控制流转。

---

## 二、LangGraph 状态图思想 ★

> LangGraph 是 Python 生态的状态图 Agent 编排，是复杂 Agent 编排的事实标杆。Java 侧借鉴其思想。13 章已讲概念，本章讲落地。

### 2.1 核心概念

| 概念 | 作用 |
|------|------|
| **State（状态）** | 贯穿整个图的共享数据（有序字典/对象），节点读写它 |
| **Node（节点）** | 一个步骤/Agent，接收 State 返回 State 更新 |
| **Edge（边）** | 节点间转移，固定边或**条件边**（函数根据 State 决定下个节点） |
| **条件路由** | 根据当前 State 动态选下一个节点（实现分支/循环） |
| **Checkpointer** | 每步状态持久化，支持中断恢复/人在环/回放 |

### 2.2 状态图能做什么

- **分支**：条件边根据结果走不同节点。
- **循环**：条件边指回上游节点（如评审不通过回到生成）。
- **并行**：多个节点同时执行后聚合。
- **人在环**：在某节点暂停，等人输入后继续。
- **持久化**：Checkpoint 每步存 State，失败可从断点续。

### 2.3 流程示例

```
[接收问题] -> [分类] --条件边--> [简单问答] -> [返回]
                    |
                    +---> [需检索] -> [RAG] -> [生成] -> [审核]
                                                          |
                                              通过<--不通过(回到生成)
```

- 这种带分支、循环、审核回退的流程，线性 Advisor 做不到，状态图能。

### 2.4 为什么取代黑盒 AgentExecutor

- 早期 LangChain 的 AgentExecutor 是「黑盒 ReAct 循环」，难控制、难调试、难加人审。
- LangGraph 把流程显式化成图，每一步可见可控，可精确加分支/暂停/回放。
- 这是复杂 Agent 从「黑盒」到「白盒可控」的演进（呼应 13 章）。

## 三、人在环 / 断点恢复 / 回放 ★

### 3.1 人在环（Human-in-the-Loop）

- 关键步骤（下单/退款/发外/删数据）**暂停**，等人确认后继续。
- 实现：在该节点 Checkpoint，等外部输入（用户确认）后恢复。
- 价值：高危操作不自主执行，安全合规。

### 3.2 断点恢复

- 长流程跑到一半失败（或服务重启），能从最近的 Checkpoint 续跑，不用从头。
- 实现：每步 State 持久化（DB/Redis），失败时加载最近 Checkpoint 继续。
- 价值：长任务可靠性，不用重跑省钱省时。

### 3.3 回放

- 记录每步 State，可「回放」某次执行的完整过程。
- 价值：调试（看每步状态）、复现 Bug、审计。

> 💡 **面试金句**：状态图 + Checkpoint 实现三件事：人在环（关键步骤暂停等人确认）、断点恢复（失败从最近 Checkpoint 续跑）、回放（复现执行过程调试审计）。这是复杂 Agent 可靠性和安全性的关键。

## 四、Java 侧编排方案

### 4.1 Spring AI Alibaba Graph ★

- 阿里在 Spring AI Alibaba 里提供的图编排能力，借鉴 LangGraph 思想。
- 支持 State/Node/Edge/条件路由/循环/Checkpoint。

```java
// 思路（伪代码）
StateGraph graph = new StateGraph(WorkflowState.class)
    .addNode("classify", classifyNode)
    .addNode("rag", ragNode)
    .addNode("generate", generateNode)
    .addNode("review", reviewNode)
    .addEdge(START, "classify")
    .addConditionalEdge("classify", state -> 
        state.needRetrieval() ? "rag" : "generate")
    .addEdge("rag", "generate")
    .addEdge("generate", "review")
    .addConditionalEdge("review", state -> 
        state.passed() ? END : "generate")   // 不通过回到生成
    .compile(checkpointer);  // 持久化支持中断恢复

// 执行
WorkflowState result = graph.invoke(initialState);
```

- 显式图结构，条件路由/循环清晰，Checkpoint 持久化。

### 4.2 自研状态机

- 复杂业务也可自研：用 Spring StateMachine / Camunda / 自研状态机。
- 把 Agent 步骤当状态机节点，状态持久化到 DB。
- 优势：可控、可审计、契合企业现有工作流引擎。劣势：要自己造轮子。

### 4.3 LangChain4j 的编排

- LangChain4j 的 AiServices 偏线性，复杂编排需自己组合（或等社区 Graph 能力）。
- 复杂流程更推荐 Spring AI Alibaba Graph。

### 4.4 选型

```
简单线性增强        -> Spring AI Advisor 链
复杂图编排(国产)    -> Spring AI Alibaba Graph
已有工作流引擎团队   -> Camunda/Activiti + AI 节点
非 Spring / 灵活     -> 自研状态机
```

## 五、并发分支编排

### 5.1 并行执行

- 多个独立子任务可并行（如多维度 Review、多源检索）。
- 状态图里用 fork-join：分叉并行执行，聚合后继续。

### 5.2 Java 实现

```java
// 用 CompletableFuture 并行跑子 Agent
CompletableFuture<String> r1 = CompletableFuture.supplyAsync(() -> agent1.run(task));
CompletableFuture<String> r2 = CompletableFuture.supplyAsync(() -> agent2.run(task));
CompletableFuture.allOf(r1, r2).join();
// 聚合 r1/r2 结果
```

- 或用 Spring AI Alibaba Graph 的并行节点。
- 注意：并行要控制并发度（限流）、处理部分失败、聚合结果。

## 六、生产踩坑

1. **过度编排**：简单任务上状态图，复杂度收益不匹配。线性 Advisor 够就别上图。
2. **状态设计混乱**：State 字段乱，节点间耦合。State 要清晰定义、最小化。
3. **条件路由死循环**：条件边指回上游形成循环，没退出条件。要有终止条件 + 最大轮数。
4. **Checkpoint 性能**：每步持久化有开销，高频场景要权衡（关键节点才 Checkpoint）。
5. **并行部分失败**：一个分支失败影响整体。要处理超时/部分失败策略。
6. **调试难**：图流程复杂，出 Bug 难定位。配合 Trace（20 章）+ 回放。
7. **人在环超时**：等人确认可能很久不回。要设超时 + 默认策略。

## 七、常见面试题

1. **复杂 Agent 流程怎么编排？**
   简单线性用 Spring AI Advisor 链；复杂（条件/循环/并行/人在环/断点恢复）用状态图编排--把流程显式化为节点+边+共享状态。Java 侧用 Spring AI Alibaba Graph 或自研状态机。

2. **LangGraph 的核心思想是什么？**
   把 Agent 当状态机/图编排：State（共享状态）、Node（步骤）、Edge（流转，含条件边实现路由/循环）、Checkpointer（状态持久化）。把黑盒 ReAct 循环显式化成可控图。

3. **什么是人在环？怎么实现？**
   关键步骤（下单/删数据）暂停等人确认后继续。实现：在该节点 Checkpoint 持久化，等外部输入后恢复执行。高危操作不自主执行，安全合规。

4. **断点恢复怎么实现？有什么用？**
   每步 State 持久化（DB/Redis），失败/重启时加载最近 Checkpoint 续跑。价值：长任务不用从头重跑，省钱省时提可靠性。

5. **条件路由怎么实现循环？**
   条件边根据当前 State 决定下一个节点，可指回上游（如审核不通过回到生成）形成循环。必须有终止条件（通过/最大轮数）防死循环。

6. **Spring AI Alibaba Graph 是什么？**
   阿里在 Spring AI Alibaba 里提供的状态图编排能力，借鉴 LangGraph：State/Node/Edge/条件路由/循环/Checkpoint。比 Spring AI 原生 Advisor 链更适合复杂流程。

7. **什么时候用状态图，什么时候用 Advisor 链？**
   简单线性增强（记忆/RAG/安全/日志）用 Advisor 链；复杂分支/循环/并行/人在环/断点恢复用状态图。别过度设计，简单任务上图是浪费。

8. **并行子任务怎么编排？**
   fork-join：分叉并行执行独立子任务，聚合后继续。Java 用 CompletableFuture 或 Graph 的并行节点。注意控制并发度、处理部分失败、超时。

## 八、资料勘误与重点提醒

1. **「复杂流程一定要状态图」是误区**：资料常暗示复杂就该上图。实际简单线性任务 Advisor 链够，状态图有复杂度成本，按需选，别过度设计。
2. **「LangGraph 只是 Python 的」漏了 Java 方案**：资料讲编排常只提 Python LangGraph。Java 有 Spring AI Alibaba Graph 等对标方案，思路一致。Java 工程师要能讲 Java 落地。
3. **「人在环就是加个确认」不严谨**：人是 Checkpoint 暂停 + 等外部输入 + 恢复执行，不是简单弹框。要处理超时、默认策略、状态持久化。资料常简化。
4. **Checkpoint 性本**：资料讲断点恢复不讲代价。每步持久化有 IO 开销，高频场景要权衡（关键节点才 Checkpoint）。
5. **并行编排的部分失败**：资料常给理想并行。实际某分支失败/超时要处理（重试/降级/部分聚合），不是简单 allOf。
6. **状态设计**：资料少讲 State 设计。State 字段混乱是编排出 Bug 主因，要清晰定义、最小化、版本化。
