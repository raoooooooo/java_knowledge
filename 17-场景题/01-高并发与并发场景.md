# 01 - 高并发与并发场景题

> 📌 **一句话理解**：高并发场景题的核心不是背方案，而是讲清"会出现什么问题 → 为什么 → 几种方案各自的代价与适用边界"。同一个超卖问题，DB 行锁、乐观锁、Redis 预扣减、分布式锁各有取舍，面试要的是这种权衡判断力。

---

## 核心场景

### 场景1：高并发下商品库存扣减 / 防超卖

**场景描述**

秒杀或抢购场景，库存只有 100 件，瞬间涌入 1 万个下单请求，如何保证不超卖（扣减后库存不为负）？

```java
// 典型问题代码：先查再扣，并发下必然超卖
public boolean deduct(Long skuId, int qty) {
    int stock = mapper.getStock(skuId);      // ① 查库存
    if (stock < qty) return false;           // ② 判断
    mapper.updateStock(skuId, stock - qty);  // ③ 扣减
    return true;
}
```

**问题分析**

1. **检查-执行非原子**：①查库存和③扣减之间有时间窗，两个线程同时读到 stock=1，都判断通过、都扣减，库存变 -1，超卖。
2. **DB 写放大**：即便加事务，普通 `UPDATE stock=stock-qty` 不带条件也会扣成负数。
3. 高并发下若请求直达 DB，行锁竞争激烈，TPS 上不去，响应变慢。

**解决方案**

| 方案 | 实现 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| DB 行锁 `for update` | 事务内 `SELECT ... FOR UPDATE` 锁行再扣 | 简单强一致 | 锁等待严重，TPS 低 | 低并发、库存精度要求高 |
| DB 乐观锁（CAS） | `UPDATE ... SET stock=stock-qty WHERE id=? AND stock>=qty` | 无锁竞争，失败重试即可 | 冲突多时重试率高 | 中等并发，推荐起步 |
| Redis 预扣减 + Lua | 库存预热到 Redis，Lua 原子扣减，异步落 DB | 抗高并发，性能极高 | 需保证 Redis 与 DB 最终一致 | 秒杀等超高并发 |
| 分布式锁 | 每个商品一把锁，串行扣减 | 控制简单 | 性能差，锁成瓶颈 | 库存极少且强一致 |

```java
// ✅ 乐观锁（带条件 UPDATE，DB 自带原子性，最推荐的起步方案）
int affected = mapper.deductIfEnough(skuId, qty);
// SQL: UPDATE stock SET stock = stock - #{qty} WHERE id = #{skuId} AND stock >= #{qty}
return affected > 0;   // 0 行受影响 = 库存不足

// ✅ Redis 预扣减（Lua 保证原子性，不能先 get 再 decr）
String lua =
  "local s = redis.call('GET', KEYS[1]) " +
  "if not s or tonumber(s) < tonumber(ARGV[1]) then return 0 end " +
  "redis.call('DECRBY', KEYS[1], ARGV[1]) " +
  "return 1";
Long ok = redis.eval(lua, Arrays.asList(stockKey), Arrays.asList(String.valueOf(qty)));
if (ok == 1) {
    mq.send("stock-deduct", new DeductMsg(skuId, qty));   // 扣减成功，MQ 异步落库
}
```

> ⚠️ 易错点/陷阱：
> - 乐观锁的 `WHERE stock>=qty` 必须在**一条 UPDATE 内完成**，不能"查出来在 Java 里判断再 update"，后者检查-执行非原子照样超卖。资料常说"查库存判断够不够再扣"，是错的。
> - Redis 预扣减**必须用 Lua** 把"判断够不够 + 扣减"做成原子操作。先 `get` 再 `decr` 两步分开，并发下同样超卖。
> - Redis 扣减成功但 MQ/DB 落库失败会致 Redis 与 DB 不一致，需配合对账与兜底补偿。

### 场景2：秒杀系统设计要点

**场景描述**

设计一个秒杀系统：10 点开抢 1 万件商品，预计瞬时 10 万 QPS，如何扛住？

**问题分析**

1. 瞬时流量是平时的百倍千倍，DB 扛不住。
2. 库存是核心稀缺资源，必须防超卖。
3. 下单链路长（校验 → 扣库存 → 创建订单 → 支付），串行慢。

**解决方案（分层防御）**

```
用户 → CDN/静态页 → 网关限流 → 活动校验 → Redis预扣库存 → MQ异步下单 → DB
      (前端削峰)   (令牌桶)    (防刷/答题)  (Lua原子扣减)   (削峰)     (最终落库)
```

| 环节 | 手段 | 作用 |
|------|------|------|
| 前端 | 按钮置灰、答题验证码、静态页 CDN | 拦掉无效点击，减少到达后端流量 |
| 网关 | 令牌桶限流、IP/用户维度限流 | 保护后端服务不被打垮 |
| 库存预热 | 活动前把库存写入 Redis | 避免开抢瞬间全打 DB |
| Redis 扣减 | Lua 原子扣减库存 | 高性能防超卖（见场景1） |
| 异步下单 | 扣减成功发 MQ，消费者异步创建订单 | 削峰，DB 按消费速率匀速写入 |
| 分段锁/分桶 | 库存拆成 N 段（如 100 拆 10×10）分别扣 | 减少单 key 热点竞争（见场景9） |
| 兜底 | 售罄快速失败、限购（每人 1 件） | 防黄牛、减少无效请求 |

> ⚠️ 易错点/陷阱：
> - 库存预热到 Redis 后**必须以 Redis 为扣减主源**，不能每笔都回查 DB，否则预热白做。
> - "异步下单"下用户拿到的是"下单排队中"，需前端轮询或长连接返回最终结果，不能让用户干等。
> - 限购要用 Redis 记录用户购买次数，且"判断+计数"要原子（Lua），否则一个用户刷出多单。

### 场景3：订单超时自动取消

**场景描述**

下单后 30 分钟未支付，订单需自动取消并回滚库存。如何实现？

**问题分析**

1. 不能让用户一直占用库存不支付（库存被恶意占用）。
2. 需要一个"到期触发"机制执行取消逻辑。
3. 订单量大时，方案的性能与可靠性差异大。

**解决方案对比**

| 方案 | 实现 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 定时任务扫表 | 每 N 分钟扫 `status=待支付 AND create_time<now-30min` | 简单，不丢任务 | 有延迟（最多 N 分钟）、扫全表慢 | 订单量小，精度要求低 |
| JDK DelayQueue | 延迟队列，到期取出执行 | 纯内存，快 | 重启丢失、单机、不持久 | 单机小任务 |
| Redis 过期通知 | 订单 key 设 TTL，监听过期事件 | 简单 | **不可靠**（见陷阱） | 不推荐用于关键业务 |
| RocketMQ 延迟消息 | 发延迟 30min 消息，到期消费执行取消 | 可靠、解耦、支持海量 | 依赖 MQ，4.x 延迟等级固定 | 中大型系统推荐 |
| 时间轮（Netty HashedWheelTimer） | 任务注册到时间轮槽位，到期触发 | 高效，适合大量短延迟任务 | 单机、重启需持久化 | 单机海量短延迟 |

```java
// ✅ RocketMQ 延迟消息（推荐）
Message msg = new Message("order-timeout", "create", orderId.getBytes());
msg.setDelayTimeLevel(3);   // 4.x 延迟等级（30min）；5.x 用 setDeliverTimeMs 任意时长
producer.send(msg);
// 消费者到期收到，执行取消订单 + 回滚库存
```

> ⚠️ 易错点/陷阱：
> - **资料常推荐"用 Redis key 过期事件（keyspace notifications）通知取消订单"，这是错的/不可靠**。Redis 过期通知默认关闭，且开启了也不保证送达（Redis 在 key 真正被删除时才发通知，大量 key 同时过期或负载高时事件可能丢失）。关键业务不能依赖它。
> - 定时任务扫表要**分页 + 按 id 渐进扫描**，一次性 `LIMIT` 深分页会越来越慢。
> - 延迟消息消费要做**幂等**（取消可能因重试执行多次，用状态机：只有"待支付"才能转"已取消"）。

### 场景4：接口限流实现

**场景描述**

对外接口要限制每秒最多 1000 次请求，超过的拒绝或排队。如何实现？

**问题分析**

1. 限流要解决"突发流量打垮服务"和"保护下游（DB/第三方）"。
2. 不同算法特性不同：有的允许突发，有的匀速。
3. 单机限流 vs 分布式限流（多实例合计不超限）。

**限流算法对比**

```
固定窗口计数器        滑动窗口               令牌桶              漏桶
|████| reset         |██|░░|██|             生产令牌入桶        匀速流出
|████|               |██|░░|██|            请求消耗令牌          (溢出拒绝)
临界点突刺问题         平滑过渡              允许突发(攒令牌)      严格匀速不突发
```

| 算法 | 原理 | 突发流量 | 复杂度 | 特点 |
|------|------|----------|--------|------|
| 固定窗口计数器 | 单位时间内计数，超限拒绝 | 临界点放行 2 倍流量 | 低 | 简单但有临界突刺 |
| 滑动窗口 | 细分小窗口滑动统计 | 平滑 | 中 | Sentinel 采用 |
| 令牌桶 | 匀速生令牌，请求消耗令牌 | 允许（攒的令牌可突发） | 中 | 最常用，允许突发 |
| 漏桶 | 请求进桶，匀速漏出处理 | 拒绝溢出 | 中 | 严格匀速，不突发 |

**单机 vs 分布式**

| 维度 | 单机限流（Sentinel/Resilience4j） | 分布式限流（Redis+Lua） |
|------|-----------------------------------|--------------------------|
| 计数位置 | 本地内存 | Redis 共享计数 |
| 优点 | 无网络开销，性能高 | 多实例合计精确限流 |
| 缺点 | 只限单机，无法全局总量 | 有网络开销，Redis 是瓶颈 |
| 适用 | 单机保护、线程池隔离 | 全局 QPS / 用户级总量限流 |

```java
// ✅ 分布式限流：Redis + Lua（令牌桶）
String lua =
  "local key=KEYS[1] local rate=tonumber(ARGV[1]) local cap=tonumber(ARGV[2]) " +
  "local now=tonumber(ARGV[3]) local permits=tonumber(ARGV[4]) " +
  "local last=tonumber(redis.call('hget',key,'ts')) or now " +
  "local tokens=tonumber(redis.call('hget',key,'tok')) or cap " +
  "tokens=math.min(cap, tokens+(now-last)*rate) " +   // 按时间补充令牌
  "if tokens<permits then return 0 end " +            // 不够则拒绝
  "redis.call('hmset',key,'tok',tokens-permits,'ts',now) " +
  "redis.call('expire',key,60) return 1";
```

> ⚠️ 易错点/陷阱：
> - 固定窗口计数器有**临界突刺**：窗口切换瞬间（如 0.9~1.0s 放满 + 1.0~1.1s 放满）实际放了 2 倍限流值。滑动窗口能缓解。
> - 分布式限流用 Redis 时**必须 Lua 保证原子**，不能先 get 计数再 incr，并发下会超限。
> - 限流阈值要从压测得出，拍脑袋设的值要么形同虚设要么误杀。

### 场景5：线程池实战场景

**场景描述**

线上接口用线程池处理异步任务，如何设置参数？突发流量怎么办？阿里为何禁用 `Executors`？

**问题分析**

1. 核心参数（核心线程数、最大线程数、队列、拒绝策略）配置不当会 OOM 或吞吐低。
2. 突发流量下队列堆积导致内存溢出。
3. 优雅关闭要保证已提交任务执行完。

**参数设置思路**

```
CPU 密集型：核心线程数 = CPU 核数 + 1        (减少切换)
IO  密集型：核心线程数 = CPU 核数 × (1 + IO等待/CPU时间)  ≈ 2×CPU核数
```

公式只是起点，实际以压测和上下文切换开销为准。队列务必用有界队列防 OOM。

**阿里为何禁用 `Executors`**

| Executors 方法 | 实际队列/线程 | 风险 |
|----------------|---------------|------|
| `newFixedThreadPool` | 无界 `LinkedBlockingQueue` | 任务堆积 OOM |
| `newSingleThreadExecutor` | 无界队列 | 同上 OOM |
| `newCachedThreadPool` | 最大线程 `Integer.MAX_VALUE` | 线程数爆炸 OOM |

应手动 `new ThreadPoolExecutor(...)`，显式设队列容量与最大线程数。

```java
// ✅ 手动构建，有界队列 + 明确拒绝策略
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    corePoolSize, maxPoolSize, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),        // 有界！
    new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略：回退给调用线程降速
);
```

**拒绝策略选择**

| 策略 | 行为 | 适用 |
|------|------|------|
| AbortPolicy | 抛异常（默认） | 不允许丢失，调用方感知 |
| CallerRunsPolicy | 退回调用线程执行 | 自动降速，保护系统 |
| DiscardPolicy | 丢弃，不抛异常 | 允许丢（日志等） |
| DiscardOldestPolicy | 丢队列最老的 | 只关心最新 |

**优雅关闭**

```java
pool.shutdown();          // 不接新任务，已提交继续执行
if (!pool.awaitTermination(60, TimeUnit.SECONDS)) {
    pool.shutdownNow();   // 超时强停，中断正在执行的
}
```

> ⚠️ 易错点/陷阱：
> - 用无界队列时，最大线程数**永远不会触发**（队列装不满就不会创建到 max），等于退化成固定线程池且 OOM。这是 Executors 被禁的根因。
> - 突发流量下 CallerRunsPolicy 把任务推回 Tomcat 线程执行，相当于**自然限流降速**，比直接 Abort 更稳。
> - 线程池隔离：不同业务用不同线程池，避免一个业务拖垮导致全局拒绝（如查询池与下单池分离）。

### 场景6：分布式计数 / 排行榜实时刷新

**场景描述**

实时统计文章阅读量、直播间在线人数、商品销量排行榜。如何实现？

**问题分析**

1. 计数高频写，直接写 DB 扛不住。
2. 排行榜需排序 Top N，DB `ORDER BY` 全表扫慢。
3. 高并发下原子计数是关键。

**解决方案**

| 场景 | 方案 | 实现 |
|------|------|------|
| 简单计数（阅读量/点赞） | Redis `INCR` | 原子自增，异步批量落 DB |
| 高并发计数（Java 内） | `LongAdder` | 分段累加，比 `AtomicLong` 高并发下快 |
| 排行榜 Top N | Redis `ZSet` | `ZADD` 加分数，`ZREVRANGE` 取前 N |

```java
// ✅ Redis 计数 + 批量落库
Long count = redis.incr("article:read:" + articleId);   // 原子自增
// 定时任务每分钟把 Redis 计数批量 update 到 DB，减少 DB 压力

// ✅ 排行榜：ZSet
redis.zadd("rank:sales", salesCount, skuId);              // 加分
List<String> top10 = redis.zrevrange("rank:sales", 0, 9); // 取销量前10
```

**为什么 `LongAdder` 比 `AtomicLong` 快**

```
AtomicLong: 所有线程 CAS 竞争同一个 value → 高并发大量自旋失败
LongAdder:  分成多个 Cell，各线程先 CAS 自己的 Cell，最后 sum = base + Σcell
            ┌─base─┐ ┌─cell0─┐ ┌─cell1─┐ ┌─cell2─┐
            │  ...  │ │  ...   │ │  ...   │ │  ...   │
            └───────┘ └────────┘ └────────┘ └────────┘
                        sum() = base + cell0 + cell1 + cell2
```

> ⚠️ 易错点/陷阱：
> - `LongAdder.sum()` 不是精确瞬时的（各 Cell 分散写入时 sum 可能略偏），适合统计场景，不适合做精确账户扣减。
> - 排行榜用 ZSet，分数相同时按成员字典序排；业务上若需"同分按时间先后"，要在 score 里编码时间（如 `score = 销量×1e10 + (MAX-时间戳)`）。
> - Redis 计数宕机会丢未落库部分，重要计数要落 DB 兜底。

### 场景7：如何保证接口幂等性

**场景描述**

用户连续点"提交订单"按钮，或网络超时客户端重试，导致同一请求执行多次。如何保证重复执行结果一致？

**问题分析**

1. **查询天然幂等**（SELECT 多次结果一样），不需要额外处理。
2. **写操作（增删改）才需保证幂等**：重复插入产生重复数据、重复扣款、重复发货。
3. 重试、消息重复消费、网络重发是幂等问题的常见来源。

**解决方案**

| 方案 | 实现 | 适用 | 局限 |
|------|------|------|------|
| 唯一索引 | DB 表对业务唯一键建唯一索引，重复插入抛异常被拦 | 插入场景 | 仅插入，需处理异常 |
| Token 机制 | 下单前先申请一次性 token，提交时校验+删除 | 前端防重复提交 | 需额外接口 |
| 状态机 | 业务状态流转约束，如"已支付"不能再转"待支付" | 更新场景（订单流转） | 仅限有状态的业务 |
| 乐观锁（版本号） | `UPDATE ... WHERE id=? AND version=?` | 更新场景 | 冲突需重试 |
| 防重表 | 唯一键写入防重表，成功才执行业务 | 通用（含 MQ 消费去重） | 需额外表 |
| 分布式锁 | 同一业务 ID 加锁串行执行 | 通用 | 性能差 |

```java
// ✅ Token 机制（前端防重复提交）
// 1. 进页前 GET /token → 服务端存 Redis(token, 随机串)
// 2. 提交带 token，服务端 Lua: 存在则删除返回1，不存在返回0
String lua = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end";

// ✅ 唯一索引（插入去重）
// 订单表 order_no 建唯一索引，重复插入触发 DuplicateKeyException，捕获转查询返回
try { orderMapper.insert(order); }
catch (DuplicateKeyException e) { order = orderMapper.selectByNo(orderNo); } // 已存在，返回已有

// ✅ 状态机（更新去重）
// SQL: UPDATE order SET status='PAID' WHERE id=? AND status='UNPAID'
// 重复请求时 status 已是 PAID，0 行受影响，天然幂等
```

> ⚠️ 易错点/陷阱：
> - **幂等要分清对象**：查询天然幂等不用管，只有写操作才需保证。资料有时笼统说"所有接口都要幂等"，不准确。
> - Token 删除必须原子（Lua），否则"先判断存在再删除"两步分开，并发下两个请求都判断成功都删除，失效。
> - MQ 消费幂等最可靠的是**防重表/唯一索引**，靠业务状态机兜底，不能依赖内存幂等标记（重启丢失）。

### 场景8：并发场景下 long / Double 计算精度问题

**场景描述**

多线程累加金额、统计计数，发现结果不对：`float`/`double` 算金额丢精度，`long` 并发自增少计。

**问题分析**

1. **浮点精度**：`0.1 + 0.2 != 0.3`，`double` 二进制无法精确表示十进制小数，金额计算必出误差。
2. **并发计数丢更新**：`count++` 不是原子操作（读-改-写三步），多线程下丢失更新。

**解决方案**

| 问题 | 方案 | 代码 |
|------|------|------|
| 金额精度 | `BigDecimal` | `new BigDecimal("0.1")` |
| 并发 long 计数 | `AtomicLong` / `LongAdder` | 高并发优先 `LongAdder` |

```java
// ❌ 错误：double 算钱
double total = 0.1 + 0.2;   // = 0.30000000000000004

// ❌ 错误：BigDecimal 用 double 构造
new BigDecimal(0.1);        // 仍是 0.1000000000000000055...

// ✅ 正确：BigDecimal 用 String 构造
BigDecimal total = new BigDecimal("0.1").add(new BigDecimal("0.2")); // 精确 0.3

// ❌ 错误：并发 count++
private long count;
count++;   // 非原子，丢更新

// ✅ 正确：LongAdder（高并发）/ AtomicLong（低并发）
private final LongAdder count = new LongAdder();
count.increment();
```

> ⚠️ 易错点/陷阱：
> - `new BigDecimal(double)` 仍有精度问题，**必须用 `new BigDecimal(String)`** 或 `BigDecimal.valueOf(double)`（内部先转 String）。
> - `BigDecimal` 比较用 `compareTo` 不用 `equals`（`equals` 把 `1.0` 和 `1.00` 视为不等）。
> - `LongAdder` 高并发计数优于 `AtomicLong`，但 `sum()` 非强一致瞬时（见场景6），不能用于精确账户。

### 场景9：热点 key 问题

**场景描述**

某个 key（如热门商品库存、明星微博）被大量请求同时访问，单点 Redis 节点压力过大甚至打挂。

**问题分析**

1. 集群模式下，一个 key 只落在一个 slot/节点，无法水平分担。
2. 读热点把单节点 CPU/网卡打满；写热点（如热点库存扣减）单 key 竞争激烈。
3. 缓存击穿（热点 key 过期瞬间）放大问题。

**解决方案**

| 类型 | 方案 | 说明 |
|------|------|------|
| 读热点 | 本地缓存（Caffeine）+ 多级缓存 | 绝大部分请求走本地内存，不打 Redis |
| 读热点 | 多副本 key | 同一数据写多个 key（`hotkey:1`~`hotkey:N`），读随机选一个，分散到不同节点 |
| 写热点 | 分段锁/分桶 | 库存拆成 N 段，扣减时随机选一段，最后合并 |
| 击穿 | 热点 key 永不过期 + 异步更新 | 不设 TTL，后台线程定期刷新；或逻辑过期 |

```
分桶库存扣减（写热点）：
  stock:0=25  stock:1=25  stock:2=25  stock:3=25   (总100拆4桶)
  请求随机选一桶 DECRBY，桶为0再选下一桶，最后合并到 DB
  → 4 桶分散到不同 slot，写竞争降到 1/4
```

> ⚠️ 易错点/陷阱：
> - 本地缓存（Caffeine）有多机数据不一致问题，适合**读多写少且容忍短暂不一致**的场景，TTL 要短。
> - 多副本 key 要保证**所有副本同时更新**，否则读到旧数据；写热点用分桶要处理好"某桶售罄转下一桶"的合并逻辑。
> - 热点 key 永不过期意味着更新靠主动刷新，需有更新失败兜底，否则数据长期陈旧。

### 场景10：多线程下如何安全使用 SimpleDateFormat

**场景描述**

线上偶现日期解析错误、年份错乱。排查发现 `SimpleDateFormat` 被多线程共享使用。

**问题分析**

1. `SimpleDateFormat` **不是线程安全**的。
2. 根因：其内部维护一个 `Calendar` 成员变量，`parse`/`format` 过程中会修改这个共享的 `Calendar`，多线程并发调用时互相覆盖，导致解析结果错乱。
3. `static final SimpleDateFormat` 这种"优化"写法，在高并发下是定时炸弹。

**解决方案**

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| 每次 new | 方法内 `new SimpleDateFormat` | 简单，但每次创建对象有开销 |
| ThreadLocal | 每线程一个实例 | 复用且线程安全，但线程多占内存，需清理防泄漏 |
| DateTimeFormatter（推荐） | Java 8 `java.time` | 线程安全、不可变、API 现代 |

```java
// ❌ 错误：共享 static 实例
private static final SimpleDateFormat SDF = new SimpleDateFormat("yyyy-MM-dd");
// 多线程同时 SDF.parse() → Calendar 被覆盖 → 结果错乱

// ✅ 方案一：ThreadLocal（兼容老代码）
private static final ThreadLocal<SimpleDateFormat> TL =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
TL.get().parse(dateStr);

// ✅ 方案二：DateTimeFormatter（推荐，不可变线程安全）
private static final DateTimeFormatter DTF = DateTimeFormatter.ofPattern("yyyy-MM-dd");
LocalDate.parse(dateStr, DTF);          // 线程安全，任意共享
LocalDate.now().format(DTF);
```

> ⚠️ 易错点/陷阱：
> - **资料常说"SimpleDateFormat 不安全是因为没加 synchronized"，不准确**。根因是 `Calendar` 成员变量被多线程共享覆盖；加 `synchronized` 能解决但性能差，非根因正解。
> - `DateTimeFormatter` 是**不可变对象**，天然线程安全，是新项目首选，不要再纠结 `SimpleDateFormat` 的线程安全写法。
> - ThreadLocal 用完要 `remove()`，否则线程池复用线程时残留导致内存泄漏和数据串号。

### 场景11：分布式锁实现与选型

**场景描述**

多台机器上的服务同时操作同一资源（如同一订单、同一库存），本地锁无效，需要分布式锁。

**问题分析**

1. 跨进程互斥，本地 `synchronized`/`ReentrantLock` 只能锁单 JVM。
2. 需考虑：获取/释放原子性、锁超时（防死锁）、可重入、高可用。

**解决方案对比**

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| Redis SETNX | `SET key val NX PX timeout` + 释放用 Lua 校验 owner | 简单、性能高 | 不可重入、需自己续期、主从切换可能丢锁 |
| Redisson | 封装 Redis，含看门狗续期、可重入、公平锁 | 功能全、开箱即用 | 仍依赖 Redis 主从一致性（极端丢锁） |
| ZooKeeper | 临时顺序节点，监听前一个节点 | 强一致（CP），锁可靠 | 性能低于 Redis，实现复杂 |
| DB 唯一索引 | 插入锁记录，删记录释放 | 强一致、简单 | 性能差，DB 单点 |

```java
// ✅ Redisson（推荐，生产常用）
RLock lock = redisson.getLock("order:lock:" + orderId);
try {
    if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {   // 等待3s，看门狗自动续期
        // 业务逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

> ⚠️ 易错点/陷阱：
> - **Redis 分布式锁不是强一致**：主从异步复制，master 加锁成功后宕机，slave 提升时未同步到锁，新请求又加锁成功 → 双重加锁（Martin Kleppmann 与 antirez 经典争论）。强一致要求用 ZK/etcd。
> - 自己写 SETNX 释放锁必须用 Lua 校验 value 是自己才能删，否则可能删掉别人的锁。
> - 必须设过期时间防死锁，但过期时间难估，所以 Redisson 用**看门狗**自动续期，不要禁用。

### 场景12：高并发下缓存与数据库一致性

**场景描述**

更新数据时，先改 DB 还是先改缓存？高并发读写下如何保证缓存与 DB 一致？

**问题分析**

1. 缓存与 DB 是两个系统，无法做到真正强一致，只能最终一致。
2. 先删缓存再更新 DB：删后、更新前有读请求把旧值又写回缓存（脏数据残留）。
3. 先更新 DB 再删缓存：删缓存失败则缓存留旧值。

**解决方案**

| 方案 | 流程 | 问题 |
|------|------|------|
| 先删缓存 → 更新 DB | 简单 | 并发下旧值回写缓存，不一致窗口长 |
| 更新 DB → 删缓存（Cache Aside，推荐） | 读时按需回填 | 删除失败需重试/兜底 |
| 延迟双删 | 先删 → 更新 DB → 延时再删一次 | 解决旧值回写，延时难定 |

```
Cache Aside（旁路缓存，最常用）：
  读：查缓存 → 命中返回；未命中查 DB → 写回缓存
  写：更新 DB → 删除缓存（不是更新缓存，避免并发写乱序）
```

```java
// ✅ Cache Aside + 兜底
public void update(Stock s) {
    mapper.update(s);          // 1. 先更新 DB
    redis.del(key);           // 2. 再删缓存
    // 3. 兜底：发 MQ / 订阅 binlog（如 Canal）再删一次，防本步失败
}
```

> ⚠️ 易错点/陷阱：
> - **为什么删缓存而不是更新缓存**：并发写时，A 先更新 DB 但后更新缓存、B 后更新 DB 但先更新缓存，缓存会停留在 A 的旧值。删缓存让下次读按需回填，更安全。
> - **延迟双删的延时无法精确**（要大于一次读的耗时），且删后仍有窗口，属于经验方案。
> - 强一致需求（如金融）不能依赖缓存一致性方案，应直接读 DB 或用分布式事务，缓存只做非核心读加速。

## 常见面试题

> 速记版，详细方案权衡见上方各场景。

1. **`for update` 和乐观锁哪个防超卖好？** 高并发用乐观锁（条件 `UPDATE ... WHERE stock>=qty`，无锁竞争）；低并发强一致用 `for update`。
2. **Redis 扣库存为什么必须 Lua？** 判断+扣减必须原子，先 `get` 再 `decr` 并发下超卖。
3. **订单超时取消为什么不用 Redis 过期通知？** 过期事件不保证送达，用 RocketMQ 延迟消息或定时扫表。
4. **令牌桶和漏桶区别？** 令牌桶允许突发（攒令牌），漏桶严格匀速（溢出拒绝）。
5. **为什么阿里禁用 `Executors`？** 无界队列/无限线程致 OOM，用手动 `ThreadPoolExecutor` + 有界队列。
6. **`LongAdder` 为什么比 `AtomicLong` 快？** 分段 Cell 各自 CAS，减少单点竞争。
7. **接口幂等只针对写操作吗？** 是，查询天然幂等，写操作才需保证（唯一索引/token/状态机/防重表）。
8. **`BigDecimal` 比较用什么？** `compareTo`，不用 `equals`（`1.0`≠`1.00`）；构造用 `String` 不用 `double`。
9. **`SimpleDateFormat` 非线程安全根因？** `Calendar` 成员变量被多线程共享覆盖，首选 `DateTimeFormatter`。
10. **热点 key 怎么处理？** 读用本地缓存/多副本 key，写用分桶，击穿用永不过期+异步更新。
11. **Redis 分布式锁可靠吗？** 非强一致（主从切换丢锁），强一致用 ZK/etcd；释放锁必须 Lua 校验 owner。
12. **缓存与 DB 一致性最佳实践？** Cache Aside（更新 DB -> 删缓存），只能最终一致，强一致直接读 DB。

## 资料勘误与重点提醒

> 本节集中纠正场景题中常见的错误说法与易踩的坑，面试时务必讲对。

1. **Redis 预扣减库存必须 Lua 原子**：资料常说"先 `get` 库存判断够不够再 `decr`"，这是错的。两步分开，并发下两个请求都 get 到够、都 decr，照样超卖。必须用 Lua 把"判断+扣减"做成一次原子操作。

2. **乐观锁不能"查出来在 Java 里判断"**：正确的乐观锁是 `UPDATE ... WHERE id=? AND stock>=qty`（或带 version），靠 DB 单条 UPDATE 的原子性。先 `SELECT` 出来在应用层判断再 `UPDATE`，检查-执行非原子，照样超卖。

3. **Redis 过期通知不可靠，不能做订单超时取消**：资料常推荐"订单 key 设 TTL，监听过期事件取消订单"。Redis keyspace notifications 默认关闭，且 key 过期事件**不保证送达**（大量同时过期或高负载时丢失）。关键业务用 RocketMQ 延迟消息或定时任务扫表。

4. **幂等性要区分对象**：查询操作天然幂等（多次 SELECT 结果一致），不用额外保证。只有写操作（插入/更新/删除）才需要唯一索引、token、状态机、防重表等手段。笼统说"所有接口都要幂等"不准确。

5. **SimpleDateFormat 非线程安全根因是 Calendar 成员变量共享**：资料常说"因为没加 synchronized"，不准确。根因是 `SimpleDateFormat` 内部持有 `Calendar` 成员变量，`parse`/`format` 会修改它，多线程共享时互相覆盖。解决方案首选 `DateTimeFormatter`（不可变、线程安全），而非给 `SimpleDateFormat` 加锁。

6. **`Executors` 被禁的根因是无界队列/无限线程**：`newFixedThreadPool` 用无界 `LinkedBlockingQueue`，任务堆积 OOM；`newCachedThreadPool` 最大线程 `Integer.MAX_VALUE`，线程爆炸 OOM。用手动 `ThreadPoolExecutor` + 有界队列替代。

7. **Redis 分布式锁非强一致**：主从异步复制下 master 宕机切换会丢锁，强一致场景用 ZK/etcd。自己实现 SETNX 释放锁必须用 Lua 校验 owner。

8. **缓存一致性只能最终一致**：Cache Aside（更新 DB → 删缓存）是最实用的方案；强一致需求不要依赖缓存一致性方案，直接读 DB。

9. **`LongAdder.sum()` 非强一致瞬时**：高并发下各 Cell 分散写入，`sum()` 可能略偏，适合统计计数，不适合精确账户扣减。

10. **限流必须原子**：分布式限流用 Redis 必须 Lua 保证计数原子，先 get 再 incr 会超限。固定窗口有临界突刺，敏感场景用滑动窗口或令牌桶。
