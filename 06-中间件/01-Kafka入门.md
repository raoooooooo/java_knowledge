## 一、核心概念

### 1.1 初识Kafka

**什么是 Kafka**
- 由 Scala 和 Java 开发的**分布式消息发布/订阅系统**，后升级为分布式事件流处理平台
- 大数据领域数据交换的核心组件之一

**五大核心特性**
- 高吞吐：单机每秒处理百万级消息
- 低延迟：毫秒级延迟
- 高伸缩：横向扩展，支持上千节点
- 高可靠：副本机制，消息不丢
- 高并发：支持海量消息生产与消费

**发展历程**
- 2010 年 LinkedIn 主导开发，首席架构师 Jay Kreps 因崇拜作家 Franz Kafka（著有《变形记》）而命名，名称与软件特性无关
- 2011 年捐献给 Apache 基金会，进入孵化器
- 2012 年 10 月毕业，成为 Apache 顶级项目
- 由消息日志传输系统转型为分布式事件流处理平台

> 💡 **面试金句**：Kafka 借鉴 JMS 规范思想但并未完全遵循，这正是其名称为 Kafka 而非 KafkaMQ 的原因

官网：https://kafka.apache.org/

### 1.2 消息队列与 JMS 规范

**MQ 的含义**
- MQ = Message Queue（消息队列）
- 同类产品：RabbitMQ、ActiveMQ、RocketMQ
- 核心功能：传输数据

**JMS 规范**
- JMS = Java Message Service（Java 消息服务），Java 平台消息中间件通用规范，定义标准接口
- 类比理解：**JMS 之于消息中间件 ≈ JDBC 之于数据库**
- 文档中还提到两种相关协议规范：
  - **AMQP**（Advanced Message Queuing Protocol，高级消息队列协议）：RabbitMQ 遵循的跨平台规范，兼容 JMS
  - **MQTT**（Message Queuing Telemetry Transport，消息队列遥测传输）：用于物联网小型设备间消息传输的通讯协议

**JMS 四大组件**

| 组件 | 说明 |
|------|------|
| JMS Provider | 消息提供者，即消息中间件本身（Kafka/RabbitMQ/ActiveMQ） |
| JMS Message | 消息，包含消息头、消息属性、消息主体 |
| JMS Producer | 消息生产者，发送消息的客户端应用 |
| JMS Consumer | 消息消费者，接收消息的客户端应用 |

**两种消息模型**

| 模型 | 基础 | 消费者数量 | 说明 |
|------|------|-----------|------|
| P2P 点对点 | 队列 Queue | 一条消息只一个消费者 | 生产者发到队列，消费者从队列取 |
| Pub/Sub 发布订阅 | 主题 Topic | 一条消息可被多个消费者消费 | 生产者按主题发布，消费者订阅主题 |

> Kafka 采用 **发布/订阅（Pub/Sub）模型**

### 1.3 生产者-消费者模式

**核心思想**
- 生产者和消费者**不直接通信**，通过中间的缓冲区（阻塞队列/中间件）通信
- 生产者生产完数据直接扔给缓冲区，不用等消费者
- 消费者从缓冲区取数据，不找生产者要

**三大作用**
- **解耦**：生产者消费者彼此独立，互不影响
- **异步**：生产者无需等待消费者处理
- **削峰**：缓冲区平衡双方处理能力差异，扛住流量洪峰

**实现方式**
- 单机环境：阻塞式队列
- 分布式环境：第三方中间件（Kafka 即是此类）

### 1.4 消息中间件对比

| 特性 | ActiveMQ | RabbitMQ | RocketMQ | Kafka |
|------|----------|----------|----------|-------|
| 单机吞吐量 | 万级 | 万级 | 10万级 | 10万级 |
| Topic数量影响 | - | - | 几千量级 | 几百量级，过多则吞吐下降 |
| 时效性 | ms级 | 微秒级（最低） | ms级 | ms级 |
| 可用性 | 高（主从） | 高（主从） | 非常高（分布式） | 非常高（分布式） |
| 消息可靠性 | 可能丢 | 基本不丢 | 可优化到0丢失 | 可优化到0丢失 |
| 适用场景 | 早期JavaEE | 企业级/低延迟 | 电商金融 | 大数据领域 |

**选型建议**
- 大数据场景：Kafka
- JavaEE 业务：ActiveMQ / RabbitMQ / RocketMQ
- 大数据与 JavaEE 融合项目：Kafka 是不错选择

**对比小结：RocketMQ vs Kafka（举例）**

> 💡 **通俗类比**：Kafka 像「高速公路物流卡车」--重吞吐、跑大宗货物（日志/数据流）；RocketMQ 像「顺丰快递」--重准确送达、带签收回执（业务可靠、事务消息）

**相同点**
- 都是分布式消息中间件，单机吞吐量同属 10 万级
- 都采用发布/订阅模型，基于 Topic + 分区/队列
- 都支持高可用（分布式架构）和分区并行消费
- 消息可靠性都可优化到 0 丢失
- 时效性均为 ms 级

**差异重点**

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 出身背景 | LinkedIn 开源，大数据导向 | 阿里开源，电商/金融业务导向 |
| 设计目标 | 极致吞吐、日志流处理 | 业务可靠性、功能完备 |
| Topic 数量影响 | 几百量级，过多则吞吐大降 | 可达几千量级，更稳 |
| 事务消息 | 弱事务（生产者事务） | 强事务（半消息机制，原生支持） |
| 定时/延迟消息 | 不支持（需自行实现） | 原生支持 |
| 功能丰富度 | MQ 功能简单 | 完善（重试、死信队列、消息轨迹） |
| 底层存储 | 每个 Partition 独立文件 | 同一 Topic 的队列共用文件 |
| 适用场景 | 大数据、日志、流处理 | 电商订单、金融交易、业务解耦 |

**一句话区分**：要扛海量数据吞吐 → 选 Kafka；要业务消息可靠 + 事务 + 延迟 → 选 RocketMQ

### 1.5 ZooKeeper 与 KRaft 模式

**ZooKeeper 是什么**
- 开源的分布式应用程序协调服务软件
- 保证分布式多节点间环境与配置信息一致

**Kafka 中的角色**
- Kafka 多 Broker 节点间靠 ZK 协调调度
- 存储集群元数据、参与选举、监控节点变化

**ZK 三大核心机制**

| 机制 | 说明 |
|------|------|
| 数据结构 | Tree 树形，每个节点可存储数据（元数据/配置） |
| 节点类型 | 持久节点（一直存在） + 临时节点（连接时创建，断开时删除） |
| Watch 监控 | 监控节点变化，变化时通知客户端 |

**去 ZK 化趋势（重点）**
- ZK 是外部依赖，导致 Kafka 与其他软件耦合，制约发展
- Kafka 2.8+ 引入 Raft 算法实现节点间协调管理（**KRaft 模式**），替代 ZK
- 计划 **4.X 版本完全移除 ZooKeeper**
